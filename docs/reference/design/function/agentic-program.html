Agentic Program: tools, skills, and agentic functions as one concept

The three are degrees of the same thing:a reusable unit of work, differing only in how much is encoded. A tool is the smallest one-step form; a skill gives guidance while the model controls the process; an agentic function fixes the process in code and leaves only decision points. Under the common nameagentic program, they occupy three positions on one continuum rather than three unrelated categories. This page defines that continuum, gives criteria for choosing a form, and checks whether conceptual unification also requires implementation unification.

Why no recurring work pattern was encoded

The old distill skill offered two outputs: SKILL.md for judgment-heavy work and@agentic_functionfor mechanical work, but implementation covered only the former. That default skill has now been removed from the package; reusable product workflows belong to Programs. Predictably, none of the four current agentic functions came from distill, and prose remained the easiest output at every session's end. Encoding one-off work does not lack capability; writing a function needs a path as easy as writing prose.

04Ideal state

05Answers to six design questions

1. What is the continuum's axis? Are there only three positions?

The axis iswhere the work's step sequence resides and whether it is enforceable: tools have no step sequence, covering one step while inter-step decisions occur in conversation; skills put steps in prose that models may disregard; agentic functions put steps in Python enforced by the interpreter.

Of two candidate descriptions,“how much is encoded” is more precise than “who controls the flow.”The latter mischaracterizes the tool end:mixture_of_agentsis a@functiontool whose body fans out to N models, gates minimum successes, then aggregates once. Control flow is entirely code-defined, so control ownership is not the distinction.

Measurable definition:how much must remain identical across two runs of the same work.Tools guarantee little; skills are broadly similar but vary in detail; agentic functions retain identical structure with varying content. This makes the axis measurable.

There are more than three positions.These are common positions. A structure containingdecision.makeinside a fixed structure embeds model decisions in code; a skill whose third step says “invokesurvey_references” embeds code within prose. Work may therefore mix enforced steps and flexible decisions.

Another point the design must state:decorators do not determine position on the continuum.See question 3.

2. Which form should a new capability use?

Three questions, stopping at the first match (diagram in section 3):

Q1 Does the model need to participate between steps?Not whether a model is called, but whether execution must inspect its answer before deciding what follows. If no, use a tool even with internal model calls.mixture_of_agentsinvokes models N+1 times internally but is one externally visible input/output operation, so its tool form is correct.

Q2 Can participation points be identified beforehand?Can code authors specify which steps involve a model and how often? If no, use a skill: count and placement become known only during actual inspection.

Q3 Would an omitted step be noticed immediately?This concerns value, not classification. If obviously wrong output reveals omissions, a skill suffices without code maintenance. Use an agentic function when omissions remain hidden: verifying before delivery, checking citations, or inspecting all eight repositories.Encode the checklist when its omissions would otherwise go unnoticed.

Each form has a falsifiable acceptance criterion:Toola correct choice has a parameter schema fully describing input, without “before use, first...” in its description;Skilla correct choice contains decision criteria rather than numbered steps;agentic functiona correct choice lets you state a model-call upper bound; otherwise the process is not truly encoded.

These criteria explain the current 46 / 7 / 4 distribution. Most capabilities are single input/output operations; pre-identifiable decision points with hidden omissions are uncommon. The fourth case is one-time work: do it directly without a reusable artifact.

5. After unification, how many categories should the model see?

Previously there werethree and a half, the half being a second chat-format listing of the same skills without paths and capped at 20. It is removed; now there arethree: ① schemas in the tools array (split by@functionplus@agentic_function, split_tools_for_dispatch); ② deferred catalog (defer=True, with one name/description line in the system prompt andtool_searchloading schemas into the current turn); ③<available_skills>(name, description, and absolute path, opened through theskill tool orread).

② and ③have identical shapes: one name/description line in the system prompt plus a content-loading action. Only the action name and catalog label differ.skillThe tool itself already belongs to ②, so both catalogs at least point to the same loading semantics. Combining their listings is the next rendering-layer task; registry unification is complete.

The final target istwo: directly callable tools with schemas, and named entries requiring loading through one catalog/action that dispatches by type: schemas for deferred tools and bodies for skills.

Is predictable cost a main benefit?

Yes, precisely stated: after encoding,call counts are not fixed, but have visible upper bounds in code.
