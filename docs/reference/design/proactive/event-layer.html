DESIGN · EVENT LAYER

Oneunified event stream,
for the entire framework.

Signals that something happened in the framework are currently spread across six disconnected mechanisms. This layer unifies them through one bus:sources emit and consumers subscribe. Proactive is only its first consumer.

01 · ARCHITECTURE

Architecture overview

All components run in the same worker process(as daemon threads), so the bus is a process-level singleton. Event flow:

Class-A events · Observation (asynchronous) Class-B events · Observation (asynchronous) Interception (synchronous, tool.before only)
02 · EVENT

Event model: three core fields plus open metadata

The core (event type, content and time) is fixed; correlation information goes into open metadata,not hard-coded fields.

Event · dataclassfrozen=True · Immutable after creation
CORE · FIXED
idUnique identifier tsOccurrence time typeEvent type originuser / agent / tool / system / proactive
Content
payload : dictCommand, file path, rate-limited account, etc.
OPEN METADATA · ADD WHEN NEEDED
metadata : dict{"session":…, "turn":…, "lane":…}
Why are turn / session metadata rather than fields?
They are external correlations rather than intrinsic event properties. They are meaningless for half the events, such as auth and channel; dedicated fields would require nullable values. Mature event systems such as DOM, logs, MQ and tracing use a fixed core with correlations in labels or headers.
This layer does not model turns.
There is no Turn object in the framework; a turn is the assistant message id passed through a ContextVar (_current_turn_id). Agent emit sites include it in metadata when available; auth / channel emit sites have no value and therefore no turn metadata.

05 · PLACEMENT

Bus: one process-level singleton

webui, agent loop, channels, memory, auth, task runner Everything runs in the same worker process. Follow the existing get_store() / get_runner() double-checked locking singleton pattern and reuse the unused agent/event_bus.py. No cross-process bridge is needed.

06 · TWO MODES

Observation vs. interception

Observation

Default · Asynchronous

After emit, subscribers receive events asynchronously; the source does not wait.

  • All events use this path
  • Slow subscribersmust not slow the framework

Interception

tool.before only · Synchronous

Before a tool executes, downstream code can refuse execution. Attach to the single tool entry point _execute_tool_calls before its tool.execute() call.

  • Must be fast: no LLM calls
  • When responses differ, use the strictest:Block > Confirm > Allow; Confirm reuses existing _approval
  • Also applies to subagents, independently of permission_mode=bypass; otherwise dangerous actions could bypass the gate through subtasks
07 · PRINCIPLES

Two principles to retain

One

An event requires a consumer that wants to respond

Not every call is an event. The type list isselective: imminent tool execution and credential rate limits are events; an internal list concatenation is not. Emitting every action is a common cause of event-system degradation.

Two

Evolve additively

Sources and consumers do not know each other, soadding an event changes only its emit site: add one line to a framework function, or one emit at a shared entry for a class of actions. Adding types or payload fields is safe;changing existing structures can break existing subscribers. This is why payload and metadata use open dictionaries.

Current wiring is defined by openprogram/events/{registry,bus,bridges}.py and actual emit sites; file:line references in the event table must stay synchronized with those implementations. The proactive rule layer remains a separate deferred design.
