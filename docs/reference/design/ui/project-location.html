Storage, relocation, migration and acceptance (expand)

Adopted choices

Adopt application-owned conversation storage shared by Claude Code, Codex and DeepSeek Harness. Group by project as Claude and DeepSeek do, but use stable project IDs rather than path encodings. Keep existing OpenProgram Git repositories, branches and recovery semantics instead of rewriting to JSONL.

Codex filters against recorded cwd and recent turn context. DeepSeek workspace attachment validates real paths against immutable session header cwd and rejects unavailable or mismatched directories. These paths do not establish automatic tracking of arbitrary folder moves; they also do not imply that moving a folder deletes history.

Further source verification: Codex Project stores id separately from roots; update_project updates roots by id and threads reference project_id. Adopt this separation. DeepSeek Workspace also has an independent ID, but its current path is explicitly immutable; do not adopt that restriction.

Storage and identity

Use the existing profile/state root, default ~/.openprogram. Preserve registered project IDs; generate opaque unique IDs for new projects. Session IDs remain globally unique. Names are display metadata. Location records carry path, revision and a portable folder identity token. Existing default-session placement remains compatible.

~/.openprogram/
  projects/
    projects.json                    # registry / location / identity
    <project-id>/                    # existing project settings
  sessions/
    index.json                       # rebuildable listing
    locations.json                   # legacy compatibility
    projects/
      <project-id>/
        <session-id>/                # complete session Git repository
        .file-recovery/<session-id>/ # external rewind data
    <legacy-session-id>/             # existing default sessions
  memory/                            # existing memory store, unchanged

Portable project identity

A working folder contains .openprogram/project.json with a versioned random identity token. The registry maps this token to the existing project ID. Paths are replaceable location data; conversation repositories remain under the application state directory. Renames, parent-directory moves and copy-then-delete moves preserve the token.

Startup, project-list requests and file/execution access reconcile unavailable locations. Search registered project parents, or their nearest surviving ancestor when a parent moved, up to three directory levels and 4,000 visited entries; exclude the home directory and its ancestors, hidden/dependency directories and directory symlinks. An incomplete search or multiple matching folders does not relocate. Opening a moved folder anywhere checks its token directly and restores the original project when its previous location no longer has that identity. Arbitrary unknown destinations require opening or locating the folder once. There is no background recursive home scan or platform-specific observer.

If the original location still has the token, opening a copy registers a separate project and writes a fresh token in the copy. If the original is gone and only one candidate is found, retain the original project, including for cross-volume copy-then-delete moves. A copy followed by deletion of the original is indistinguishable from a move under this portable model. Multiple candidates retain explicit Locate. A marker is identity metadata, not an authorization credential; file permissions and execution authorization are revalidated at the new path.

Ordinary metadata edits and portable location checks never create or overwrite a marker. New registration and explicit Locate create it atomically, refuse symlinked metadata and malformed files, and do not overwrite a marker owned by another registered project. Legacy records with an exactly matching standard-library device/inode pair can be upgraded once at their recorded path; other unverified legacy records need Locate once. Device/inode values and native bookmarks are not used for ongoing identity after upgrade. Existing history and project IDs are retained.

Adopt independent identity and location from the inspected Codex/OpenCode designs, and explicit Locate from GitHub Desktop. Keep Claude-style application-owned session storage. Reject platform-specific bookmarks/events as a required identity mechanism and reject Git remote equality as proof that two checkouts are the same working folder. The existing platform links below are comparison references only.

Acceptance: public registration plus rename/restart, moving a parent, copy-then-delete, opening a destination outside discovery roots, simultaneous copies, conflicting markers, incomplete discovery, read-only or symlinked metadata, missing folders and explicit legacy Locate. Verify project/session IDs, persisted history and execution refusal at a wrong directory. No native framework or platform event API is invoked.

Execution and references

History reads do not require the working folder. Block new project tasks when it is unavailable, without falling back to HOME, server cwd or session workdir. Do not retarget or replay running subprocesses; validate before subsequent file operations. Check independent worktrees separately.

Do not replace absolute paths inside historical messages or checkpoint manifests. New project file references use project ID plus relative path; unavailable legacy attachment paths remain explicitly unavailable. Audit uploaded attachments, session resources and external recovery storage for migration. Preserve memory text/history; permanent source-conversation deletion removes its clickable link or marks it deleted, without creating an independent source copy. Archived sources stay accessible.

Migration and deletion

Quiesce every session writer before migration, including model tasks, fork children, jobs, checkpoints and attachment writers. A Python lock or singleton worker lock alone is insufficient. Initial migration runs before execution starts; reconnecting legacy sources require the same quiescent boundary, never a hidden move during ordinary reads.

Journal source, destination, identities and a full inventory. Copy into private staging, verify content and unchanged source, durably publish session and external recovery data, then atomically publish authoritative placement before cleaning old storage. Publication failure never authorizes source deletion. Resume after interruption without overwriting conflicting destinations. Serialize deletion with migration and retain durable deletion intent so recovery cannot resurrect deleted sessions. Maintain one authoritative writable location.

Rebuild indexes from both layouts. Never prune a temporarily unavailable migrating session as empty. Project relocation updates only location revision, not conversation placement. Registration removal, archiving, permanent conversation deletion and working-folder deletion remain distinct operations; never cascade into user working files.

Implementation and acceptance

  1. Probe portable identity and bounded location lookup with temporary folders.
  2. Implement home storage, compatible reads, index reconstruction and correct deletion.
  3. Implement quiescent, recoverable migration and failure/restart/delete tests.
  4. Use shared resolution, identity validation, execution refusal and visible states for startup, access failure, user Locate and explicit folder reopening.
  5. Independent specification review, then quality review, affected and full gates, default App refresh and actual interaction checks.

Acceptance covers same history after move/restart, migrated history while offline, no execution in a wrong directory, copies and same-path replacements, archives, failure at every migration stage with intact messages/branches/Git/recovery data, no idle scanning and bounded lookup.

Exact compatibility and operation rules

“Chat files do not move” and offline readability apply to new or migrated conversations. Initial legacy migration physically copies data. Location checks run on startup, project-list requests, access failure, Locate and opening a folder. They do not poll while idle.

Preserve existing path-derived IDs without recomputation. New registrations generate UUIDs after checking validated canonical-path registrations; retry ID collisions, never merge conversations. Existing projects keep their IDs throughout upgrade.

Automatic relocation requires a matching portable token and an unambiguous discovered location. Manual location permits an explicit replacement after showing old and new paths, without requiring platform-specific file identity. Both revalidate location revision, permissions and destination ownership at commit; reject another project's destination. Legacy placement repairs belong in a durable operation journal: show “Updating location”, withhold full success and new execution until all compatibility mappings recover. New-layout relocation updates only project location.

All updated session writers, including CLI, worker, fork children and rewind, share an interprocess lock keyed by session ID under application data. Re-read storage revision and location after acquiring it. Stop accepting tasks and wait for registered writers; defer on timeout instead of killing tasks or copying concurrently. Migration holds exclusive access through copy and publication. Stop pre-upgrade processes through lifecycle management first; mixed-version writes to one profile are unsupported. An empty in-process task list is insufficient.

The project location overrides stale session work_dir. For registered additional directories and source_folders inside the confirmed old project root, derive the new path from the relative suffix, then validate identity and permissions. External additional directories keep absolute paths and independent checks. Unavailable required directories block dependent file operations with a repair affordance. Do not rewrite historical messages, authorization snapshots or rewind manifests. If rewind still targets an unavailable old location, report it rather than creating or overwriting files there. Revalidate permissions at the new location.

Sidebar visibility derives from the current valid session set after filtering archived conversations. Management total counts include archives and show archived counts separately; total session_count is not the sidebar predicate. Refresh the same derived set after archive, restore or deletion. Hiding or removing registration does not delete working files.
