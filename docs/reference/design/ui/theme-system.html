OpenProgram / Web UI

Themes are complete data sets; components read semantic tokens only

This answers three questions: where themes are selected and persisted, which surfaces a setting affects, and how theme additions or edits avoid updating only some components, windows or states.

Audience: Web / Desktop implementersStatus: current specificationScope: colors, fonts and cross-window themes

Design boundaries

CSS custom properties remain the sole runtime mechanism. Do not introduce JS theme objects, CSS-in-JS or a second component skin system. Built-in themes must provide identical token sets; components must not branch on specific theme names such as dark, light .

Included

  • Appearance and Font in Settings
  • First frame, React hydration and system color-scheme changes
  • Main window, desktop overlays and new windows
  • Surfaces, text, borders, states, focus, composer and DAG

Excluded

  • Changing component dimensions, layouts or interaction logic
  • Automatically rewriting saved user CSS overlays
  • Business logic conditional on theme names
  • Forcing application themes onto syntax highlighting or website content

How settings affect components

1 · Select

Settings

Appearance has four layers: Mode, named theme pack, accent color and CSS overlay. Font options come from font-pref.ts.

2 · Persist

Browser preference

Schema 3 writes to agentic_theme_style + agentic_theme_mode; accent and overlay belong to the same preferences family. Fonts also maintain a cookie for the first frame.

3 · Apply

HTML attributes

The first-frame script and hook set data-theme, data-custom-css, accent tokens and --font-sans.

4 · Resolve

Complete token files

Every theme pack defines the same token contract; accent overrides only three accent tokens; CSS overlays apply on top of the current pack.

5 · Consume

All components

The Tailwind bridge, CSS modules and desktop overlays all read tokens without checking specific theme names.

Diagnosing intermittent theme switches

Desktop startup and system color-scheme updates prefer the complete valid theme-prefs.json preferences saved by the main UI. Legacy browser-storage migration is used only when the file is missing or its mode/style is invalid. Raw browser-database byte scans cannot identify the latest record, must not override valid desktop preferences and must not restore cleared accent colors. After loading, the web page uses its own localStorage as authority and synchronizes the desktop cache.

The desktop main page records successful message-send times, first-screen initialization, settings changes, system color events, cross-window preference synchronization and HTML theme-attribute changes. Records contain only timestamps, fixed event names, theme enums and system light/dark state, excluding chat content, page URLs, CSS and user paths. Under desktop userData, theme-events.json retains at most 64 records; write failures do not affect theme rendering. The log identifies the source of intermittent switches and does not establish that unknown triggers are fixed.

Acceptance criteria

  • Theme listSettings displays only Beige / Neutral / Aurora; check scripts establish agreement between CSS imports, theme files and allowed desktop overlay values.
  • Complete tokensSix built-in themes (three packs × light/dark) provide the same token set;custom-light.css is only a legacy-snippet fallback with values matching beige-light.
  • Accent colorAn independent picker overrides --accent-orange / --accent-fill / --accent-orange-hover; an empty value uses the current pack default. Desktop error-page and directory-listing link colors follow the override, while the window background remains the pack's --bg-primary.
  • CSS overlayUser CSS overlays the current pack, gated by the Enable switch; legacy [data-theme=custom] selectors are rewritten to data-custom-css.
  • Component isolationOutside theme files, no component CSS branches on specific built-in theme names.
  • Cross-window consistencyAll six theme-pack ids pass unchanged to desktop overlays; desktop window backgrounds use that theme's --bg-primary.
  • Font consistencyOrdinary text and native form controls inherit the same --font-sans, with explicit exceptions for mono regions.
  • Primary-color matrixNeutral light/dark themes use blue, Beige uses orange, and Aurora uses teal; pack-default accents continue to come from CSS files.
  • Active desktop tabIn dark mode, the tab bar's --tab-active-bg blends the content background with 12% white, shared by ordinary tabs and split groups. The selected background remains stable on hover; light mode and browser tabs retain the content background.
  • Visible acceptanceInspect the main window, tabs, composer, popovers and desktop overlays in dark, light and aurora using the default installed App.

Implementation status

The current implementation uses Obsidian-style Appearance: Mode × named theme pack × accent color × CSS overlay.

Schema 3's THEME_STYLE_PAIRS remains the light/dark matrix of Beige / Neutral / Aurora. Custom is no longer a fourth style card; existing custom / custom-light migrates to beige, saved CSS enables the overlay, and old selectors are rewritten to data-custom-css. Accent color persists independently and overrides only three accent tokens. Composer, provider icons and DAG consume role tokens only. Desktop BrowserWindow backgrounds still use the pack's --bg-primary; error-page and directory-listing links use the accent override when present. Theme-contract checks are included in the complete Web checks.

Windows tests use Node.js fileURLToPath to convert module URLs into local paths, avoiding an extra slash before drive paths; theme behavior and assertions remain unchanged.
