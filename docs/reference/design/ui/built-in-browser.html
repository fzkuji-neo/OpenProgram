Browser actions follow task execution

Clicks, scrolling, keyboard input, navigation, and closing a page never pause an Agent. This applies equally to user input and automation, including automation of OpenProgram itself. Only the conversation execution controls pause or cancel the task. Browser resources do not maintain a separate write prohibition.

The existing page input notification path incorrectly requests execution pauses. A retained page prohibition can outlive the execution that created it. Remove that path and the separate prohibition checks while retaining execution dispatch guards, ownership checks, and current-frame validation.

When a target disappears, discard its session and return actionable recovery information with its last URL. Recover by observing a newly opened exact URL, never by replaying a mutating action or selecting an unrelated tab. The Agent continues the task using a fresh observation. Missing authentication or unsaved state is reported rather than invented.

Browser screenshots preserve ToolReturn images and structured errors. Executor shutdown must not leave a live server submitting work into a closed default executor. Recovery must respect task cancellation and unresolved external effects.

Acceptance and implementation status

Implemented and independently reviewed: page events leave execution running; explicit conversation pause still stops dispatch; old page prohibition cannot block a new execution; closed targets provide usable recovery; screenshots retain images; shutdown errors are handled at their owning lifecycle boundary. Verify affected desktop and Python components, contracts, documentation links, and installed App. Independent specification and quality reviews precede completion.

01

Product decisions

Content entry points, browser home, and data management currently share one page. The design separates their responsibilities before defining the controls on each page.

New pane only selects content

An empty pane only shows Files, New chat, Browser, and Terminal. The address bar, quick sites, Bookmarks, and History do not appear here.

Four entries use equal visual priority and distinct colors

Files, New chat, Browser, and Terminal all use equally sized rounded icon containers and Lucide outline icons. Files uses blue, New chat green, Browser orange and purple, and Terminal purple. Color only identifies content types; it does not change card hierarchy, interaction states, or accessible names, and introduces no brand logos, external assets, or extra animation.

Browser home reuses complete browser chrome

Selecting Browser opens browser home in place. Home and actual pages share the address bar and bookmarks bar structure. Back, Forward, Reload, Home, Bookmark, and external opening remain visible but disabled when no current page applies; address input, Bookmarks, Import, and Browser ⋯ remain available.

The page determines navigation versus popup

Ordinary links, form submissions, script assignments, and same-document navigation continue to commit in the current WebContentsView and only update that WebTab's URL, title, and History; they must not create a tab. Only when the page explicitly requests a new browsing context (target="_blank" or window.open) does the main process convert a validated HTTP(S) URL into a WebTab with its own id. The new WebTab immediately becomes active; when already at /chat or /s/<id> , do not push /chatagain, so session-route synchronization cannot overwrite popup activation.

Web context menus bind to the hit content

The native page area directly uses Electron context-menu hit parameters. HTTP(S) links show Open Link in New Tab and Copy Link Address; editable content shows Undo, Redo, Cut, Copy, Paste, and Select All; ordinary pages show Back, Forward, and Reload. Open Link in New Tab reuses the popup entry point and therefore has the same semantics as the page's own window.open for URL validation, unique tabs, and immediate activation. Menu actions only affect the WebTab that produced the menu and is still owned by the same window.

Floating web previews belong to the initiating session

A floating web preview opened by an agent in chat records its session tab at creation. It appears only while that session is the current center content. Switching to another chat, a regular Browser tab, or a non-chat page must remove the WebTab from the renderer's native visible set and restore the user's web zoom. Returning to the original session reuses the same WebTab, URL, scroll position, and form state without reloading. After the user closes the preview, its restore entry also appears only in that session.

Saving and managing bookmarks are separate

The star at the right of the address bar only saves or removes the current page; the adjacent Bookmarks button opens the complete bookmarks page. Browser home shows only user-maintained quick sites, not all bookmarks.

Bookmarks manager uses a Chrome-style two-column layout

The complete bookmarks page has a fixed page title, search field, and page menu at the top. The left column contains only a collapsible folder tree with the current directory highlighted; the right column contains only that directory's direct children. Bookmark rows have a favicon, title, and single ⋮ menu; folder rows open the corresponding directory. The entire tree, URLs, and edit/delete buttons no longer share one list. Rows in both lists use 36px; the search field uses the global 30px control height, inline icon buttons use 28px, and the header uses 52px. The right list's initial viewport padding is 16px. In a narrow pane, the directory tree moves above the content list rather than disappearing.

The bookmarks bar is visible by default

Browser home and actual pages show the same bookmarks row below the address bar by default. Users can disable it through Browser ⋯ or Settings. Narrow split panes temporarily hide the row, while all content remains accessible through Bookmarks in Browser ⋯ .

The bookmarks bar displays source-directory contents

Chromium's Bookmarks bar is the bookmarks-bar container, not an ordinary folder button. Its direct children enter the bar in original order;Other bookmarks and Mobile bookmarks appear as right-side folder entries only when nonempty. Ordinary root bookmarks remain bar items. Items placed in overflow must not leave partially clipped buttons in the visible bar; the last visible button must retain its full background and both rounded ends.

Bookmark menus retain Chrome-style hierarchy

The single-row bookmarks bar has no horizontal scrollbar; items that exceed its width appear in the right-side overflow menu. Menus have a fixed width of 280px and ellipsize long titles. Folder rows show a Folder icon in the existing 14px icon slot and a right arrow to enter the next menu, rather than concatenating full paths. Site rows show bookmark favicons; when imported data lacks a favicon, fetch it from the URL and show a Bookmark icon on failure, never an empty slot. In the desktop App, hovering over a bookmarks-bar folder opens it immediately, and moving horizontally to an adjacent folder switches menus without extra delay. Consecutive folder switches reuse one menu view and replace only its data, without rebuilding the view or decoding previously displayed favicons again. The native overlay starts at the bookmarks bar's lower edge and must not cover the buttons' pointer hit areas. Each menu level is constrained by the current window height and supports mouse, trackpad, and keyboard interaction.

Settings have one source of truth

Settings in the window menu opens OpenProgram settings; Browser's ⋯ opens its Browser section directly. The toolbar adds no persistent gear button and no second browser-settings store.

Split layout belongs to panes

Splitting, leaving split view, and pane arrangement apply to Files, Chat, Browser, and Terminal; they are not current-page actions. They belong in Tab/Pane controls or the tab context menu, not the browser toolbar.

Import preserves source structure

Chromium's bookmark bar, other bookmarks, and nested folders retain their hierarchy and order in the OpenProgram bookmark tree. Import must not flatten bookmarks into separate entries below home.

Each menu binds to its own trigger

Browser ⋯ and the window ⋯ use their respective trigger buttons' actual screen rectangles. The menu's right edge aligns with the button's right edge, with a 4px vertical gap; the two menus cannot share placement or content.

History uses compact rows

Records are grouped by local date. Each row shows only time, favicon, title, domain, and actions; the full URL no longer occupies a second line.

Import requires an explicit action

The source browser, profile, and data types are confirmed separately. OpenProgram does not read or modify the source profile actively used by the user.

Reference behavior and tradeoffs

Reference products establish visible behavior; platform documentation establishes implementation boundaries. OpenProgram does not duplicate the complete Chromium importer.

Content hierarchy

Codex pane entry points

Files, New chat, Browser, and Terminal are top-level content types; browser controls appear only inside Browser.

Adopted
Browser profile

Independent browsing state

The built-in browser maintains its own profile. Users explicitly initiate import when existing data is needed.

Adopted with changes
Bookmark access

Chrome's layered entry points

The star saves the current page, the bookmarks bar can be toggled, and the complete manager is separate. OpenProgram retains these three levels with stricter collapse rules for split panes.

Adopted with changes
Settings ownership

OpenAI App Settings

The built-in browser maintains independent state; Cookies and history clearing belong to desktop App Settings. OpenProgram adds a Browser ⋯ deep link without duplicating settings storage.

Adopted with changes
Page intent

Chrome distinguishes navigation from popups

Navigation in the current browsing context commits in place; explicit requests for a new context create and activate a new tab. OpenProgram preserves this distinction while converting native popups into WebTabs managed by center-tab state.

Adopted with changes
Page menu

Electron native context menu

webContents provides link, selection, edit-state, and frame hit parameters;Menu.popup provides the current OS's native menu. OpenProgram adopts a limited action set without exposing DevTools or arbitrary protocol opening.

Adopted with changes
Importer

Chromium C++ importer

components are not exposed as Electron JavaScript APIs and provide no general Cookies import implementation.

Not duplicated
  • OpenAI built-in browser documentation: establishes independent browsing state, external-browser boundaries, and clearing Cookies and History through desktop App Settings.
  • Chrome bookmarks documentation: establishes saving the current page beside the address bar, toggling the bookmarks bar, and a separate complete Bookmark manager.
  • Chrome import settings: establishes data-type selection and Imported Bookmarks merging behavior.
  • Chromium user data directory: establishes profile storage locations for History, Bookmarks, and Cookies.
  • Chromium user_data_importer: establishes native importer capabilities and Electron exposure boundaries.
  • Electron session and Cookies: establish persistent partitions and per-cookie write APIs.
  • Electron webContents and renderer window.open: establish that setWindowOpenHandler receives resolved popup URLs, andcontext-menu provides link, selection, and edit hit parameters.
  • Electron Menu: establish that Menu.buildFromTemplate and BaseWindow bound to their owning menu.popup are native context-menu entry points in the main process.

Import architecture and data flow

The renderer passes only opaque source/profile ids issued by the main process. It cannot freely specify file paths, source-browser executable paths, or Cookie values.

Ordinary data pathSensitive Cookie path

History

  • Read a copy of Chromium History SQLite
  • Accept only http/https
  • Deduplicate by URL + visitedAt
  • Preserve existing records on error

Bookmarks

  • Parse Chromium Bookmarks JSON
  • Preserve roots, nested folders, and sibling order
  • Avoid duplicate URLs and remove empty folders
  • Display and manage only on the Bookmarks page

Cookies

  • Direct Cookie database copying is prohibited
  • Decrypt in a temporary source-browser process
  • Validate each item before writing to the partition
  • Never log values
