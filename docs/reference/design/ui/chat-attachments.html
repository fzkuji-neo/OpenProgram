Chat attachments: bidirectional delivery and previews

How incoming user files and outgoing agent files appear in chat, and whether they can be opened. Four sections: current behavior, eight implementations, remaining work, and the target design. How attachments enter model context is a separate subject covered in Complete attachment handling design. This page references its conclusions where needed. 01 Our current implementation Current behavior

Attachment bytes, markers in message text, model input, and user-visible content are separate concerns. All four inbound paths follow the same rules: persist bytes once, leave a marker using the shared grammar, provide images or paths as appropriate to the model, and render chips with one parser.

1.1 Four inbound paths, one marker grammar

Diagram details: Same persistence path, deduplication, and limits as documents. Plus a 4KB opening preview. Slack (WeChat has no attachments). Can be opened on the web. [display name (id)]. is prepended to the text; attachment markers are appended. They never overlap. _one_line removes square brackets, preventing forged additional prefixes.

All four inbound paths provide content to the model and leave the same clickable representation in chat. Markers are generated exclusively by attachments.format_marker ; chips are parsed exclusively by parseAttachments . A fifth inbound path must call this formatter instead of defining another grammar. Web images previously existed only as base64 in memory: the model could see them, but users could not reopen them. They now share document persistence (sha256 deduplication, 32MB/64MB limits, path insertion) while remaining ImageContent in model input. openprogram/attachments.py · openprogram/channels/_attachments.py:181 · apps/server/openprogram_server/_webui/ws_actions/chat.py · apps/web/components/chat/messages/user-attachments.tsx

1.2 One message, three sources, one result

Diagram details: Only the speaker prefix and message remain; the marker is hidden.

Three sources, one component.parseAttachments extracts markers from text; AttachmentChips renders chips; AttachmentPreview opens them using FileViewer the absolute-path mode. User messages, assistant messages, and the message rail share this implementation. apps/web/components/chat/messages/user-attachments.tsx · attachment-preview.tsx · apps/web/components/files/file-viewer.tsx · apps/web/lib/net/chat-stream.ts

1.3 Outbound: one tool, two delivery paths

Diagram details: Extract marker → post_file → omit marker from delivered text. Failure / unsupported → rewrite as a readable explanation.

Why use a tool instead of a MEDIA: instruction line in message text? A textual convention can leak to the user when extraction fails; channel inbound handling already exposed that failure mode. A tool call validates file existence and can report “the file no longer exists.” Merely mentioning a path is not interpreted as a delivery request. openprogram/programs/tools/interaction/send_file.py · openprogram/agent/dispatcher/__init__.py · openprogram/channels/_conversation.py:_deliver_outbound_files

1.4 Byte-serving endpoints: two routes with separate contracts

Do not expand /files/raw. Its “always reject absolute paths” invariant should remain. Each route retains its own contract. The viewer implementation remains shared: FileViewer adds an abs argument to switch the two endpoints to absolute-path routes. Image, PDF, Markdown, line-numbered code, and download-card rendering still have one implementation. openprogram/attachments.py:readable_roots · apps/server/openprogram_server/_webui/routes/files/file_search.py · apps/server/openprogram_server/server.py · apps/web/components/files/file-viewer.tsx

Output as a page

Implemented independently by three projects

Openclaw materializes documents as /__openclaw__/canvas/documents/<id>/index.html, rendered inline in chat through [embed ref="cv_123"] ; its system prompt prohibits local paths in embeds. Codex asks the assistant to emit an ::codex-inline-vis{ instruction line; the TUI materializes the HTML fragment in a sandboxed viewer and replaces the line with a browser link, with a 2MB limit and strict CSP. Pi-mono’s /share exports the complete session as self-contained HTML, publishes a private gist, and returns a hosted viewer URL.

Short-lived signed tokens

Openclaw’s /__openclaw__/assistant-media?source=…&mediaTicket=… uses token format v1.<payload>.<signature>, with a five-minute TTL. This addresses browser access to bytes without granting arbitrary-path access, imposing stricter controls than allowed-root checks alone.

Chips as editing units

Removing the placeholder cancels delivery

Claude-code treats [Image #N] as an indivisible unit for cursor and vim operations. An image is sent only while its placeholder remains in the text. Deleting the chip cancels the attachment without a separate remove button.

Cursor.ts:322vim/operators.ts:469
Other techniques: Hermes rewrites host cache paths to container paths so a sandboxed agent can open the same file. Its native mode inlines pixels and also includes a path hint, giving the model both. Codex has a view_image tool for loading local images into context. Pi-ai removes image blocks entirely when the model lacks declared image-input support—the fallback gap recorded in attachment-handling. Cleanup intervals differ: Openclaw two minutes, Hermes 24 hours, Claude-code removes other sessions’ caches at every session start.
An earlier description has been corrected: attachment-handling previously described Opencode as synthesizing a fake read tool call and result on submission. The actual code injects two plain-text parts marked synthetic, containing “Called the Read tool with the following input …” and the actual read result. The model receives role: "user" text, not tool_use and tool_result blocks. The three reasons for rejecting that approach remain; only the description was wrong. Both documents are corrected.

04 Target design Desired behavior

The requirement: any file, regardless of source channel, producer, or format, opens through the same viewer in every interface. Agent-produced and user-uploaded files differ only in their source field. The diagram is not constrained by the current implementation. Dashed elements are unavailable or too costly; reasons follow.

Diagram details: Anything openable on the web can be received on Telegram. It would violate the invariant that each session workdir is committed to git every turn and remains replayable. The cost is retaining large binaries permanently in git history, an acknowledged and accepted cost.

Relationship between sections three and four: after section three, the solid-line behavior in the diagram exists, represented by a text marker instead of a record. Section four replaces that marker with an ID without changing the remaining interfaces.
