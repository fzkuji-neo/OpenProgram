Integrated terminal and Claude Code launch

Center tabs provide a real local terminal and can launch the locally installed Claude Code CLI directly from a new tab. Web mode does not expose host command execution or describe a local CLI as a remote cloud session.

Verified gaps

Ordinary pipes are not PTYs

The old draft used child_process.spawn, TERM=dumb and pipes. Interactive programs lacked a terminal device, so Claude Code cursor handling, fullscreen refresh, colors and shortcuts did not work correctly.

Input/output controls lack terminal semantics

<pre> and a single-line <input> do not interpret ANSI, cursor movement, alternate screens, paste or Ctrl+C.

Entry points do not match capabilities

The old entry showed only Terminal and submitted commands line by line, with no direct Claude Code launch entry.

The terminal view is not integrated with the theme contract

Terminal background, foreground, cursor and selection colors were hardcoded to a single dark palette, with no explicit ANSI 16-color palette. Light, warm and custom themes therefore differed from the rest of the App.

Missing process operations and state

The original view accepted input but provided no toolbar actions for copying selection, pasting, clearing, restarting or stopping; it did not distinguish starting, running, exited and error states.

Terminal

Claude Code

Shell directory and foreground command lifecycle

The existing desktop PTY resource reports the latest shell directory and foreground command cycle for ordinary macOS zsh and compatible bash 3.2 login shells. These reports are advisory: a command returning zero proves neither external effects nor Agent task success. Background jobs can continue after the foreground cycle finishes. Input delivery still returns phase=delivered or an unconfirmed operation with command_complete=null. Reports never change ownership, leases, approval, input revisions or cancellation.

Metadata and transport

shell_integration?: {
  status: "starting" | "ready" | "unavailable" | "ended",
  mode: "zsh-hooks" | "bash-debug" | null,
  reason: string | null, event_sequence: number,
  cwd: { value: string, event_sequence: number } | null,
  cycle: { id: number, phase: "running" | "finished" | "unknown",
           exit_code: number | null } | null
}

Existing resource reads and events carry this optional field; older hosts may omit it. start_cwd stays immutable and the top-level exit_code belongs to the PTY process. The nested exit_code belongs only to a matched shell cycle. Initial prompts report ready/cwd with cycle=null. Process exit makes an unfinished cycle unknown and ends integration. Last cwd/cycle values remain historical observations, not guarantees about a running child. The Web type accepts metadata without adding a renderer, prompt parser, command API or new store.

Startup and compatibility

zsh retains native -l. Private .zshenv/.zprofile/.zshrc/.zlogin forwarders restore the user's ZDOTDIR value and unset state before sourcing each corresponding user file, capture redirection, and restore the final user directory before appending preexec/precmd hooks. RCS remains authoritative: disabled phases do not re-enable it or install hooks. Existing hook functions remain in place. Readonly callback arrays decline installation. Arbitrary global startup scripts or plugin configurations are not claimed equivalent.

bash retains native -l and receives a one-time PROMPT_COMMAND only if the launch environment did not already define one. The top-level bootstrap captures DEBUG before sourcing. A retained, writable bootstrap installs the minimal DEBUG/prompt pair. Existing custom DEBUG, readonly PROMPT_COMMAND, extdebug, functrace, replaced prompt commands and bash-preexec configurations do not receive integration. Incompatible and unsupported shells remain usable and report unavailable; existing hooks are not overwritten. bash-preexec callback registration remains outside this implementation. Root-parent PID checks prevent nested bootstrap adoption; installed callbacks reject nonroot/subshell reports. No user configuration, shell options or history policy is rewritten.

Protocol and lifetime

Frames use ESC ] 777 ; OpenProgram ; 1 ; nonce ; rootPid ; eventSequence ; kind ; cycleId ; exitStatus ; cwdHex BEL. Kinds are ready, cwd, start and end. Each launch has a random 128-bit nonce; parser checks actual PTY PID, strictly increasing positive safe event sequences, increasing cycle identity and matching completion. UTF-8 absolute cwd is hex encoded using printf/od/tr, limited to16KiB, with no NUL or malformed UTF-8. Frames are limited to36KiB. The incremental parser handles chunk boundaries and releases incomplete candidates after one second. Only valid accepted frames are removed before both live delivery and replay storage; invalid or unrelated output remains unchanged. Output cursors count the same filtered stream.

The shell can read or forge its own nonce, so metadata grants no authority. It contains no command text or environment dump. After three seconds without ready, status becomes unavailable; a later valid first handshake can recover. Missing hooks are not inferred from quiet output; the last report can be stale. Root exit makes a running cycle unknown, never finished.

The existing launch path reads individually packaged scripts through Electron fs and extracts them to a per-launch0700 directory with0600 files, allowing source outside app.asar. Spawn failure or confirmed root exit removes these assets; view reattachment, lease release and hidden panes do not. Old-generation data cannot update replacements. Unsupported preset/platform or asset preparation failure retains the raw terminal. No new settings, terminal engine, CLI or Windows integration is added.
