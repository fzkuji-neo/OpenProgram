OpenProgram / Conversation frontend / Target design

Read and interact while state recovers

Audience: frontend and runtime maintainers. Scope: initial open, navigation, long history, streaming, tools, approval waits, draft and send recovery, offline states, background work, and accessible interaction. Implementation is in progress; the complete scenario matrix remains the release contract.

Observed behavior

0.18–0.20 secondsDirect initial history request.
16 recoveriesProcessed before the first history request; five history loads in one refresh.

The frontend reconnect path sends every persisted execution cursor before the selected conversation. The server processes commands serially per connection. Replay snapshots enter the live execution update path, which requests another transcript for terminal executions. Cursor storage retains completed executions and performs synchronous persistence on every cursor frame. Some persisted execution streams contain more than 200 MB of event payloads. The current Web replay handler only consumes the resulting execution snapshot. Recovery reads therefore request snapshot-only mode: the execution record and event cursor are read in one SQLite transaction without reading event bodies. Explicit event-history clients keep their existing behavior.

State ownership and data flow

TranscriptOne request owner per session and view generation. Persisted messages, pagination, search targets and scroll anchors.
ExecutionMonotonic cursors and status versions, active task and approval identity. Snapshot recovery does not simulate a new terminal event.
ComposerSession-owned draft, attachments, queued entries and acknowledgement. Navigation or disconnect never clears unacknowledged input.

Connection generation owns timers, pending read requests and fragment buffers. Obsolete responses cannot mutate a new connection or the visible session. Storage failures degrade persistence, not event delivery. The server remains authoritative for authorization, execution, cancellation and approvals. No client optimization bypasses those boundaries.

Implementation sequence

  1. Centralize reconnect and execution recovery, distinguish recovered snapshots from live transitions, and make cursor persistence resilient. Use atomic snapshot-only reads for ordinary UI recovery; preserve full event replay for explicit inspection.
  2. Centralize history request ownership, navigation generations, stale-cursor recovery and loading/error/retry presentation.
  3. Validate and optimize long-history rendering, streaming batching, tool output expansion, scroll follow and jump behavior.
  4. Complete interaction coverage for drafts, queue/ACK/retry/cancel/steer, approvals, background tasks and accessibility.
  5. Run combined verification, update the default App once, and measure the full scenario matrix.

Each stage receives independent specification and quality review. Passing one stage does not establish completion of the whole frontend. No new execution runtime, remote service, account integration or historical data deletion is part of this design.

Implementation evidence

Status: in progress. Recovery sequencing and cursor persistence pass independent specification and quality reviews, 938 Web tests, 526 repository contracts, Web structural checks, typecheck and build. Snapshot-only recovery also passes independent specification and quality review, 344 affected Python tests, the full Web suite, repository contracts, typecheck, build and link checks. Its public WebSocket regression forbids reading the historical event payload column; the store regression interleaves a writer to verify record/cursor consistency. Native App latency remains unverified. Navigation, render and interaction matrix acceptance remain pending. Release requires complete Web tests, typecheck, structural checks, build, repository contracts, documentation links, affected browser checks and final native App acceptance. No performance improvement is claimed before refreshed-App measurements.
