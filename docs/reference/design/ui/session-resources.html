Session resources

Engineering design for the collapsible right-side Session resources panel. It lists complete software and environment objects used by the session. Activity owns code executions, commands, scripts, background processes and output; files remain in file views. Status: implementation reviewed; installation acceptance verifies the default App. Canonical Resources, preview, Open page and PiP interaction lives in GUI Agent Resources and operation preview.

Interaction

A Session resources navigation button sits in the right sidebar beside Files and Activity. It uses their shared row, icon and label classes, left-aligned label, 20px animated icon, and matching hover/focus behavior. Files, Activity and Resources remain the existing vertical navigation. It opens a searchable panel in the existing resizable right dock. The dock toggle collapses the panel to its icon rail. Only resources whose recorded owner matches the selected session appear, grouped by conversation branch. Child-agent resources appear under the originating parent branch with their actual owner identified. Switching sessions resets search and details and aborts previous requests. An owned webpage retains its recorded session context; drafts and unassigned views show no session resources. Legacy records without provable branch ownership belong in Unassigned. A resource row click selects a read-only chat preview; it does not activate or recreate the Page, change the user's tab layout, or steal tab focus. Explicit Open page shows the same existing Page as a regular top-level tab and hides that preview; returning to the conversation restores the preview unless the user hid it. Repeated opening reuses that Page without duplicates. Hidden agent-opened pages stay retained in Resources and do not add top tabs until that explicit action. Resources has no Pin control. Other resources show their details while keeping the resource panel available. Collapsing the dock or selecting another dock view stops resource polling. The selected dock view persists across reloads.

Conversation preview and Page access

A preview stores the conversation ID independently of the reusable chat tab ID. Navigating within a chat tab or through its history displays only the selected conversation's preview. A conversation without a selected Page displays no preview; returning restores its own selection. Hiding a preview does not release or reveal the Page.

A retained agent Page that has not been opened as a top-level tab is private to its recorded conversation. Page inventory, turn context, screenshot, resolve, activation and close enforce that ownership using trusted execution session attribution, independently of the selected UI tab. Explicit Open page exposes the existing Page as a regular tab: other conversations may discover it and acquire it only when the existing exclusive Page lease permits acquisition. Exposing a Page changes discoverability, not its original provenance or preview ownership. Closing the tab removes its previews. An asynchronous result must still match the current access scope before delivery.

This extends the existing renderer-owned tab provenance and server-owned Page lease; it introduces no alternative browser registry. Existing GUI Agent preview and built-in-browser references remain authoritative. Unified resource interface

Resources identifies persistent environments. A Terminal resource is the existing PTY and shell, not a command transcript. Web, Terminal and installed applications share discovery, identity, session attribution, capability descriptions and view selection. Their existing providers retain execution authority and type-specific operation schemas.

Structured observations retain images, output cursors and typed results. Existing web_use and terminal_use remain compatible public entries. A resource identifier is not an access grant.

Trust and failures

The worker derives the session, execution and originating window from trusted context. Providers retain ordinary tool approval, sandbox checks, private-resource checks, exclusive bindings, generation checks and input revisions. Application manifests cannot provide arbitrary host code through a renderer request. Third-party resources use installed and explicitly trusted application packages. Desktop availability is reported without substituting another host. Uncertain writes are never replayed automatically. Hiding a view, releasing Agent access and terminating an environment are separate operations.

Shared interaction

The right sidebar presents one session-filtered list with common grouping, status and selection. Terminal rows participate in the same list rather than an appended independent section. Selecting a Terminal attaches an interactive view to its existing PTY; it must not create a new shell. Switching sessions clears the selected view. Web retains its native Page preview and explicit top-tab action. Terminal input remains available while the conversation is visible. Close controls identify the environment they terminate. Output is untrusted content and input acknowledgement does not mean command completion.

Framework comparison

The existing Page registry provides native target ownership and observation freshness; it is retained. The shared Terminal manager provides generation, binding, output cursors and native receipt correlation; it is retained. The Applications runtime provides installed manifests, instances and declared operations; it is reused for user software. The existing resource_use context manager supplies display-only lifetime reporting; it cannot provide control by itself. A second browser registry, a universal shell-command fallback and an unrestricted renderer plugin loader are rejected because they duplicate authority or bypass provider constraints.

Backend operation parity and installable providers

Every product operation has an authenticated backend entry. HTTP operations are described from the registered API schema; existing WebSocket business commands are also callable through a request/response backend adapter using the same handlers. The Agent discovers a named operation and invokes it with structured arguments. It never needs to inspect or click the OpenProgram interface to perform a framework operation.

Authority and boundaries

The framework tool requires the existing owner authority and tool approval, refuses an active sandbox or a nonlocal backend, and never returns owner credentials. Internal authentication, native receipt and connection-registration endpoints are transport internals, not callable product operations. Renderer preferences, navigation and native window functions have explicit backend commands addressed to an exact connected window. Replies are correlated to that connection; disconnects and uncertain mutation results do not trigger retries. Browser and Terminal resource operations preserve their original provider checks. Application operations retain explicit Agent exposure and installed-package trust.

Automatic application integration

An enabled installed application automatically provides application.<id> in the resource catalogue, without process restart or a hand-written registry edit. Its manifest describes operations and input/output schemas; open binds its durable instance to the current session, observe reads state and runs, act submits a declared Agent-visible operation, release removes only the session association. Cancellation and question answers operate on the exact instance and run. The same instance opens in an isolated application view from Resources. Disabled, removed or updated applications revoke stale descriptors. A scaffold command creates a runnable package whose interface and Agent use the same backend operations.

File organization

Resource contracts and dispatch live in openprogram/resources, adapters in its providers package. Framework discovery, authority and client calls live in openprogram/framework. Server routes remain under the Server application, grouped by control responsibilities. Interface command handlers live under apps/web/lib/framework and resource views stay under components/session-resources. Compatibility imports preserve existing integrations. New modules have a single responsibility; no unrelated repository-wide file moves are included.
