Resources and operation preview

How the right-sidebar Resources list, the chat preview and human takeover of Agent-operated Pages behave.

Chinese edition

Related: Session resources, Browser control surfaces, Agent control overlay.

Resources and a unified operation preview

Resources groups retained targets by resource type. Resources has no search field. A row click shows a interactive chat preview and keeps that existing select behavior. An explicit Preview in conversation icon button does the same for the exact existing Page, without adding a top tab, restores a hidden PiP, and returns to the owning session when a webpage currently occupies center so the chat preview is visible. Hide keeps the Page. There is no standalone Show preview control. Explicit Open page reveals that same Page as a regular top-level tab and hides that preview together with any reserved space; returning to the conversation restores the preview unless the user hid it. TARGET (not current runtime): a webpage tab and its small chat preview may display at the same time and stay in sync on the same Page; hiding the preview does not close the Page or the main view. Runtime is unchanged. Desktop PiP presents the existing native Page with direct input and live rendering, including while dragged. Its bounds and layout zoom follow the preview size. A never-shown Page starts with a 1920×1080 CSS-pixel viewport. Plain-browser previews use a separate sandboxed iframe with browser embedding restrictions. Browser interaction is the first implementation scope. Native application and VM adapters, trace review and learning require separate implementation discussions. Verification and remaining work are recorded in the implementation-status appendix.

Resources in the current conversation's right sidebar lists all associated targets by resource type. Agent-opened pages remain in the background without adding top tabs. One chat preview follows the target most recently operated on by the viewed branch. Browser Pages, native application windows, the host desktop and VM displays share selection rules while retaining distinct input capabilities.

A function result that names the window it acted on as target (window_id, pid, app_name) moves the preview to that app. The worker keeps only the latest window and its last screenshot per conversation, in memory, announces it as a native.window event and serves the frame from /api/session/{id}/native-window/frame; a GUI step inside an agentic subprocess forwards the window to the worker, which attributes it to the conversation that owns the subprocess. The preview shows what the Agent last saw, not a live view. A terminal the conversation is using moves the preview when it starts running or receives new input, and the preview mirrors its screen read-only. Pinning keeps only Pages; app and terminal targets follow and are not stored as a pin.

The preview header identifies Auto preview or Fixed preview beside the current control status. The More menu checkbox Automatically show the page the Agent is using selects Auto preview; disabling it keeps the current Page as Fixed preview. A different preview title does not retarget the Agent, resume or start the Agent, or change Page lifetime or top-tab placement. This display option exists only in the preview menu; Resources keeps its existing action buttons. Default-App acceptance is a separate release check.

Interactive appearance

The current interactive resource grouping and preview controls are maintained in Resource panel and preview interaction. It uses type groups, unchanged sidebar actions, and Open page, More and Close preview icons.

Resource and preview responsibilities

  • Retained browser descriptors and branch associations provide the resource inventory. Temporary usage records describe execution use and do not determine Page lifetime. The same Page can have references in more than one branch.
  • A resource row click selects a interactive chat preview and keeps the current tab. Explicit Preview in conversation uses the exact existing Page and does not pin or duplicate a top tab. If a webpage occupies center, that action activates the owning current session so the requested preview is visible, without changing the viewed branch. Explicit Open page uses the exact existing Page as an ordinary top view and hides that preview together with any reserved space. Changing automatic display in More does not steal tab focus. Returning to the conversation restores the preview unless the user hid it.
  • Resource lifetime, preview preferences and execution input leases have separate state. A window-level projection keeps following and control status current when the Resources panel is closed. Hiding the preview releases its visible bounds and retains its target.

List and preview appearance

Keep the existing vertical Files, Activity and Resources navigation at the top of the right sidebar; do not replace it with horizontal tabs. The Resources redesign changes only its content. Use the existing sidebar's dark surfaces, system font and 16px type icons, with no bordered card per resource. Each group heading reuses the left sidebar Pinned and Projects SectionHeader: 14px normal secondary text, a 16px chevron immediately after the resource type title, the same padding and hover, and the resource count as trailing actions. Enter or Space expands or collapses that group only. Compact rows are approximately 44-48px tall: title first, then type, state and child-agent name when needed. Long titles truncate; details expose full titles, sanitized origins and target identity. Hover and selection use subtle surface changes. An operating indicator and preview selection are distinct, with text rather than color alone explaining state. Webpage rows expose three compact Lucide icon buttons beside the title: Preview in conversation, Open in tab, and Close webpage. They share the existing compact toolbar pattern (24px hit target, 14px glyph, same hover, disabled, and keyboard-focus treatment as PiP chrome). Do not use a literal arrow glyph or the global 36px Button for these controls.

The chat preview identifies its title. Chrome is one compact row that must not wrap, including at the 240px minimum width, the 300×198.75 default (300×168.75 image plus a single header), and the 720px expanded width: an ellipsized title, a compact control-status indicator, Open page, More, and Close preview (X). Title truncates before buttons. Show actions and Operation history belong in the existing native-safe More menu. Primary actions stay on the row; do not move them into a second row or a popover toolbar. The screenshot fills the remaining box with native layout zoom and keeps the captured aspect ratio; do not crop or zoom page content to enlarge the thumbnail, and do not accept clicks on the image. Idle and closed show Ready to use and have no Pause or Continue control. Failure text stays discoverable through the status indicator, title tooltip and aria-live without adding a second chrome row. Reuse the sidebar's adjustable width. On narrow product layouts, a Resources drawer selects a target while retaining chat and preview access. This document stacks its mock panes on narrow screens for review; it does not propose an additional product page.

Selection and following

  • At most one preview per App window; preferences are scoped to the viewed conversation and branch. Following responds only to host-admitted operation events in that branch. Opening a resource, status polling or receiving a screenshot alone does not switch the preview.
  • Concurrent child agents follow the last operated target in host event order, with the active agent identified. Coalesce rapid changes over approximately 200ms and render the latest frame without accumulating stale frames; this is an initial parameter to measure.
  • Clicking any resource shows it without changing Auto or Fixed preview; in Auto preview the next Page the Agent observes or operates replaces it. Observe counts as an operation for following. The agent continues its task and cannot replace that preview. Inspecting another branch's resource neither checks out that branch nor grants write access. Enabling automatic display returns to the latest admitted operation in that branch.
  • Hide changes visibility only; background work and all resource rows remain. Later events cannot reopen it. A row click or Preview in conversation restores it. Close preview keeps the Page. Dragging and resizing change presentation without copying a Page or raising a native application.
  • Changing branches restores that branch's preview preference. A new preference follows its latest operation target, including an unavailable state if that target has closed, or displays an empty state when no operation exists. Other branches may keep running but cannot replace the visible preview.

Retention, opening and closing

  • Resources has no Pin control and no search field. A row click selects a interactive chat preview; Preview in conversation is the explicit accessible equivalent, restores a hidden PiP, and returns to the owning session when a webpage occupies center. Expand enlarges the same target. Explicit Open page adds an ordinary top view of that exact existing Page and hides the preview. Repeated opening reuses the same Page. Hidden agent pages stay retained in Resources.
  • Existing explicitly pinned or user-opened top pages remain ordinary user views. Migration must not close them or hide every old page. Recent agent use does not create new top tabs.
  • Task completion releases Python, input leases and temporary observations. Associated pages and VMs remain idle and available. Explicitly temporary test/intermediate resources retain their declared disposal policy; task completion does not mean close all resources.
  • Menus name the operation: Close webpage, Disconnect window, Disconnect VM. Stop VM is separate and never triggered by hiding its preview. Borrowed user applications are never automatically quit.
  • Closing a target in use or referenced by other branches shows affected executions, requests stopping and waits for write-lease release. Unconfirmed stopping remains Stopping. Closed records move to a collapsed unavailable group; default counts include only currently connectable targets.

Ownership, branches and concurrency

Resources persists serializable descriptors; the host retains actual Page/window/VM handles and leases. Reuse existing conversation and branch projections. Group keys require stable branch identity or verifiable fork lineage, not the changing message HEAD or a new group per execution. Renaming, continued turns and retries update presentation or associations; forking does not duplicate external page state.

  • A descriptor includes resource ID, type, sanitized target description, actual owner, lifecycle, connection generation and preview capability. Branch associations separately track originating invocation, branch, child agent and sharing mode. Do not merge distinct Pages with identical URLs; merge UI and usage records for the same actual Page.
  • Child-agent resources appear under the originating parent conversation branch with their actual owner identified. Later child work or branch renaming must not rewrite provenance. Existing session/execution authorization remains per resource; a shared display group grants no access.
  • Ancestor resources show Referenced from. Browser branch writes default to an independent Page, without claiming external website or login-state isolation. Native windows and VMs cannot be cloned automatically; require explicit lease transfer or an independent target.
  • Preview selection is not control acquisition. Shared references may appear in several branch rows with their current controller shown. Write leases exclude conflicts at the actual input scope: Page, application process with shared focus, VM or host desktop. Window grouping does not establish concurrent input support.
  • Preview events carry session, branch, resource, connection generation and monotonic sequence. Discard stale events after branch changes, reconnection or revocation. Metadata is restorable; process-local handles are not. Legacy records without provable branch ownership belong in Unassigned, without guessed migration.

Inspection, takeover and disconnection

The image mirror is read-only; the actual tab or application remains normally usable. Its manual entry and yielding rules are specified below. Explicit stopping acknowledgement and ordinary human access are distinct; do not turn an Agent permission into a page-blocking mask.

Idle background targets retain their connection without high-frequency capture. Only the visible preview subscribes to images; do not periodically scan all host applications. Show frame freshness and operation progress. A disconnected resource labels its image Last frame, exposes metadata and disables input. App restart, Page crash and VM reboot require identity validation; durable metadata does not imply a live target. Under memory pressure, offer explicit resource release rather than silently discarding forms or stopping VMs.

Existing tabs, operation cues and human takeover

PiP is exclusively a chat preview of an existing Page. Opening any regular webpage tab hides that preview and any reserved space so the native Page fills the available content area. TARGET (not current runtime): a webpage tab and its small chat preview may display at the same time and stay in sync on the same Page; hiding the preview does not close the Page or the main view. Runtime is unchanged. Do not duplicate a Page screenshot beside or over the actual Page, dim the Page, add a blocking ownership layer, or hide an iframe under CSS while native geometry stays reserved. Opening the Page keeps the same Page identity, resource and follow preference. Returning to the conversation restores the preview for that branch unless the user explicitly hid it. A row click and Changing automatic display never steal tab focus. Explicit Preview in conversation does not reveal a top tab; if invoked while a webpage occupies center, it activates the owning session so the chat preview is visible. Only explicit Open page reveals the Page as a top tab. The live webpage stays undimmed and usable in its own tab. The full Web toolbar, control menu and actions remain above the Electron Page.

One native WebContentsView cannot occupy two rectangles simultaneously. Keep one live native interactive view when the Page tab is current, and deliver the same target's image stream to chat PiP only while that conversation is current. This restricts simultaneous native-view attachment, not the number of UI references to one Page. Additional presentations use mirrors; locating the existing tab selects that live primary view and hides the preview. Chat PiP remains a floating overlay on the conversation. The PiP image is strictly read-only: never forward scaled clicks, keys or scrolling from it, and do not crop or zoom the capture merely to enlarge the thumbnail. A never-shown Page is created with a 1920×1080 CSS-pixel viewport at the user's normal page zoom so capture has a stable 1080p layout; PiP size is independent of that native viewport. Returning a visible Page to the background keeps its last native bounds rather than shrinking them to the thumbnail or reapplying the creation default. Do not apply the legacy PiP layout-zoom path to thumbnail size. Open page locates the exact existing tab. If no view is visible, explicitly open a view of that Page, without another Page, login, reload or URL-based identity guess. Native windows and VMs also distinguish their actual control entry from an image mirror. Hiding the mirror leaves the live page available. Viewing or focusing the live tab does not request a pause.

While PiP is visible, subscribe to continuing captures of that exact Page, including changes caused by both Agent and human input; do not move the live view to capture it. Each frame carries resource ID, connection generation, sequence and capture time. Reject frames from an old binding. Set a bounded refresh rate and stale-age threshold during adapter acceptance, expose the last-frame age, and label delayed or unavailable capture as Last frame rather than Live. A static screenshot is not a live mirror. Hiding PiP unsubscribes its capture demand without closing the Page; do not capture every retained resource continuously. Dragging the floating chat PiP caches container bounds at pointer down and previews movement with a transform on animation frames. Pointer-move does not remeasure layout, write React or store state, or persist the rect. Pointer up, cancel and lost capture write the latest position after a single clamp against the current container bounds. Unmount, live-loss and a resource switch discard an in-progress drag, clear the transform and release pointer capture without writing that rect. Capture and image replacement pause for the drag and resume on pointer up, cancel or lost capture; they do not resume a stopped loop. A capture that started before pause is discarded even if resume happens before it settles; resume then starts a fresh capture when the old request finishes, keeping a single in-flight capture. Pausing must not permanently stop the loop by clearing isCurrent. The compact preview resizes from all four edges and four corners; there is no triangular corner-only handle. Aspect lock and native-acceptance of those handles remain a separate geometry check.

    Pausing while the human can still use the page

    Agent active describes host-authorized automation writes, not a lock denying human page access. Actual human input closes subsequent Agent dispatch in the conflicting input scope, invalidates queued old-frame actions and requests a pause from the owning execution. Keep the page's brightness and usability, show Pausing… in its toolbar, and never copy or replay the human click later.

    Dispatched operations may be impossible to retract immediately, especially native input and long browser calls. Late results can occur during yielding: do not claim zero overlap or confirmed stopping. Record unresolved effects and observe again, without automatically undoing human changes or resuming the agent. Show Agent paused only after stopping acknowledgement, held-input release and target-state reconciliation. On failure or timeout, show Could not pause. Try again in the toolbar with Retry pause while connected; normal human access remains available and new Agent dispatch stays closed. Advertise zero-overlap automatic takeover only after adapter acceptance establishes it.

    Pause Agent to use page opens the exact human entry after stopping confirmation; sending a pause request is not success. While waiting, the button shows Pausing…; an already open live tab remains clickable, editable and navigable. Only subsequent Agent dispatch is gated, not human page input. Defer locating an unopened entry until acknowledgement; the separate Open page action still permits direct access and hides the chat preview.     Previewing, expanding, hiding and branch inspection are distinct from live input. Hiding a mirror neither revokes manual interaction in a visible live tab nor resumes the agent. Inspecting another branch changes presentation only; pending requests remain bound to the original resource ID.

    Pointer down in the real page (including starting text selection), page-operating key/input events, scrolling and user-initiated navigation request yielding. The real tab remains interactive during Pausing… and Could not pause. Try again; only the Paused claim and completion of the explicit acknowledged pause path remain unavailable.

Original applications, the host desktop and external VNC/RDP clients are outside those surfaces. Do not alter their menus or draw their window borders; keep controller state, Show actions and history in OpenProgram PiP or its corresponding control panel, with locations over the captured preview. Locating the original window does not grant authority to change foreign application UI.

    Later review and learning: retain verifiable records first

    Reuse existing operation receipts with task/branch/resource, before/after observation, target description, action parameters, order, outcome and human corrections. Visible cues consume that same event source, not a separate invented trace. Records initially support debugging and inspection. With user approval, a later task may read selected sanitized excerpts to analyze targeting errors or propose reusable operation rules.

    Record my next demonstration is a separate opt-in with explicit start, stop, scope, preview and deletion. When reliable redaction is unavailable, keep content-free action metadata and omit the image/demonstration segment. Distinguish human demonstrations, automation receipts and failed traces; the user selects material before use.

Validate proposed rules on independent test targets rather than replaying them directly on real user pages, applications or VMs. Training and data export require later discussion and authorization.

    Conversation tool activity details

    A computer_use_agent call appears in the timeline by its target and step: the application and action (with the same approval wording), the Page action and URL, the VM action, code run in an application, or a task handed to a new agent with the first line of its brief. Calls recorded by the earlier GUI tools (gui_agent, computer_use, browser_use, vm_use) stay readable: selecting one opens the shared Details panel with a GUI activity card above the raw parameters and output. The card replaces the transport-level Status badge, because a completed function call is not evidence that the task succeeded.

    • Outcome: the card header and the timeline row note share one status: Running, Action applied, Succeeded, Failed, Needs takeover, Cancelled, Interrupted, Paused or Result unavailable. A result without an explicit status stays Result unavailable.
    • Takeover: the recorded blocker and the user action are emphasized. A summary that repeats either is not shown again. The task text appears only in the raw parameters.
    • Steps: one line per recorded capability call (capability, target app or URL, status) in recorded order. Failed and stopped steps add a reason clamped to two lines. Steps come from the result history; while a call runs they are derived from visible capability children without counting nested planner calls. A direct capability call is its own header and has no step list.
    • Ownership: a detail carries its call's conversation id, and a detail from another conversation with the same call path is never replaced. Updates refresh only the selected call. A failed full-output fetch shows its error without marking the call failed.

    Recorded screenshots are not offered. Capture paths are temporary directories outside the readable attachment roots and may already be deleted; showing them needs the runtime to retain observations in the session directory first.
