Web-tab presentation Center tab · Compound split · Session picture-in-picture (PiP)

Audience: developers maintaining the apps/web center area Scope: presentation and binding within the renderer Excludes: cross-window transfer and main-process View geometry

This document answers where a web leafis currently displayed, who controls it and what the Agent can do with it. Interaction rules follow one invariant rather than separate patches.

1 · Conceptual model

Thepairing between session S and page W is the sole first-class relationship. Split and preview are two presentations of that pairing. A WebTab leaf has only one native WebContentsView rectangle at a time; chat PiP directly presents that Page's interactive native view. When the same leaf is active as a normal top tab, hide the chat preview and its reserved space and let the native page fill the content area. The page tab and PiP must not appear simultaneously or replace the page with a mask or screenshot.

Pairing is established when an Agent opens W in S, the user drags W into S's split/group, the user collapses it, or an Agent operates an unpaired page.show() and registerPipPair write to the pairing table; the coverage function only decides which host renders that pairing now. Standalone pages have no pairing before Agent interaction and therefore no collapse-to-preview action.

Leaf identity An entry in the center-tabs store's kind:"web" . Its canonical id is w:<url>; a fork uses nextPopupWebTabId to form w:<url>:popup:…. Floating does not remove the leaf. tabs[] / groups[] / splitWebTabId / activeId
Pairing A persistent session↔page relationship stored in pairedOwnerByTabId. A session may pair with multiple pages; closing either side clears it. Each session has one preview slot showing the Agent's current working page; other paired pages remain in the tab bar. Module-level Map, registered through show() / registerPipPair
Binding Globally at most one active (tabId, ownerTabId): which paired page currently occupies the preview slot. Switching sessions does not change the binding;hide() moves it into background memory. Rebinding another page does not erase the old pairing. useWebTabPip singleton, not persisted
Host The place that actually renders the page. Derived by pipCoversCenter(tabId, ownerTabId, center) as a pure function of binding × active tab. Components do not store a separate visibility state. pane · chat PiP · none

First-class state therefore consists of pairing, layout (tab-bar membership, groups and active tab), active binding and background memory. Split and floating views are two presentations of one pairing, not separate relationships.

Compound group groups[] At most two members, projected as one tab-bar entry. User-created groups use groupTab; PiP Expand to split uses setSplitWebTab to pair the current session and leaf.splitWebTabId is a compatibility pointer, materialized into a group during normalization only when the leaf is ungrouped and the active tab is a session.

When an Agent repeatedly invokes open / activate on pages in one session, the preview slot follows attention: the new working page show enters the slot (or revealAgentWebTab inserts an unpaired page or a page paired with the current session but not visible, recording pairing), and the previous page returns to the tab bar. Pages paired with other sessions are excluded and not taken over.

    3.3 Coverage function pipCoversCenter

    The preview renders if and only if pipCoversCenter holds:pipCoverBase and owner checks are true, and activeId is the owner session. Split retains exclusive native bounds (the preview does not render whensplitWebTabId === tabId ). Opening the page tab makes coverage false and hides preview while retaining binding.

    1. The leaf still exists and kind === "web";
    2. The leaf is not in the active group's visibleIds : split already renders it, so no second view is overlaid;
    3. splitWebTabId !== tabId;
    4. The active tab is a session;
    5. activeId === ownerTabId.

    PiP floats only over chat, inside .center-pane-chat. When the page tab is active, the component returns null without reserving native docking space. The store subscribes to center-tabs: owner or leaf deletion → end(); invalid background reference → clear memory.

    7 · Known inconsistencies

    These are existing differences between code and product semantics, not newly proposed work.

    Fork ignores memory after hide.pipOpenMustFork Checks only active binding. After A clicks ✕ and B opens the same URL, ensureWebTab reuses the leaf and show(id, B)——show clears background, silently removing A's restore chip. No takeover precisely covers currently displayed previews, not a session's preview resources.

    Fork recognizes only canonical leaves.The condition is webTabId(url) === boundTabId. When a third party opens an already-forked popup id, the condition is false andensureWebTab returns another canonical leaf. The outcome happens to be correct, but the check protects id shape rather than every bound same-URL leaf. Each fork leaves an orphan leaf, cleaned by op=close or manual user closure.

    Close does not track the opener.The product says an Agent can close tabs it opened but not tabs in user layouts. Implementation checks only group membership. User-opened standalone pages can be closed; Agent-opened pages dragged into groups cannot.

    Fork is absent from the split path.On a wide desktop layout with an existing web member,openWebTabInSplit changes that pane's URL without calling pipOpenMustFork. Same-URL conflicts apply only to the PiP branch.

    No takeover protects leaves, not slots.R3's fork gives B a new instance, but the same show(id, B) overwrites the sole global binding. A's canonical leaf remains but its binding disappears, so returning to A does not restore preview. Collapsing another page to preview similarly replaces the old binding silently. If no takeover means retaining A's preview resource, implementation does not satisfy it.

    Show does not ungroup.When an Agent binds a canonical leaf already in another group's layout as its own PiP, it does not call ungroupTab. Returning to that group retains the member; if the leaf is activeId, coverage is false, preview hides and the native page fills the content area.

    Region definitions differ.surfaceRefForChat Marks ungrouped paired pages, including PiP, as region:"right"; browserPageInventory Marks ungrouped visible pages as "center". Agent-visible left/right/center positions disagree with inventory.

    Condition 5 implies condition 4.Every owner in show is a session tab, andactiveId === ownerTabId already guarantees kind === "session".pipCoverBase . The condition remains so WebPreviewChip can independently reuse pipCoversCenter before restoring as a fallback.

    PiP is absent from version-2 payload.Refresh loses binding, background and preview position; leaves return to normal center tabs. Reappearing on owner return applies only within the same renderer lifetime.

    8 · Session-tab back and forward

    Back and Forward appear at the far left of the tab bar and use only the current tab's own history, including its default entry page. Web pages retain their own navigation controls.

    ← → [Session B ×] [Web page ×] ＋

    Current tab history: session A → session B. Back restores A; Forward restores B. Choosing C after going back removes B's forward entry.

    Public entryObservable result
    Open session from sidebar, history page or deep linkNavigate in place in the current session tab or new-tab page; other page types may select an existing session tab or create one.
    Back / ForwardEach tab stores independent history and cursor. Even if a target appears in another tab, replace only the current tab and preserve others. Reopening the current session adds no history.
    Drafts and ACKHistory retains draft IDs; input remains keyed by session ID. Background acknowledgements update all matching history records without activating background sessions.
    Reload / Delete sessionHistory persists with version-2 tabs; legacy tabs become single-entry histories. Known deleted sessions are removed from every history and cannot be restored with Back.

    Implementation uses the existing Zustand tab store, layout normalization and route activation. Tab ID identifies a tab instance and sessionId identifies its current session; tab identity is no longer inferred from session ID. Page history stores page identity, session metadata, sidebar route and file location without copying input or messages. New tabs receive a unique suffix on ID collision. Source-window transfer removal checks prepared session history before and after asynchronous acknowledgement; navigation changes cancel stale transfers, and rollback does not overwrite newer navigation.

    Route synchronization responds only to pathname changes; markSessionReady handles session acknowledgement. User tab navigation reacts to current-tab sessionId / draft changes, preventing intermediate old currentSessionId updates from overwriting new navigation. Deletion uses only IDs confirmed removed from loaded lists; unloaded records do not count as deleted.

    Comparison scope retains this page's existing web, split and PiP references and boundaries. Session history is application state, not browser-global History used per tab, and does not change page navigation, server protocols or permissions. Independent tab instances may show the same session; restoration retains every tab's identity, content and history. Different sessionIds remain distinct even with equal titles.

    Independent per-tab navigation and default-entry restoration are implemented and passed independent specification and quality reviews. Public-entry tests cover navigation, routes, file renaming and historical-draft transfer.

    Initial page navigation

    Replacing an explicit New tab page records it in that tab's page history. Back returns to that initial page and Forward restores the selected application or built-in page, without adding another visible tab. Selecting another destination after Back discards the old forward entries. Existing conversation history remains navigable before returning to the initial page. History is persisted with the tab.

    Tab controls

    Back, Forward, and New tab each use a 28px-wide button with an 8px gap. An empty tab-list container takes no layout space. New tab has no left divider.

    Closing the last tab

    The final visible tab can close completely. Its window and empty tab strip remain open, and the center content area stays blank. The plus button explicitly opens a new tab. Session-owned hidden pages remain available in Resources and never become the close fallback. Close selects visible neighbors after normalizing split groups. The empty state persists across route changes and reloads; it does not automatically create a draft conversation. Moving tabs between windows retains its existing window lifecycle.

    Acceptance: close the final tab through the close button or keyboard command; no visible tab or center content remains, and explicit open actions create the requested tab.

    Interactive floating page

    The supplied Codex screenshot is a visual reference; its internals are not established by the image. Adopt continuous visible content, direct input and frame-coalesced dragging. Reuse the existing Electron WebContentsView and visible-bounds collection instead of creating another Page or forwarding image coordinates. The native view remains displayed during movement. Each animation frame updates the host transform and native bounds; only release persists geometry. Native input keeps the existing browser control and permission behavior.

    The plain browser uses a sandboxed iframe for HTTP(S) pages. It is a separate embedded browser document, not a connection to the Desktop Page; login state and frame-ancestor restrictions follow browser policy. Restricted URLs display an unavailable message and retain Open page. Older Desktop bridges without visible-view support keep a labeled image fallback. Hidden, switched or unmounted previews release bounds and observers without closing their Page. Menus and dialogs occlude native content.

    Acceptance: the public WebTabPip mounts the exact tab id, performs no capture on a current Desktop bridge, updates native bounds during drag without recreating or hiding the page, preserves pointer cleanup and session isolation, and exposes iframe interaction without a body click overlay. Native App acceptance verifies a changing counter, clicking, typing, scrolling and continued updates during drag.

    Tab press, release and resource attachment

    Pressing a tab highlights that tab without changing the active page, route or conversation. A release without a drag activates it through the ordinary click path. A drag, Escape, cancellation or lost focus consumes the pending click. Dragging within the strip preserves reorder; releasing outside it preserves the existing transactional window transfer.

    The New window cue stays inside the top tab strip, above the native webpage bounds. It does not follow the pointer into a WebContentsView. CSS stacking cannot place renderer content above an Electron child view; hiding the page or creating another native overlay is unnecessary for a strip-level cue. Existing pointer capture and desktop transfer transactions remain authoritative.

    A single webpage tab dragged onto Resources in an existing visible conversation attaches that exact Page to the conversation on release. The Resources navigation entry works even while another sidebar view is selected; the open Resources body is also a target. The target highlights before release. Success opens Resources while preserving the active conversation, webpage identity, top tab and original associations. Attachment grants use through the existing resource governance; it does not interrupt or override another execution's active operation. Compound groups, unsent drafts and other tab kinds are not attachment sources or destinations.

    The owner-authorized server verifies the session and exact live window/tab/native-target identity from the registered desktop connection before retaining the association. It reuses BrowserResourceStore rather than creating a URL copy. Failure reports an error and does not navigate, detach or fabricate a successful binding. Native connection changes reject stale results. Drag cancellation sends no attachment command. Keyboard activation and context menus retain their existing behavior.

    Independent tab navigation

    Each tab owns one ordered page history and cursor. Its default launcher is the first page. Navigation replaces content in that tab; Back and Forward change only that tab's content. Selecting another tab never records a visit. A destination already shown elsewhere does not redirect replay or modify that other tab. Sessions and applications may be displayed by distinct tab instances.

    Page snapshots contain page identity, session metadata, sidebar route and file-view snapshot, never nested histories. The existing pageHistory persistence is the only history storage. Session legacy history is converted on first navigation. File-tree view data is derived from the active tab; switching tabs restores that tab's current route and file view. Background ACK/title changes update retained pages without appending history.

    Explicit new-tab actions still create tabs. Launcher choices and navigation within a session, Files or Browser home replace the current tab. When a target identity already belongs to another tab, the current slot gets a unique instance identity. Native browser URL history remains in browser controls. No window-wide or cross-tab fallback history is retained.

    Acceptance: create A and B with different page histories; switch between them; traverse both directions and assert the other tab and its cursor remain byte-for-byte unchanged. Cover default launcher, files/folders, sidebar routes, sessions and applications, including identical destinations in two tabs, draft ACK/title, delete, reload and grouped layout references.

    Code organization: center-tabs-store.ts is the public composition entry. store/ contains typed state, shared commit helpers and actions grouped by layout, navigation, sessions, pages, browser, split and transfer. navigation/ contains pure page-history and legacy-session helpers plus selectors. No action module owns a second history store.

    Application settings and tab navigation

    Settings routes (/settings and its descendants) belong to the application shell. All settings entries, including the account menu, window menu, keyboard shortcut and browser settings links, use this boundary. Opening settings or changing sections leaves the selected tab and its page history unchanged. Clicking a tab restores its own content. Settings may retain their URL for direct links and reload, but never become a tab history entry.

    Persisted and transferred tabs discard legacy settings visits. The current settings visit restores the preceding page of the same tab identity, retaining current metadata. If no underlying visit exists, the tab retains its content identity with no settings route. Other page visits, forward history, groups, drafts and file snapshots remain intact. Docs and About are external links; fullscreen remains a window action.

    The existing router and tab persistence normalizer are reused. A separate settings tab or second navigation-history store is unnecessary. Ordinary sidebar content and native browser URL history retain their existing ownership.

    Acceptance: open settings from a session, launcher, file or browser; switch settings sections; select the same or another tab; Back/Forward and reload must never restore settings through a tab. Normalize old histories with settings before, at and after the cursor, including all-settings records and transferred payloads.
