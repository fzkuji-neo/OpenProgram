Total response duration and interaction count

Default chat responses have neither a tool-interaction limit nor a total processing-duration limit. HTTP model streams that keep producing data are not interrupted merely for running a long time. OPENPROGRAM_SSE_TOTAL_TIMEOUT_S defaults to 0, meaning no total-duration limit; positive values remain explicit deployment deadlines for one stream. An unset limit uses a positive-infinity deadline. Existing HTTP URL, redirect and response-size checks remain unchanged.

Connection establishment, writes, pool waits, no-data and no-effective-data checks remain distinct from total response duration. User cancellation always applies. Explicit runtime.exec deadlines, program call-round parameters and declared budgets of standalone GUI/browser tools are not overridden by chat defaults.

Acceptance uses public boundaries: an actual AgentSession exceeding the former 200 interactions, a managed HTTP stream returning content beyond the former 7200 seconds, and continued termination under explicit deadlines. Tests neither wait for real long periods nor modify real sessions.

Implementation status

Chat interaction loops and individual HTTP streams now default to unlimited counts and total duration. Regressions cover more than 200 tool interactions, continuous responses beyond the former duration, Google synchronous/asynchronous transport, and explicit total-duration configuration.

1 Three timeout responsibilities

The system has three semantically different timeouts, owned by different layers and code. Confusing them causes most misunderstandings.

① call-level Covered

Owner: provider transport

Maximum wait for one HTTP request/SSE stream and maximum interval between chunks, enforced jointly by httpx timeouts, TCP keepalive and codex SSE parsing budgets.

② exec-level Partial

Owner: runtime.exec(timeout_s=)

Wall-clock limit for an entire exec, including all retry sleeps. Currently a soft deadline between attempts; it does not propagate into inner stream retries, and defaults to None=unbounded.

③ task-level Unreliable

Owner: caller (runner / dispatcher)

Total budget for one benchmark sample/Agent turn: OCR, multiple crops, gates, review and retries. Only the caller knows it. ScreenSpot currently uses signal.alarm, which the framework catches.

4 Exec retry state machine

Retry logic within one exec() . Key point: the deadline is checked only between two _call between attempts(dashed box), so it cannot interrupt the currently running _call.

Duplicate retries at two layers (design issue). ConnectError The inner layer already classifies retryable=True and retries it three times before raising ProviderStreamError(retryable=True); once it reaches exec, _is_permanent_error does not match → exec again retries the same transport error with a fresh 6× budget.The same transport error is independently retried at two layers, turning a ~90s problem into 600s+.
Fixed 4e64ac95. Exec propagates one deadline into stream_retry(checked before each attempt and backoff), and stream_retry marks budget-exhausted exceptions with transport_exhausted ; exec thendoes not retry with a new budget , reducing 18 attempts (3×6) to the three inner attempts._parse_sse_stream SSE waits in min(budget, remaining deadline) are also clamped, so individual streams cannot exceed the budget.

Web/worker contexts are worse. With a running event loop, _run_async takes asyncio.run and offloads it to a thread-pool worker(runtime.py:1260). Python delivers signals only to the main thread, so signal.alarm in this contextcannot reachthe running _call : the soft watchdog is ineffective.

Signals never reach worker threads; instead, --exec-timeout-s → OPENPROGRAM_EXEC_TIMEOUT_S provides a signal-independent call-level deadline, and _run_async now propagates the deadline ContextVar into the worker thread.

Side effects of thread-future fallback (#6). Python cannot safely kill a thread: the caller returns on timeout, but the _call thread keeps running in the backgrounduntil the socket itself fails; meanwhile it may append model-call nodes or write store/DAG state, causing contamination. Thus #6 is only a last resort and must rely on #1 read timeouts to bound the leak. Ideally providers expose async and exec uses asyncio.wait_for(cancellation reaches await points with no leaked threads); synchronous threads remain a fallback only when async is unavailable.
