OpenProgram · Provider / Runtime design · implemented and reviewed · 2026-08-12

JSON Schema Structured Output

Design baseline: main@708bfbab. Implementation evidence: Tasks 1–6; final review commit 2fb471b3. Sections 2–15 retain the approved design and implementation checklist; §16 separates implemented contracts, verification evidence and unmet complete gates.

Design conclusion: Continue the existing Runtime.exec(..., response_format=...) as the sole public entry. Add normalized schema configuration to public provider types. Capability negotiation selects native provider JSON Schema or a constrained hidden-tool fallback. Regardless of provider strict claims, final results require strict JSON parsing and local validation against the caller’s original schema. Failure permits at most one semantic repair request; return only validated Python JSON values.

The existing Agent loop now implements schema normalization, negotiation, strict local validation, one optional repair, typed CLI/Web entries, record/replay v2 and the session-title consumer. Unverified provider combinations fail closed; ordinary text calls retain return semantics.

1. Scope, goals and boundaries

Unified semantics

Python Runtime, Agent, CLI and WebSocket/API share one schema, negotiation result, validator and error classification.

Streaming compatibility

Preserve incremental provider text/tool events while explicitly representing candidate attempts, discard, retry and final structured results.

Reproducibility

Record/replay captures normalized requests and every provider call; offline replay reruns identical parsing, validation and bounded retries.

Excluded: lossy schema-to-provider-subset rewriting, automatic Pydantic types, cross-language code generation, tokenwise incremental JSON AST, Web schema editor, or changed ordinary-text returns/events.

3. Public API and normalized types

Retain the parameter name response_format because it is already public and documented. Support bare JSON Schema and an envelope containing OpenProgram controls. Normalize exactly once.

JsonValue = None | bool | int | float | str | list["JsonValue"] | dict[str, "JsonValue"]

class JsonSchemaOutput(BaseModel):
    type: Literal["json_schema"] = "json_schema"
    schema: dict[str, Any]                  # Original caller schema; never mutate in place
    name: str = "response"                 # ^[A-Za-z_][A-Za-z0-9_-]{0,63}$
    description: str | None = None
    strict: bool = True
    fallback: Literal["auto", "none", "prompt"] = "auto"
    max_validation_retries: Literal[0, 1] = 1

# Existing-call compatibility: a bare dict is the schema, not a provider payload.
Runtime.exec(content=..., response_format={"type":"object", ...}) -> JsonValue
Runtime.exec(content=..., response_format=JsonSchemaOutput(...)) -> JsonValue
Runtime.exec(content=..., response_format=None) -> str
  • Use overloads for return types; ordinary text calls still return str. Successful structured calls do not return JSON strings.
  • async_exec, exec, AgentSession and dispatcher use the same JsonSchemaOutput; provider-private response_format payload.
  • is not accepted. Before any network request, invoke validator_for(schema).check_schema(schema). Unknown meta-schemas or invalid schemas raise StructuredOutputSchemaError without consuming a provider request.
  • Declare pyproject.toml directly in jsonschema>=4.23. An existing transitive lockfile dependency is not a core-feature contract.

4. Capability negotiation

The model catalog says only whether the model claims structured-output support. API adapters must also specify payload dialect, streaming and tool-combination constraints; negotiation checks both.

class StructuredOutputCapabilities(BaseModel):
    native: Literal["supported", "unsupported", "unknown"]
    dialect: Literal["openai_chat", "openai_responses", "anthropic",
                     "google", "bedrock"] | None
    streaming: bool
    with_tools: bool
    schema_profile: str                 # Provider-subset checker name

negotiate(model, api_provider, options, tools) -> StructuredOutputPlan
# plan.mode: native | tool | prompt
# plan.provider_schema: Semantically equivalent projected copy
# plan.original_schema: Used for final local validation
  1. Invalid schema: fail immediately.
  2. If the adapter explicitly supports the API, the model field is not False, schema projects losslessly and current tools are supported, choose native.
  3. fallback="auto" and the provider supports strict tool schemas, schema projects losslessly, and tool_choice does not prohibit/force another tool: choose a hidden tool.
  4. fallback="prompt": explicit prompt fallback guarantees only local validation, not provider-level strictness.
  5. Otherwise raise StructuredOutputUnsupportedError before sending, reporting provider, model, conflicting capabilities and fallback reasons.
Do not optimistically interpret unknown capability. openai-codex and gemini-subscription may reuse official model entries but use different backends. Without API-adapter contract tests, Model.structured_output=True alone must not enable native fields.

5. Native mode and fallbacks

Native schema

Adapters only map normalized configuration to provider payloads. Existing providers/_schema may supply traversal/dialect detection, but transformations must preserve semantics, such as key naming or JSON-string serialization. Dropping constraints, relaxing additionalProperties, rewriting unions or any other lossy transform reports the exact path and disables native mode. Final validation always uses the caller’s original schema.

Hidden-tool fallback

{
  "name": "__openprogram_submit_json",
  "description": "Submit the final response matching the required schema.",
  "parameters": <provider_schema>,
  "strict": true
}
  • Send the hidden tool alongside caller tools. Ordinary tool calls execute normally and continue to the next round.
  • The hidden tool must appear alone. Its arguments are the final candidate; do not execute it or generate ToolResultMessage.
  • The fallback round sets parallel_tool_calls=False. If the caller explicitly requests parallel execution, tool_choice="none" or forces another tool, negotiation fails rather than overriding settings.
  • Plain text without a hidden-tool call is classified as missing_submission and may enter one repair request.

Prompt fallback

Enable only when the caller explicitly sets fallback="prompt" : add a compact schema and JSON-only requirement to the system layer, then parse/validate final text identically. This is not strict and is never silently used in auto . This distinguishes provider constraints from purely local detection.

6. Streaming events and incremental text

Structured output does not incrementally validate schemas. Forward raw text deltas per attempt so consumers may display generated JSON; parse only after final text_end . Add two framework events and optional attempt metadata on text events to prevent invalid attempts becoming final messages.

EventTextStart/TextDelta/TextEnd.output_attempt: int | None = None

EventStructuredOutputRetry {
  type: "structured_output_retry",
  attempt: 1,
  next_attempt: 2,
  issues: [{code, path, schema_path, message}],
}

EventStructuredOutputEnd {
  type: "structured_output_end",
  attempt: 1 | 2,
  mode: "native" | "tool" | "prompt",
  value: JsonValue,
}
1
Forward attempt=1 text/tool deltas into a client candidate buffer without committing persistent messages.
2
After provider raw done , strictly parse and validate. On success emit structured_output_end, followed by exactly one done; stream EOF without raw done/error fails as incomplete rather than synthesizing success from a partial message.
3
For repairable failure emit structured_output_retry. CLI/Web clear candidate buffers; the Agent loop starts another provider stream.
4
Commit if attempt 2 succeeds; otherwise emit error without done and do not persist an invalid final assistant message.

Provider raw done is consumed by the Agent loop; expose only the structured transaction’s final done. Ordinary text retains its event sequence. CLI/TUI/Web safely ignore unknown events for rolling upgrades.

7. Strict parsing, validation and bounded retries

Parsing rules

  • Direct text uses json.loads(raw, parse_constant=reject_nonfinite); reject Markdown fences, surrounding explanations, trailing content, NaN/Infinity.
  • Parse hidden-tool arguments as complete JSON text too; never use utils/json_parse.py partial/forgiving parsing.
  • Use jsonschema.validators.validator_for(original_schema) to create the validator, with a registry prohibiting external-resource access. Sort errors by instance path, schema path and message.
  • Schema preflight rejects all $ref/$dynamicRef/$recursiveRef that cannot resolve to embedded resources in the current schema. Fragment references and relative references defined by embedded $id remain valid, so Runtime, CLI, Web and replay never initiate DNS, HTTP or file reads for local validation.
  • Canonical schema JSON is limited to 1 MiB, 4096 container nodes, 8192 container edges and depth 100. Exceeding any limit returns stable invalid_schema.
  • before provider calls. Fragment-only references allow local JSON Pointers/anchors; direct reference self/mutual cycles fail preflight to prevent validator recursion overflow. Finite recursive schemas advancing through instance structure remain supported.
  • Transport at most 20 errors with messages of at most 500 characters each, avoiding copying complete sensitive output into logs or WS errors.

Shared call budget

max_validation_retries and max_retries are two limits, not multiplicative loops. The former caps semantic repairs after initial-candidate failure; the latter caps total provider calls initiated at the Runtime boundary by one synchronous/asynchronous exec , including the initial call, semantic repair and calls following transport failures. Repair requires both an available validation retry and remaining shared call budget.

Therefore Runtime-boundary provider calls never exceed max_retries. For example, max_retries=1 causes an invalid first candidate to immediately return StructuredOutputValidationError; max_retries=2 with one default validation retry permits only initial call plus one repair. A repair transport failure already consumes budget; the outer layer cannot regain a full budget. Adapter/SDK transport retries remain governed by existing deadlines/transport settings, not validation retry counts.

structured_output_retry.attempt and next_attempt continues identifying structured candidate attempts, not transport attempts. Emit only after Runtime confirms remaining shared budget and is about to repair; never emit false retry events on exhaustion.

Repair prompts contain only failure type and bounded issues, without reinterpreting schemas or calling another LLM. Repair context lasts only for this exec; session history/final DAG keep only the valid final assistant, while model-call records retain both provider calls for audit.

Python API

    e.provider

    e.attempts

StructuredOutputError uses the existing LLM-error boundary without pretending to be a transport error.retryable means whether a new exec/budget could succeed; validation-retry exhaustion is indicated by attempts .

CLI

Add to existing one-shot openprogram --print the option --json-schema PATH; initially leave interactive REPL/TUI input unchanged. Success writes canonical UTF-8 compact JSON plus newline to stdout and exits 0. Errors go to stderr: usage/invalid schema exits 2, unsupported 3, generation/final-validation failure 4. Existing provider/auth/cancel semantics remain. Persist compact JSON in session assistant content with parsed value/mode in metadata.

  • Server json.dumps(..., default=str) must not serialize structured values; validated values already belong to the JSON data model, otherwise this is an internal error.

10. Record/replay and persistence

  • RECORDING_FORMAT_VERSION moves from 1 to 2. v2 request options record complete normalized response_format; explicitly reject old v1 to avoid ambiguous mismatches from default None fields.
  • Record raw provider events, not locally derived validation events. Replay returns identical raw events and the Agent loop deterministically reconstructs retry/end/error.
  • Each validation repair creates a new provider call and call_index; recordings must contain two request/call_end pairs. Missing or extra replay calls are mismatches.
  • After normalization, recursively sort schema keys and compute SHA-256 for logs, DAG metadata and error correlation. Recordings retain the full schema for strict comparison; hashes do not replace it.
  • Session assistant content stores final canonical JSON; metadata stores mode, attempt and schema hash. Invalid candidates never enter the session message chain.
