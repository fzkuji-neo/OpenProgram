Framework comparison: OpenProgram and twelve references

This page compares complete frameworks: their product forms, strengths, weaknesses and missing capabilities. Six subsystem comparisons already cover sandboxing, agent collaboration, long-term memory, memory adoption, speaker identity and chat attachments. This page uses their conclusions without repeating their detail. Twelve dimensions each have a concise assessment and a diagram; detailed evidence stays in the subsystem documents.

00Three questionsConclusions

The investigation answers these three questions. The twelve-dimension matrix and missing-capability inventory provide the supporting evidence.

Strongest

Sessions are graphs, and code execution is recorded as nodes

Among the twelve references, no second implementation was confirmed to record the function call tree in conversation history. Model tool results and successfully persisted function calls with session DAG recording enabled, excluding expose=hidden, are recorded at the @agentic_function call level as code nodes in the session DAG. They share caller/predecessor edges with user and llm nodes and reside in the same session Git repository. Multiple heads can reference different history branches.

OpenClaw and pi-mono both support transcript branching. OpenClaw Control UI provides fork, rewind and branch; pi-mono JSONL records carry parentId and /tree switches branches. OpenProgram additionally shares a DAG across user, llm and code nodes, with code nodes representing both tool results and nested calls. Transcript branching and worktrees are independent: agent branches share the current working directory by default; only jobs explicitly bound to worktree_id isolate file changes.

context/git/dag.py · store/session/session_store.py · agentic_programming/function.py
Weakest

Standard local entry points exist; a stable remote-control contract is missing

OpenProgram supports bundled, dynamic community and custom providers, an MCP client, skills and plugins. External programs can invoke tools through an authenticated stdio MCP server and drive sessions through an ACP server. An OpenAI-compatible endpoint, stable versioned remote-control SDK, complete public headless event protocol and maintained IDE extension remain unconfirmed. Owner-authenticated WebSocket and Python library entry points are internal or embedded interfaces; they do not provide these external compatibility commitments.

For project instructions, OpenProgram and OpenClaw both store agent-level guidance in agent workspaces. OpenClaw provides migrate-claude and migrate-hermes. Codex desktop/CLI import can migrate Claude Code and Cursor setup and recent work. OpenProgram currently has no importer for external agent sessions, configuration or skills.

openprogram/mcp/server/server.py · openprogram/acp/server.py · apps/cli/python/openprogram_cli/_impl/commands/mcp.py · agent/management/workspace.py
Unexpected

Codex code mode: model-written code invokes tools

Instead of emitting tool calls, the model writes JavaScript that invokes tools in the current turn. In CodeModeOnly mode, the model-visible tools are limited to exec and wait. Four crates and a V8 runtime implement this feature, which the feature registry disables by default; examining only default behavior would miss it.

OpenProgram lets a model generate a workflow package, then execute a versioned Python workflow after static validation and atomic publication. Codex code mode instead generates JavaScript and invokes tools immediately within the current turn. OpenProgram currently has neither this per-turn code mode nor a model-visible tool set reduced to exec/wait as its two entry points.

codex-rs/features/src/lib.rs · code-mode / code-mode-host / code-mode-protocol / code-mode-runtime / v8-poc
Separate capability scope by use case: OpenProgram provides three core Python/TypeScript LSP tools: diagnostics, references and definition. It has no maintained IDE extension, formatter collection, tree-sitter code index or GitHub Action. These differences directly affect coding use cases. Channel breadth concerns the general harness: OpenClaw and Hermes expose considerably more integrations than OpenProgram’s four channels.

01What OpenProgram isCurrent state

A general-purpose Python agent harness. Installation provides the openprogram command and a persistent worker. TUI, Web, Electron desktop and four chat channels share process_user_turn through the dispatcher; the Python library enters through Agent.run or Runtime directly into agent_loop. Each session’s Git repository is the source of truth for its transcript. SQLite holds the usage ledger. Memory content is Markdown, with rebuildable in-memory BM25/embedding indexes for retrieval. Workflows can be Python functions decorated with @agentic_function; nested calls that meet recording conditions and persist successfully enter the same session DAG. The history/ JSON nodes support updates and deletion; context/commits/ is frozen per turn. Providers can be bundled, dynamic or custom. Web and WebSocket entry points enforce single-owner authentication through owner_auth, using a per-start token and profile-specific cookie. This is a single-user framework, not a multitenant service.

2.1 Four execution models

The four execution models can coexist: Codex and Claude Code support local processes, services and remote execution. Claude Code can teleport to cloud containers, Codex supports remote environments and cloud tasks, and OpenClaw pairs optional cloud workers with managed worktrees. OpenProgram has a persistent worker and Docker/SSH backends, but no hosted cloud execution service. Mechanisms to consider: OpenCode separates the local TUI and execution service through RPC. control-plane/move-session.ts can relocate a session and Git changes within a project to another absolute directory or worktree, but cannot move them to another machine or take over an active turn. OpenProgram already has a persistent worker, WebSocket clients and per-session Git storage. Cross-worker migration would still require a versioned migration protocol, target placement, authentication, active-turn semantics and failure recovery.

Theme 4 · Proactivity and testing
openclaw Automations + Heartbeat: Automations support cron, fixed intervals and one-time tasks, delivering results to chat channels or webhooks. Heartbeat runs a proactive main-session turn every 30 minutes by default and reports only noteworthy items. OpenProgram Scheduler persistently registers one-time, recurring and monitoring tasks, with signed execution, retries, recovery and a persistent worker. It runs agent prompts or controlled commands. It has no result-delivery protocol for chat channels or webhooks, and no default main-session heartbeat with importance filtering. Two independent scopes remain: a Scheduler result-delivery protocol, and a main-session heartbeat with frequency, quiet-period and filtering rules. Both require separate design approval.

openclaw Dreaming: background processing extracts entries above a score threshold from daily notes in memory/YYYY-MM-DD.md and promotes them to MEMORY.md. openclaw Nodes expose remote device capabilities as tools: macOS, iOS, watchOS and Android have native nodes. Branches are head pointers		 One graph, three node roles (user/llm/code), two edges (caller/predecessor). 04Target stateTarget

Three framework-level targets correspond to the three opening questions.

Complete the strongest capability

A session is portable, shareable and reproducible

A session is already a Git repository containing a complete graph. The target is to transfer that repository to another machine for continuation, publish a redacted version for others to inspect, and branch again from any node. All three operations use the same representation rather than three export formats.

Complete external control

Other programs can operate OpenProgram through stable contracts

MCP server and ACP already provide standard local entry points. The target additionally requires a stable versioned remote-control contract and external session/configuration import. These latter capabilities remain unapproved candidates.

Systematically identify missing capabilities

One capability registry and one reproducible execution record

Each capability has a registry entry recording its stage and default switch; every run can export a redacted complete trajectory. The registry makes supported behavior explicit, while trajectories make failures reproducible for others. Both are needed as complexity grows.
