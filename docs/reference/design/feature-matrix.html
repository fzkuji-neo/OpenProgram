Each cell records confirmed status in the specified snapshot, not end-to-end verification of every execution path.

00 Three questions to resolve before design Assessment

Three candidate groups to review first

Remaining Git workflows, recoverable-deletion boundaries, and external control protocols

First, six Git workflow items are now confirmed. Of ten items, OpenProgram confirms read-only commit-message generation, worktree creation from a PR number or GitHub URL, worktree-isolated execution, .worktreeinclude synchronization, shadow git, and diff security review. Unconfirmed items are a default product entry for commit/push/PR creation, PR or Issue comment triggers, AI authorship attribution, and non-git version control. Without usage and effort data, this page cannot establish usage priority or implementation cost.

Second, recoverable deletion currently covers common entry points in local agent subprocesses bound to a session/turn. PATH, PYTHONPATH, and NODE_OPTIONS cover common shell, Python, and Node deletion APIs; openprogram trash list/restore can list and restore recorded entries. Cron and background tasks without session/turn context receive no injection. Docker/SSH backends, absolute-path system commands, direct syscalls, find -delete and other bypasses are outside coverage. The list is not a complete deletion audit, and the mechanism is not a security sandbox.

Third, external control already includes ACP and an authenticated stdio MCP server.openprogram acp An editor-driven server implements ACP v1; openprogram mcp serve reuses tool registration and permission mapping. OpenAI-compatible endpoints, an official remote-control SDK, and inbound webhooks remain unconfirmed. Local FastAPI and WebSocket actions still carry no versioned external compatibility guarantee. Image generation is gated by provider availability and scores 0.5.

Existing SessionStore and branching do not imply an arbitrary /side entry point. Temporary side sessions change history visibility and first require persistence, cancellation, recovery, and cross-interface consistency semantics. This candidate still needs design approval.
Six Interfaces and diagnostics: first ensure keyboard/screen-reader usability, then assess shortcut remapping, Vim, code-aware /init and usage insights. Web/TUI already persist themes, and Web provides a standalone PWA manifest/install icons; openprogram diagnostics already creates redacted zip diagnostic bundles. Currently, /init synchronously creates three generic templates, preserves existing files, and reports created/skipped individually without analyzing code. Keybinding work first needs a cross-interface configuration model. Accessibility is a basic acceptance requirement. Minimum acceptance: major flows work with a keyboard; screen readers have semantic labels; settings persist with clear scope. Shortcut remapping, Vim, code-aware initialization, and usage insights each need separate scope definitions.
Two groups excluded from this sequence. Inline completion/chat, CodeLens, and status-bar actions require long-term native IDE-plugin maintenance. If an IDE only needs to invoke OpenProgram, openprogram acp already covers that need. Enterprise policy, silent audit reporting, credit purchases, and organization-wide enforced configuration assume multi-user governance/commercial billing absent from the current single-user local product scope. Reassess if users or deployment change rather than reusing this conclusion.
