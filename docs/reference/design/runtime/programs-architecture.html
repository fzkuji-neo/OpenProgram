Programs code structure

Place deterministic tools in tools/, complete capabilities requiring model reasoning or workflow orchestration in workflow/, and complete products in packages/. Keep only the basic call primitives llm() and agent().

Status: current designScope: source, registration, Programs UI, packaging

1. Canonical directory contract

openprogram/
├── agentic_programming/
│   ├── llm.py                  # single model-call primitive
│   └── agent.py                # Agent-loop primitive with tool calls
└── programs/
    ├── tools/                  # deterministic, directly callable tools
    │   ├── files/  web/  code/  planning/  ...
    ├── workflow/               # all model reasoning, Agent orchestration, and composite capabilities
    │   ├── auto_workflow.py    # complete single-file Workflow; no empty same-name directory
    │   ├── goal/               # single Goal Workflow and session Goal mechanism
    │   │   ├── __init__.py
    │   │   ├── goal.py         # public entry goal()
    │   │   ├── command.py      # /goal command adapter
    │   │   ├── judge.py        # completion-condition evaluation
    │   │   ├── refinement.py   # goal specification and acceptance checklist
    │   │   ├── loop.py         # state transitions, retries, and stop rules of the single loop
    │   │   ├── state.py        # persistent state and events of the same GoalRun
    │   │   └── notices.py      # session status notifications
    │   ├── browser/  document/  research/  ...
    ├── packages/               # independent packages providing callable capabilities
    ├── _registry.py            # shared registration and discovery
    └── _programs.py            # Application provenance and installation metadata
Remove programs/functions/, programs/functions/agentic/, programs/workflows/ or agentic_programming/goal.py. Each capability has one authoritative implementation and one public import path.

2. Three Program categories

programs/tools/

Tools

Ordinary code determines outputs from inputs, without model inference or an Agent loop. Register with @function for reuse by Agents, Workflows, and Applications.

Portable package sources

Project-local Programs record locations as relative paths scoped by programs. An external installation binding connects the installed runtime to the source checkout. Relative paths do not use the chat working directory. Only exact authorized package names participate in Python resolution; the entire external directory is not added to import scope. Migration, rejection conditions, and publishing rules follow the Workflow package contract.

programs/workflow/

Workflow

Any capability calling llm(), agent(), other Workflows, or containing multi-stage state and completion checks belongs here. Single-model-call capabilities are also Workflows; there is no separate Agentic Function directory.

programs/packages/

Packages

A package is an installation unit for callable capabilities, with its own dependencies and release boundary; it can provide multiple Tools or Workflows. Software Applications use separate management pages, declarations, and registration directories and call public Program capabilities; they are not part of this source classification. Legacy applications/ package locations retain read compatibility.

4. Goal has one execution function

Single Workflow
from openprogram.programs.workflow.goal import goal is the sole execution function, owning GoalRun initialization, spec refinement, Agent rounds, completion evaluation, user questions, stop rules, state writes, and terminal states. No second Goal loop may remain in the dispatcher, command adapter, or another module.
Programs form
The form directly calls goal(prompt, condition, context_mode="isolated", ...). Run records may belong to the current session, but goal() model context does not read pre-call chat history; it reads only form parameters and calls already produced in this GoalRun.
Chat command
/goal <condition> is only a session adapter for the same Workflow: parse the command, then call goal(prompt=condition, condition=condition, context_mode="session", ...).context_mode="session" reads the current session view at execution start; otherwise it uses the same state machine as the form.
State and control
Both entry points produce identical GoalState, progress events, GoalChip, questions, cancellation, clear/status, and terminal states./goal clear controls the GoalRun associated with the current session, without starting or maintaining a second Goal object type.
Internal modules
judge.py, refinement.py, state.py, loop.py serve only this function.command.py only parses set/status/clear and constructs one goal() call. It does not create state, refine goals, or run continuation.
No duplication
Do not retain continue_goal_turns() and goal() as two round controllers. Do not copy spec/checklist from session Goal to isolated Goal or change default rounds, need_user, or terminal semantics based on entry point.
Public pathOnly permitted differenceMust remain identical
Programs → Use → Goal formcontext_mode="isolated"GoalState, refinement, judge, loop, round budget, questions, cancellation, events, terminal states, and return values
Chat composer → /goalcontext_mode="session"
Result ownership and model context are separate fields: form runs may write DAG/runtime cards into the current session, but must still use render_range.callers=0 to isolate pre-call history. Session commands restore current chat evidence through explicit session-context input.

5. Choosing files and directories

FormWhen to useExample
Single .pyOne public entry and a few local helpers; the file can be read independently.workflow/auto_workflow.py
Same-name packageMultiple modules with distinct responsibilities, resource files, or session adapters.workflow/goal/, workflow/browser/
Internal directoryShared implementation serving only adjacent Workflows; its name begins with _ and it does not become a Programs UI node.workflow/_runtime/

Do not create same-name folders for every Workflow merely for uniformity. File count and responsibility boundaries determine package splitting.

7. Registration and Programs UI

Shared registration
_registry.py loads public entries from tools/ and workflow/; Applications use provenance records and installation contracts.
Top-level UI
Show only Tools, Workflow, Applications, without historical levels such as Functions, Vanilla, or Agentic Function.
Entity recognition
A registered entry is runnable, so the Programs sidebar shows Use. Expanding a same-name package lists responsibility modules from the actual directory (such as goal/command.py). These files can be opened to inspect call relationships but are not registered as additional Programs and have no Use action.__init__.py and _ internal directories still do not become nodes.
Canonical path
After migration, only new imports are supported. Old paths fail directly, with no aliases or dual scanning of old and new directories.
Stable contract
Moving source does not change public names, parameter Schemas, permissions, DAG semantics, or session state formats.
