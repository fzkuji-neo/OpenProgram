Agent Programs configuration: separate from the entity catalog

This page details Programs within the complete Agent configuration framework. Programs answers “which callable entities exist in the system”; Agents answers “which entities a particular agent may discover and call.” Pages and data ownership are separate, while actual calls use the same AgentTool registry, resolver, and executor.

1. Page and data boundaries

Programs · entity catalog

Manage entities

Functions (Vanilla / Agentic), Workflows, and Applications are callable system objects.

  • Source, exports, schemas, Git status, and tests
  • Static Calls / Used by relationships
  • Install, edit, favorite, run, and delete
Agents · configuration

Manage usage policies

Agent configuration determines models, instructions, Skills, MCP, and accessible Programs.

  • Default access mode and reusable Access presets
  • Allowed, excluded, and globally unavailable entries
  • First-turn context and on-demand discovery policies
Do not copy entities: Agent configuration stores only tool-access intent or tool-name references, never copies of Program schemas, descriptions, Python source, or Workflow repositories. After a Program is deleted or disabled, every agent receives the same result on the next resolution.

2. Agents configuration page prototype

The main page provides only agent selection, configuration tabs, access mode, and a current-scope summary. It reuses existing Web management-page and Settings structure rather than creating an agent-specific window. The global header contains only page-level actions; configuration tabs appear below the selected agent’s detail header. Typography uses the Web-wide --fs-base/--fs-sm hierarchy rather than copying 8–12px local sizes from a scaled prototype. The tool catalog opens on demand as a selector, not as persistent agent-detail content. The shared management-page header provides agent creation.

5. Acceptance contract

  • The Programs page does not show User Profile, Access presets, agent allow/deny state, or session overrides.
  • The Agents page can create and select agents and save their Tools & Programs policies; Program entities are not copied into agent configuration.
  • The agent-detail main page uses three vertical collapsible sections: Functions, Workflows, and Applications. Collapsed sections show counts; expanded sections show effective entries and structure previews.
  • Expanding Workflows on the main page does not enter editing mode. Only Edit access opens the authorization selector with search, status filtering, and individual selection.
  • The Workflow selector has type-navigation, Workflow-list, and inspector columns. Selecting another Workflow updates entry, input/output, direct composition, dependencies, and verification status in the inspector.
  • Expandable composition-tree nodes use fixed circular controls on the left. Expanding does not move the control or row; the subtree appears with a 200ms container animation and continuous hierarchy lines.
  • Agent configuration expands at most two levels in place. Recursive Calls / Used by graphs open in Programs; actual execution instances open in the session DAG.
  • Connected Services appear only in MCP configuration, not again as Program sources.
  • Closing the selector preserves the main page’s scroll position; the page does not grow with the Program count.
  • The default chat agent does not place all Workflow names, descriptions, schemas, or source in first-turn context.
  • After selecting an Access preset, tool_search, explicit-name loading, and actual invocation are all constrained by the same allowed set.
  • The session Tools menu defaults to “Use Agent configuration”; temporary changes do not write back to the agent.
  • Globally disabling or deleting a Program gives every agent the same unavailable result next turn without configuration migration.
  • Functions, Workflows, and Applications all ultimately enter the existing shared AgentTool execution path.

6. Implementation scope and verification

This change directly reuses AgentSpec, existing Tool Profile storage, resolve_tools() and the AgentTool executor. The page layer directly reuses ManagePageHeader, ManageRow, shared columns, and Settings detail containers. Additions are limited to agent-specific forms and on-demand Programs / Skills / MCP selectors, with no second page-window or execution model.
