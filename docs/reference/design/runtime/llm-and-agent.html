Refactor Plan · Design Only

Unify Agent execution semantics and refactor Self Programming Workflow

Programs use only openprogram.agentic_programming.agent(). Independent sessions, background Jobs and sub-agent branches remain owned by internal adapters, but both paths must enter the same Agent loop instead of maintaining separate planning, tool-call, model-override and error semantics.

Goal: one public Agent APIScope: Runtime / Workflow / DAG / Chat UIMigration: staged and reversibleStatus: Workflow orchestration migrated · App/DAG acceptance pending

1. Conclusions and boundaries

This refactoring adds no third Agent abstraction and does not wrap the session Job API in another public function. Public semantics remain in agent(); persistence and branching belong to the execution environment, not the Workflow authoring API.

Sole public entry

agent() is the sole autonomous tool-loop entry inside Workflows and Applications.

Ordinary Agentic Functions do not call it and permit only one llm(); the full classification contract is in Programming model and categories. Within a Workflow, agent() runs in the current Runtime and forms parent-child Call relationships.

Internal session adapter

run_agent_turn() serves only Chat, CLI, background Jobs and genuinely independent sub-agents. It creates session branches, claims workers, restores Jobs and moves session heads; Programs must not import it directly.

Included in this refactoringUnified Agent loops, Workflow selection/creation/repair, DAG ownership, structured output, error propagation, migration tests and UI display contracts.
Not introduced by this refactoringA new Workflow DSL, graph execution engine, second Agent profile system, extra persistence database or display of hidden chain-of-thought.

3. Target architecture: two adapter entries, one execution core

Differences exist only in lifecycle before/after execution: Programs reuse the current Runtime; sessions create durable Jobs first. Model loops, tool selection and error semantics remain identical.

4. Fixed hierarchy of four execution primitives

Workflow is the highest layer and may directly choose llm(), agent(), goal() or ordinary Python Functions.goal() builds on agent(); agent() builds on llm(). These are dependencies; a Workflow need not traverse every layer.

5. Target Self Programming Workflow process

Public behavior is split into search_workflows, create_workflow, revise_workflow and the user-triggered entry auto_workflow(task). Chat Agents directly call the first three capabilities or a specific Workflow as needed; only a manually requested complete flow enters auto_workflow. This section describes only their use of public agent(); the complete contract is defined by Discovery, creation and automatic execution.

8. Staged migration plan

Each stage first adds tests reproducing the current gap, then modifies the corresponding layer. Never change public API, session lifecycle, Workflow layout and chat visual styles in one stage.

01

Freeze execution contracts

  • Record current agent(), run_agent_turn() and Runtime call graphs.
  • Add architecture tests: Programs must not import agent.sub_agent_run.
  • Add real registered-schema tests fixing public parameters of the four Workflow management functions.
Gate: add only failing tests and documentation; no behavior change.
02

Complete public agent()

  • Pass through response_format, content blocks, description and Agent profile.
  • Reuse profile/tool resolvers without a new configuration format.
  • Add an Agent wrapper Call for stable ownership of LLM/tool nodes.
Gate: public-agent unit tests, DAG-caller tests and provider-fallback tests.
03

Separate Workflow public behaviors

  • search_workflows remains deterministic and read-only.
  • auto_workflow selection Agent chooses reuse/create only; no file writes or automatic revision.
  • Authoring, writing and pre-publication validation belong to create_workflow and revise_workflow.
Gate: integration tests for four independent search/create/revise/auto public entries.
04

Restrict the session adapter

  • run_agent_turn() remains internal, supporting branches, Jobs, recovery and archive.
  • Confirm dispatcher ultimately uses the same Agent-loop core as public agent.
  • Remove duplicate model defaults, tool resolution and error normalization.
Gate: background recovery, cancellation, branch/head and spawn-caller tests.
05

Migrate all Programs

  • Scan openprogram/programs/ for internal Agent API and direct-loop calls.
  • Workflows and Applications consistently use public agent(); ordinary Agentic Functions permit only one llm().
  • Retain the vanilla sub-agent tool as the product entry for the session adapter.
Gate: static dependency checks + Programs catalog/graph regressions.
06

DAG and chat display

  • Backend events add execution_kind, label, caller, iteration and artifact metadata.
  • Frontend renders the same Runtime hierarchy without inferring a separate structure.
  • Conclusion, footer and collapse behavior reuse existing shared components.
Gate: mapper, RuntimeBlock, reload and actual-App DOM acceptance.
07

Compatibility cleanup and release

  • Read-only recovery for old runs; prohibit legacy SINGLE for new runs.
  • Delete unused planner helpers and duplicate test fixtures.
  • Update design navigation, API documentation and Programs dependency graphs.
Gate: wheel packages current web/out; default 18100 App/Web/TUI share the same source.
08

Controlled rollout

  • Run focused component tests first, then required complete suites.
  • Accept one real reuse, create, repair and cancel session each.
  • Retain the old recovery reader for one compatibility period; never write the old format again.
Gate: record all acceptance evidence in implementation status, not as retroactive design assumptions.

10. Acceptance matrix

API and registration

  • Registry contains only search_workflows, create_workflow, revise_workflow and auto_workflow; category directories are not registered.
  • agent() has stable model/tools/profile override order.
  • Structured output validates with providers supporting and lacking native schemas.

Call structure

  • Selection belongs to auto_workflow; authoring and pre-publication retries belong to create_workflow or revise_workflow.
  • All Programs called by a Workflow appear in the DAG.
  • Direct/manual Workflows are not incorrectly attached to the prior assistant through predecessor.

Lifecycle

  • Parent cancellation terminates Agent, LLM and tools.
  • Session Job restart recovers only the session path.
  • New runs never generate SINGLE; old runs resume or return an explicit incompatibility error.

UI

  • Collapsed state shows Workflow title, Conclusion and footer.
  • Expand progressively, not all children at once.
  • App/Web/TUI read the same default profile and worker at 18100.

11. Framework comparison and decisions

Compare only capabilities directly relevant to this architectural decision. OpenProgram introduces no new third-party orchestration runtime.

ReferenceAdoptedNot adopted
OpenAI Agents SDK · Running agentsRunner owns the model/tool loop of one logical turn; max turns, sessions and hooks are separate.Do not use Runner as a second OpenProgram runtime; retain current Runtime/dispatcher.
OpenAI Agents SDK · ToolsPython function tools and agent-as-tool are explicit calls; parents can observe child execution.Do not implicitly convert Workflows into handoffs; they remain Python packages.
OpenAI Agents SDK · OrchestrationDistinguish a manager calling a child Agent from handing control to another Agent.Inside a Program, agent() does not automatically create session branches; only product-level sub-agent actions switch sessions.
LangGraph · Workflows and agentsWorkflows are predefined code paths; Agents dynamically choose tools locally.No new graph DSL; static call graphs derive from Python imports and @agentic_function .
LangGraph · PersistencePersistence, threads, checkpoints and interruption recovery should be explicit lifecycle capabilities.Do not force every in-Program Agent into a persistent thread; only the session adapter uses durable Jobs.
