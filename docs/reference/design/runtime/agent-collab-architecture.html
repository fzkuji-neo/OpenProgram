Agent collaboration: tool surface

All tools for one agent to interact with others, organized into four domains: planning, execution, entities, and communication. This page explains each tool, which sessions may operate which tasks, and how two budgets limit a chain. Design document: docs/reference/design/runtime/agent-collaboration.md. For eight reference implementations compared across the same eight dimensions, see Agent collaboration: eight implementations compared.

01Four-domain vocabulary

Each domain has its own noun. Distinguishing these nouns makes tool names straightforward: each domain’s tools operate its own noun.

Planning

todo

A written plan

A manually maintained plan list. It records intentions only, corresponds to nothing currently running, and does not run an agent when edited.

todo_createtodo_updatetodo_list
Execution

task

A running task

A dispatched running task: a task_id, a state, and a result. It is an entry in the task list, not the entity executing it.

list_taskstask_outputtask_stop
Entities

agent

The entity executing a task

Create one, assign work to an existing one, list all agents, or archive finished agents. An agent is a branch in the session DAG.

agentlist_agentsarchive_agent
Communication

message

Send messages and read history

Send a message without creating a task record, or read any branch’s full transcript without triggering execution.

send_messageread_conversation
The two most easily confused pairs:Todo and task both describe work, but one is a written plan and the other a running execution record. Therefore plan-list tools use the todo_* prefix, while execution tools use list_tasks. Task and agent also differ: stopping a task stops only that run, while the agent remains in the agent list; archiving the agent uses archive_agent.

02Four actions an agent can take

Create an agent, assign a task, send a message, or query. The first two create a task_id and enter it in the task list; the third does not, and the fourth is read-only.

How to read: Four horizontal paths start at “Me” on the left.CreateandAssignboth useagent; the only difference is whether to= is present: without to=, create a new branch; with to=, assign the task to the existing branch. Both record a task and return a task_id. Messageusessend_message; it ends on delivery and creates no task_id.Queryuses four read-only tools.
Colors: green = entity creation · orange = managed tasks and task records · blue = messages · teal = read-only. Dashed lines = asynchronous return.

03Messages versus tasks: messages create no task record; tasks are trackable and cancellable

Both deliver content to another branch for a turn, but messages and tasks offer different guarantees. The receipt header the recipient sees first states the difference.

GuaranteeMessage send_messageTask agent() / agent(to=)
Who may initiateAny agent, to any unarchived branchAny agent as well, but the resulting task_id may be operated only by its owner
Has a task_idNo; returns only a delivery_id acknowledging deliveryYestask_id, recorded in the task list and queryable with list_tasks
Must the recipient replyNo. The receipt header explicitly says “do not reply if there is nothing to add”Yes. The turn’s final response is the task result
Can it be cancelledNo. A delivered message cannot be withdrawntask_stop; queued tasks are withdrawn and running tasks have that turn stopped
Does cancellation cascadeNot applicableYes: stopping a task stops all tasks it spawned
Can you operate someone else’s taskNot applicable; sending a message has no subsequent operationNo. task_output/task_stop enforce ownership
Is concurrent dispatch safeYes. No task record is created; the worst outcome is no replyYes, with records: a busy target queues the task and is not interrupted
Archiving an agent itself is separate; any session may do it: archiving neither interrupts running work nor deletes data, so archive_agentdoes not performtask_stop-style ownership checks. See the next section.

04Two budgets: two counters with separate responsibilities

A chain includes all calls arising from one user turn. Message count increases at each hop, including returned replies; generation depth increases only when a new agent is created. Reading results consumes messages but no generation depth, allowing one batch of work, result collection, then another batch.

Both support 0, meaning that limit is disabled and blocks nothing.

# Change from the CLI; effective immediately
openprogram config set agent.max_spawn_depth 1   # Default: the main agent creates workers, and workers complete their own work
openprogram config set agent.max_spawn_depth 2   # Workers may create one more generation; the third generation is rejected
openprogram config set agent.max_spawn_depth 0   # Unlimited depth

openprogram config set agent.max_messages 8      # Default: at most 8 hops per chain
openprogram config set agent.max_messages 0      # Unlimited messages; agents may keep exchanging messages

openprogram config set agent.max_spawn_fanout 8  # Default: at most 8 agents created per turn
openprogram config set agent.max_spawn_fanout 0  # Unlimited agents created in one turn
The Settings Agent group contains the same numeric fields: Max spawn depth, Max messages per chain, and Max spawn fan-out. Changes apply immediately and persist in the ~/.openprogram/config.json file’s agent section. With all three set to 0, the remaining controls are the concurrency limit (OPENPROGRAM_JOB_WORKERS, default 4), the 50-tool-call limit per turn, and manual user cancellation.
Fan-out is separate from the two chain counters above.Spawning passes counters to the child without changing the parent’s copy, so chain counters cannot count siblings. Fan-out is counted separately per (session, turn), rejecting calls without removing tools: the tool list is frozen at the start of the turn, while this budget is consumed during it.
The two counters move differently on the return hop.Message count continues from the child, ensuring A↔B exchanges eventually stop; generation depth returns to the dispatcher’s value because reading results is not creation, allowing another batch after the first completes.
One rule is independent of budgets: self-messaging is always rejected.to=Addressing the initiator’s current branch creates a direct cycle and is rejected immediately.

05Archiving: stop receiving deliveries, preserve history

Branches remain permanently in the session DAG for forks, replay, and transcript reading. Archiving does not delete a branch; it writes an archived marker on the branch.

06Typical scenarios

Three common workflows using different combinations of the same tools.

Scenario 1 · dispatch a batch of tasks

There are five independent tasks. Write the plan, dispatch each item, then update the plan.

01 Plan
todo_create(subject=…)
Write five entries for the five tasks.blocked_byMark dependencies.
02 Assign
agent(prompt, description, run_in_background=true)
Dispatch one at a time. Background mode immediately returns a task_id without occupying my turn.
03 Monitor
list_tasks()
Five task_ids, five states. To retrieve results use task_output; to cancel use task_stop.
04 Collect
Results return automatically
Polling is optional. Each completed result is appended to my session for my next turn.
05 Update the plan
todo_update(todo_id, status="completed")
Keep plan state consistent with actual execution.

Scenario 2 · find an existing agent

An agent has already done part of the work, so no new agent needs to start from scratch. Check the agent list, then choose a message or a managed task.

01 List agents
list_agents(scope="all")
Grouped by session. Each branch provides a name, a directly usable to="SID:HEAD", turn count, approximate word count, and a tail preview.
02a Message
send_message(to="name", message=…)
Ask a question, notify, or share a conclusion. Creates no task_id; the recipient may choose not to reply.
02b Assign
agent(to="name", prompt=…)
The target must do the work and return a result. Creates a task_id, is cancellable, and guarantees a returned result.
03 Queue if busy
Enters the inbox when the target is running
Neither interrupts nor drops the work. It runs after the current turn finishes.

Scenario 3 · inspect an old conversation

Find out how previous work was completed without running an agent or loading the entire history into context.

01 Get the address
list_agents(scope="all")
Use the same agent list. Turn and word counts help estimate the size.
02 Read only the end
read_conversation(session_id="SID:HEAD", start_turn=-10)
Negative indices count from the end; -10 means the last ten turns.list_agentsThe full SID:HEAD string it provides is also accepted when pasted.
03 Include tool details or not
include_function_calls=false
By default, include the tools called each turn, their arguments, and results. Disable this to see only conversation text.
04 Limit size
max_chars=60000
Drop later turns if the limit is exceeded. Archived branches remain readable, and reading never triggers execution.

07Mapping to Claude Code

Matching names are intentional. Differences consist of one naming conflict and three additional tools.

HereClaude CodeRelationship
agentSame nameSame meaning. The only entry point for creating a new agent; to= assignment is our extension
list_agentsSame nameSame meaning. Visibility of the other agent is required for communication
send_messageSame nameSame meaning. Send a cross-branch message
task_outputTaskOutputSame parameter shape: block defaults to true, timeout is in milliseconds, defaults to 30000, maximum 600000
task_stopSame nameSame meaning. We additionally enforce ownership and cascading cancellation
todo_create / todo_update / todo_listTaskList Same concept, different name. Claude Code’s TaskList is a plan list, while our list_tasks has the same name but a different meaning, so our plan tools consistently use the todo_* prefix and reserve list_tasks for tasks that are actually running
list_tasksNoneAdditional tool: lets the model query running background tasks without continuously retaining the spawn-time task_id
archive_agentNoneAdditional tool: without archiving, the agent list accumulates long-finished workers
read_conversationNoneAdditional tool: renders a branch as a readable transcript with turn ranges and size limits, without reading raw record files
Closing statement: Four nouns define four domains. agent handles creation and assignment; messages create no task records and may be sent by any agent; tasks are trackable and cancellable and may be operated only by their dispatcher; two budgets limit a chain; archiving stops only future delivery.
