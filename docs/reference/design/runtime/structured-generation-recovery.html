Output parameters

Workflow execution has no default aggregate token quota. Explicit user limits remain authoritative. Context reservation is a planning estimate, not the provider output cap. Default requests use the model output capacity constrained by available context; explicit limits are validated without silent reduction. Unknown model limits retain adapter handling. Normal model reasoning does not count as a timeout merely because it is long.

Default recovery allows two extra attempts. Explicit zero disables repair. Each retry reports a reason and attempt identity through existing structured-output and execution-stream events. A regeneration instruction requests a complete value and excludes the invalid partial candidate. Completed tool results remain in context. At model capacity, workflow-specific decomposition is explicit rather than guessed by the generic runtime.

Persistence and observable behavior

Actual requests, effective parameters, stop reasons, available usage, and retries must be distinguishable. Unknown usage stays unknown. Error paths retain metadata without requiring retention of reasoning or sensitive partial text. Paused is distinct from actively retrying. Existing durable execution and effect records own restart and side-effect reconciliation; no parallel scheduler is introduced.

Report workflow stages preserve resolved scope, supplied materials, retrieved evidence, and validated draft results. A text-only resume_task is a restart request, not a durable continuation. Acceptance observes pages and prepares local drafts without sending reports.

EOF recovery and terminal state

A structured stream that ends without a terminal event consumes the same recovery allowance as length truncation. Partial content is never submitted or executed. Exhausted structured recovery is paused before its error reaches Runtime persistence. Cancellation is cancelled. Normal return alone is not evidence of successful generation; canonical execution status remains authoritative. Public-entry acceptance covers empty EOF, partial EOF, mixed validation failures, disabled recovery, cancellation and completed-tool non-replay.

Browser Workflow reliability

Browser stages expose only the actual web_use tool, using its command-based schema. Inspection requires real browser observations; a textual JSON example is not a tool receipt. Prompts describe list_pages, observe and act according to the current tool contract. Missing tools, login and permission failures remain explicit failures; they never authorize another transport or a write.

A workflow that starts with an origin window but no bound Page preserves that origin context when it calls web_use(command="list_pages"). In a subprocess, Page inventory then goes through the parent webtab bridge, which accepts only the originating window and bindings authorized for that execution. The child keeps its own registry for Page tokens and consumes those tokens in the same process; a token is not transferred between parent and child registries. If there is no authorized origin context, inventory does not fall back to all desktop windows.

The Desktop bridge registers its exact window identifier immediately on startup and reconnection, before awaiting retained-view or resource restoration. Restoration completion may repeat the idempotent registration. A pending restoration must not prevent a Workflow from opening its first page. Registration never selects another window or broadens ownership.

desktop_unavailable means that the worker cannot use a registered Desktop WebTab at that moment. It is separate from a model response that imitates a tool call and separate from the browser page's network or document content. The installed default service is accepted only after the public /api/web-use boundary lists a page and observes it, returning a title and observation identifiers without submitting or saving an external record.
