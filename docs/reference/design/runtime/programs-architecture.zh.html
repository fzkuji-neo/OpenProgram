确定性工具放在 tools/，所有需要模型推理或流程编排的完整能力放在 workflow/，完整产品放在 packages/。基础调用原语只保留 llm() 与 agent()。

2. 三类 Program

programs/tools/

工具

输入到输出由普通代码决定，不发起模型推理，不启动 Agent loop。使用 @function 注册，可被 Agent、Workflow 和 Application 复用。

可迁移包来源

项目内 Program 使用带 programs 范围的相对路径记录位置；一个外部安装绑定负责连接已安装 runtime 与源码 checkout。相对路径不使用聊天的工作目录。只有已授权的确切包名参与 Python 解析，不扩展整个外部目录的 import 范围。迁移、拒绝条件与发布规范以 Workflow 包合同 为准。

programs/workflow/

工作流

凡是调用模型、调用其他 Workflow，或包含多阶段状态与完成判定的能力，都归入这里。模型调用通过模块顶层的角色（Agent 实例）进行；单次模型调用能力也属于 Workflow。用户 Workflow 使用同样的形式，放在 ~/.openprogram/workflows/，见 Workflow。

可迁移包来源

项目内 Program 使用带 programs 范围的相对路径记录位置；一个外部安装绑定负责连接已安装 runtime 与源码 checkout。相对路径不使用聊天的工作目录。只有已授权的确切包名参与 Python 解析，不扩展整个外部目录的 import 范围。迁移、拒绝条件与发布规范以 Workflow 包合同 为准。

programs/packages/

包

程序包是可调用能力的安装单位，包含自己的依赖和发布边界，可提供多个 Tool 或 Workflow。软件 Application 使用独立管理页、声明和注册目录，调用公开 Program 能力；它不属于此源码分类。旧 applications/ 程序包位置保留兼容读取。

可迁移包来源

项目内 Program 使用带 programs 范围的相对路径记录位置；一个外部安装绑定负责连接已安装 runtime 与源码 checkout。相对路径不使用聊天的工作目录。只有已授权的确切包名参与 Python 解析，不扩展整个外部目录的 import 范围。迁移、拒绝条件与发布规范以 Workflow 包合同 为准。

4. Goal 以普通聊天轮次运行

唯一机制
Goal 是 programs/workflow/goal/ 中的会话状态。每次聊天成功结束后，由 chat.py 决定是否为 active Goal 发起下一轮普通聊天。不存在独立的 Goal 循环、judge Workflow 或嵌套工作 agent。
Programs 表单
goal(prompt) 只接收目标，在当前会话保存聊天 Goal，路由通过与 /goal 相同的控制启动第一轮。表单没有轮数、角色、模型或上下文参数。
聊天命令与 agent 工具
/goal <目标> 和 agent 的 create_goal 工具创建同一种聊天 Goal。goal Program 不作为工具提供给 agent。
完成
update_goal(status="complete") 或 todo 计划全部完成只提交完成候选。verification.py 运行一次独立的只读验收轮次，通过后 Goal 才变为 achieved。
上限
Goal 不限制轮数。连续两个自动轮次没有调用工具时，Goal 以“无进展”停下。可选的 token、执行时间和费用上限是仅有的预算。

5. 文件与目录的选择

形态使用条件示例
单个 .py一个公开入口和少量局部 helper，文件可以独立阅读。小型内置 workflow/<name>.py
同名包存在多个明确职责模块、资源文件或会话适配。workflow/goal/、workflow/browser/
内部目录只服务于相邻 Workflow 的共享实现，以 _ 开头，不成为 Programs UI 节点。workflow/_runtime/

不为形式统一而给每个 Workflow 创建同名文件夹。文件数量与职责边界决定是否拆包。

7. 注册与 Programs UI

统一注册
_registry.py 从 tools/ 和 workflow/ 加载公开入口；Application 使用来源记录与安装合同。
UI 顶层
只显示 Tools、Workflow、Applications，不再显示 Functions、Vanilla、Agentic Function 等历史层级。
实体识别
注册入口是可运行实体，Programs 侧栏对它显示 Use。同名包展开后按真实目录列出职责模块（如 goal/command.py）；这些文件可以打开查看调用关系，但不注册为第二个 Program，没有 Use。__init__.py 和 _ 内部目录仍不成为节点。
唯一路径
迁移后只支持新 import。旧路径直接失败，不设置 alias，不同时扫描新旧目录。
稳定合同
移动源码不改变公开名称、参数 Schema、权限、DAG 语义和会话状态格式。

工具参数的动态 mapping

工具的 canonical schema 区分调用时才确定键名的 mapping 与声明固定字段的对象。公开 program.args 接受已注册程序合法的关键字参数，包括 task。匿名 object mapping 与 Python dict/Mapping 注解保留开放键名及已声明的值类型。含 properties 的对象，包括显式空字段集合，保留固定字段限制。显式 additionalProperties: false 不会被打开；nullable mapping 保留原有 null 语义。本次不额外关闭既有隐式开放的顶层参数对象。

Canonical 对象本地验证Provider 工具模式
匿名或 typed mapping接受合法动态键，验证 object 与已声明的值类型保留 mapping schema，使用非 strict 工具模式
声明固定字段或显式关闭对象保留必填字段、类型与额外字段拒绝支持时保留原 strict 模式
两类工具同时出现在请求中每次调用按各自 canonical schema 验证逐工具选择模式，不对整个请求关闭 strict 验证

共享 provider schema adapter 不得把开放 mapping 转成只能为空的关闭对象。OpenAI function calling 要求 strict 模式使用关闭对象，并说明 Responses 通过显式 strict: false 保留非 strict 行为。因此动态 mapping 工具在 Responses、Codex 与 Chat Completions 中显式使用该标志；可兼容的固定字段工具继续 strict。Anthropic strict tool use 同样逐工具启用 strict 验证；mapping 工具保留普通 input schema，不设置 strict 标志。原 provider 可用性、认证、请求级能力开关和其他 schema dialect 不变。

验收在自有 session 中调用真实公开 schema、生产本地 validator 和注册程序 consumer。合法 task 参数到达 consumer；未知程序和 child 不支持的关键字保留现有错误，mapping 的错误类型或值仍无效。生产 provider payload 保留动态 mapping，同时关闭对象的 companion 工具继续 strict。固定 execute_code schema 保持 strict，不给它新增动态参数。测试包括固定对象额外键拒绝、nullable 与 typed nested mapping、不修改输入、受影响 provider/program 测试与 repository contracts。现有 live session、App、worker 和用户 state 不参与受控测试。

Wiki 修改元数据

公开 Wiki ingest 报告实际修改和新建的内容页，包括新目录中的页面以及含中文、空格或引号的路径。修改发现请求逐项列出未跟踪文件，使用 NUL 分隔的 Git porcelain 记录，保留准确路径，不解码展示引号或按箭头字符串拆分文件名。重命名记录消费配对的原路径，并保留目的路径。内容页后缀、目录索引排除、文件存在与 Git-ignore 规则保持不变；不修改无关的链接、页面、模板、生成、提交或索引行为。

验收通过已注册 ingest 入口创建目录内新页，验证 slot、实际 Git 提交及可搜索索引，并核对交给既有 conclusion 步骤的页面和目录元数据不为零。自有 Git 案例验证中文、特殊路径、重命名、忽略文件及排除目录索引。原 dirty ops 文件保存在独立输入基线提交中。路径发现及索引刷新修复已通过独立规格和质量审查，并导入本地包。组合源码与已安装界面验收分别记录。
