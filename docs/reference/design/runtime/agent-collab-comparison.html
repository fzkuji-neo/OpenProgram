Agent collaboration: eight implementations compared

Ask eight reference implementations the same question: how does one agent delegate to another, and can it still control that work afterward? Compare eight dimensions across all eight systems, explicitly marking absent features. Our own mechanism is described inAgent collaboration: tool surface; the design specification isagent-collaboration.md.

Return delivery rebinds the completed task's counter rather than incrementing it: one round trip costs 1, permitting eight round trips. Generation depth is separate, increasing only on creation and restoring the dispatcher's value on return. Reading results is not creation, so coordinators can dispatch another batch afterward

Add a per-turn fan-out limit

Three settled-design gaps remaining in code, verified individually against code: truncate oversized results at both ends and save full text to a file (agent-collaboration.md §5.6) is absent from return delivery; visibility metadata excluding internal branches from session pickers (§5.9) is absent beyond current archive fields; session cancellation clearing the inbox (§5.3) is connected only to the Web entry, not CLI stop
Closing statement: child spawning is common, generally in-process with a low depth limit. Direct communication distinguishes four systems. Loop prevention varies from eight mechanisms to none. We use more loop controls than most and uniquely remove tools according to remaining allowance, deliberately binary to preserve prompt caching. This comparison informed our values: retain depth 1 and message budget 8, add per-turn fan-out 8, and omit steering rate limits and child hard timeouts after inspecting their actual purposes. Each rationale is recorded beside its constant.
