整个会话运行时的重启恢复与 Goal 设计

设计问题：App 或 worker 重启后，如何自动继续原本在执行的会话与 Goal，恢复子任务、审批、上下文和用量，同时不重复未知写入、不恢复用户主动停止的工作。

参照状态恢复验收费用界面实施实现状态

面向框架开发与产品验收。本文定义目标方案；实现状态集中在文末。范围覆盖 Web、TUI、ACP、后台 Job 和已获授权的子任务；Goal 使用同一聊天执行层。不复制另一套执行引擎，不增加通用调度框架，不承诺任意外部操作恰好执行一次。

已核实的现状 · 自动恢复合同 · 全状态恢复矩阵 · 故障验收矩阵

核心合同：恢复会话不等于重试工具。旧轮次可以结束为 interrupted，旧操作仍保持 outcome_unknown；新轮次先检查现实状态。Goal、Todo、聊天记录和已发生用量均保留。
  1. 1. 保存目标原目标、完成条件、权限范围和显式预算。
  2. 2. 普通聊天工作agent 维护 Todo，使用现有工具及审批。
  3. 3. 轮次结束检查结算用量，判断继续、等待、暂停或验收。
  4. 4. 验收完成逐项证据成立后提交 achieved；否则继续工作。

默认没有轮数上限。轮数只是诊断信息，不能替代进度或停止条件。短状态工具 create_goal/get_goal/update_goal 保留；它们只读写目标，不在一次函数调用中执行整个任务。

五个 harness：采用什么，不复制什么

参照及证据核实的行为OpenProgram 的选择
Codex：历史修复 · 空闲续轮缺失工具输出补 aborted；Goal 通过普通线程空闲准入继续。采用普通聊天续轮、配对修复和当前状态验证；不把 aborted 解释为外部效果已撤销。
Claude Code：恢复 · Goal 评估崩溃中的工具不自动重跑；独立小模型按对话证据评估 Goal。仅核实官方合同，非内部源码。采用恢复后不盲目重跑与独立完成审查；不每个工作轮次都额外评估，避免无必要的延迟和费用。
OpenCode：历史转换 · 步骤用量pending/running 调用转换成中断错误；模型步骤结束记录 tokens 与 cost。采用可继续的中断历史和逐请求用量；Todo 是工作计划，不独立决定完成。
OpenClaw：配对修复匹配已有结果，缺失时补错误，处理重复及位置不正确的结果。采用 provider 请求投影修复；不覆盖原始真实记录，不把 heartbeat 等同于 Goal。
DeepSeek harness：中断关闭 · 续轮合同独占写入后追加修复；区分未开始和结果未知；关闭旧 turn，恢复后的 Goal 需明确授权继续。采用分层状态及幂等修复；不复制默认 round cap，也不采用重启后必须手动重新启用的产品策略。

以下是基于这些实现作出的 OpenProgram 设计选择，不声称五个项目具有相同的安全、验收或费用保证。参考源码固定到已检查的版本；未运行外部项目的测试。

Codex 的可确认边界：官方 App Server 文档区分 thread/resume、turn/start 和持久 Goal；公开扩展源码在恢复线程时加载 active Goal，在空闲时尝试续轮。这些证据没有证明任意桌面退出、系统重启和工具进程死亡均可恢复原内存或继续原工具。OpenProgram 将“此前运行意图仍有效时自动继续”定义为自己的明确产品合同，不依赖这个未经证实的更强假设。

现状：已有持久化，缺少一致的恢复决策

已检查的代码当前行为需要改变或验证的部分
execution/startup.py、execution/control/recovery.py已有 owner 核查、canonical 恢复、wait 回执恢复和投影重送；不是空白实现。未确认 effect 可使整个 execution 进入 reconciliation_required；要把“操作待核查”和“会话可继续”分开。
execution/restart.py已有重启暂停意图、去重续接命令和资源准入；默认无恢复期限，显式禁用和有限期限保留，要求无未决 effect。全状态恢复尚待验收；旧记录已保存的有限期限不自动延长，未决效果不因取消默认期限而获得重放权限。
workflow/goal/chat.py、_webui/_exec_dag.py聊天 Goal 不因停机或显示投影修复而暂停；执行完成前持久化通知，重启后按原策略续轮。缺失恢复来源的旧记录保留显式 Resume。完成通知与检查点恢复已有针对性测试；未知效果、新轮次恢复和完整子任务路径仍待实现及验收。
agent/job/runner/recovery.py、execution/control/waits.py已有 Job 恢复、延后 inbox、持久回答与去重 continue；普通聊天部分重启路径排除 spawn/merge。统一父子任务恢复决策及结果投递，不能假设已保存 Job 等于已完整恢复子 agent。
execution/waits.pydurable wait 与 live producer wait 不同；失去 producer 的 live wait 会取消。可恢复的审批和问题不能只依赖进程回调；失效的问题保留记录，重新确认而不是默认批准。
usage/context.py、usage/event.py已有会话、agent、Job 归属及账本；上下文未直接保存 Goal/revision/request-attempt 身份。请求前固定归属和唯一键，支持重启后的迟到回执；缺失用量不能作为零。
browser_resources.py、terminal_resources.py、Web session store已有资源身份、恢复状态及会话投影；不等于进程、网页状态和运行环境全部可重建。逐资源验收真实重连、失效报告和新资源身份；前端重连不能触发重复执行。

检查覆盖上述共享入口，不宣称所有资源适配器已经逐个完成故障测试。不能仅凭 UI 暂停推断历史数据已删除，也不能仅凭记录存在推断任务可自动继续。

自动恢复合同：运行意图不随进程消失

在现有 admission / command / restart intent 上补齐持久的 run_intent，不新建平行调度系统。它记录 work_id、原始输入与待消费消息、desired_state（run / paused / cancelled / done）、最近有效控制版本、权限范围、目标 revision、执行宿主身份、父子关系、最后提交进度及恢复策略。原用户请求被可靠保存后才能向客户端确认已接受。

默认自动恢复此前仍为 run 的已授权工作，普通会话与 Goal 一致，不依赖用户重新打开该会话。暂停、停止、完成、审批未通过和预算耗尽均保留。没有 Goal 的普通请求只继续到这次请求完成，不转成无限 Goal。后台任务沿用原有授权和并发额度；重启不允许生成额外子任务。

关闭窗口或前端重载只断开客户端；“退出并停止全部任务”必须持久化用户停止意图。普通 App 退出、升级维护、worker 崩溃和机器重启不隐式等同于用户 Pause。正常退出先停止新准入、保存已接受控制操作和检查点，再退出 worker；强制退出按最后已提交记录恢复。仅存在客户端草稿、尚未被服务端确认的输入不冒充已提交请求。

取消隐藏的两小时恢复有效期；长时间停机也保留运行意图，但继续前重新检查工作目录、宿主、模型和工具可用性、凭据、当前权限与预算。资源不存在或权限已撤销则显示准确等待原因，不自动切换项目、账号、模型或扩大权限。已有显式禁用自动恢复的设置仍有效；旧暂停记录原因不明时保持暂停并提示，不能猜成正在运行。

  1. 加载事实：读取运行意图、用户控制命令、消息、checkpoint、effects、waits、资源、用量和投影游标。读取或迁移失败时显示恢复失败，不清空旧状态。
  2. 确认所有权：存活执行者重新关联，死亡执行者被 generation fencing 排除；同一工作只由一个宿主恢复。单机恢复不偷偷变成跨主机接管。
  3. 修复上下文：合并真实结果，补齐缺失工具输出并记录中断；有完整安全检查点时从检查点继续，否则以相同 work_id 的新 turn 继续，不重复追加用户输入。
  4. 作出决定：用户停止优先；随后检查审批、权限、预算、资源和未知效果。可运行进入 queued；待依赖进入 waiting；故障给出可重试原因。所有决定保存到同一控制服务。
  5. 准入与续接：经现有公平调度和资源额度启动；按 work_id + 控制版本 + 前序提交点生成稳定 continuation key。保存准入和消费恢复意图不能留下重复窗口，跨库部分用可重试 outbox 收敛。
  6. 恢复界面：App/Web/TUI 从 canonical 快照及单调事件序号重建，显示恢复中、排队、工作、等待或失败；展示不是第二套控制逻辑。

恢复协调逻辑属于现有 execution control；服务器和 JobRunner 可以调用同一幂等入口，但不能各自作不同恢复决定。UI orphan cleanup 只修复派生投影，Goal.after_terminal 只提交当前版本的续轮请求。客户端发送队列里等待的用户消息优先：客户端上报有消息在等，续轮最多让出一小段宽限时间；期间用户轮次在 Goal 锁内完成 admission，旧续轮随之作废。临时故障使用持久重试时间和有上限的退避间隔，不空转模型；持续故障保留待恢复记录，显示错误和 Retry / Pause / End，不删除任务。

全状态恢复矩阵

重启前重启后默认行为必须保留的限制
已接收、尚未调度的普通请求保留原输入顺序重新排队，只准入一次。以客户端请求 ID 去重；Stop 不被迟到重试覆盖。
模型流式回复中断保留已提交文本和工具结果；未完成输出明确标注，重新请求剩余工作。不能拼接成虚构的完整回复；新的 provider attempt 可新增成本。
active Goal 正在工作或两轮之间加载目标、Todo、证据、预算和原运行意图；自动继续工作或验收。不能因无当前 execution 漏掉空闲 active Goal；5/5 只触发验收。
用户 Pause / End / Stop保持暂停或终止，不受完成通知及自动恢复解除。停止命令一经接受即持久化；可见执行停止进度与业务意图分开。
待审批或待用户回答恢复原问题、请求摘要及作用范围；持久回答已提交则只消费一次。重启不是批准；工具实现、参数或权限变化时旧批准不适用于新动作。
父 agent 等待子任务恢复已有子任务身份、输出、inbox 游标及等待关系；父任务收到终态后按原意图继续。存活子任务重新关联，已结束子任务不重建；用户暂停策略传播给同一任务范围内的子执行，不误停独立任务。
外部进程、终端或远程作业运行中凭宿主、进程启动身份或作业 handle 查询，存活则继续观察。不能仅用 PID 判断；无法确定是否完成则保留 unknown，不重复提交。
浏览器 / MCP / 临时资源保留稳定资源引用，重连后核实身份；确实失效时报告并按授权新建资源。网页表单、登录、JS 内存、REPL 变量不保证恢复；新 tab 或新 session 不能冒充原对象。
context compaction 或消息持久化中使用最后已提交历史与摘要，未提交摘要不覆盖原历史。部分工具参数不可执行；权限配置取当前有效值，持久的工作配置与不可用依赖明确显示。
结果已写入、完成通知未送达重放终态投影与 inbox 投递，不重新运行任务。canonical 终态和投影版本防止 UI 回退；父级汇总不重复计费。
费用回执未到或仅在流中出现按 provider attempt 核查可取得的回执，已有记录去重汇总。无法取得的消耗保留未知；停机时间不计入 active time。

恢复承诺的是已确认保存的工作状态、运行意图与可重建执行，不是任意进程内存快照。未落盘流片段、已死亡 shell 的交互内存或外部服务丢失的回执必须如实说明，不能用清空任务掩盖，也不能用虚构成功补齐。

投影派发的处理权限

执行存储拥有权威执行状态，DAG、任务、工作流和 UI 消费者通过持久化 outbox 接收派生事件。批量领取不允许在租约过期或领取被替换后启动后续回调。

派发器在每次调用消费者之前核对持久化的所有者、租约及领取次数，成功确认和失败报告使用同一领取身份。重复使用所有者 id 不允许旧回调结束新的领取。过期记录保持可恢复，权威执行状态保持不变。此约束不保证外部副作用恰好执行一次，也不能停止租约过期时已运行的回调；消费者仍须幂等并检查版本。

验收通过真实 SQLite 和公开派发入口验证：前序回调期间租约过期时跳过后续旧回调；同一所有者重新领取后拒绝旧确认与失败报告；正常派发、重试及停止时释放保持兼容。

实现状态：后端领取身份校验已实现。规格与质量审查通过，234 项执行组件测试和 119 项 Web 执行接口测试全部通过。合并、安装及已安装 App 的验收分别记录于发布证据。

一个聊天执行层，五类持久数据

数据及唯一所有者保留内容不能承担的职责
Goal / 目标状态服务goal_id、revision、原目标、验收条件、status、显式 budget、阻塞原因。不持有 provider stream，不恢复函数调用栈。
Todo / 现有计划存储稳定 item_id、goal_id、revision、状态、证据引用；UI 从同一来源读取。不能通过删掉未完成条目缩小目标；计划编辑不是任务进展的充分证据。
轮次 / canonical execution输入来源、权限、目标归属、owner generation、轮次状态、子任务。interrupted 不等于 Goal 失败，不等于所有外部进程停止。
工具尝试 / 效果存储调用和实际工具实现身份、输入摘要、开始记录、真实或合成结果来源、效果确定性。结果未知不能伪装成成功或“从未执行”；工具名称不能证明只读。
Usage receipt / 用量账本request/attempt 唯一标识、turn/goal/revision 归属、模型、tokens、价格快照、金额和可信状态。不从会话总额猜 Goal 费用；不将估算伪装成实际结算。

继续复用现有 session、execution、effect、todo、usage 存储，不建设第二套事件平台。需要跨库更新时使用现有可重试通知及唯一操作键；不假设跨数据库原子事务。派生 UI 与统计可重建，原始记录不被派生状态覆盖。

Goal 状态保持 active / paused / blocked / achieved / cancelled / budget_exhausted；执行、等待、验收放在 phase 或既有等待记录中，不组合出重复状态机。兼容 paused_recoverable 的存量读取。revision 或权限改变使旧验收与自动续轮预约失效，旧用量仍归原目标。

中断恢复：先确认执行所有权，再恢复上下文

  1. 确认旧执行者：使用现有 owner lease / generation 判断；租约不明、存储不可读时暂不写修复。不能仅凭“连接断开”宣称旧进程死亡。旧 generation 的后续写入被拒绝。
  2. 核实子进程：可跟踪的存活进程重新关联并等待或显式取消；不能把仍运行的 shell 当作已停止。失联的远程操作保留未知效果记录。
  3. 选择唯一恢复方式：存活 owner 只重新关联；确认死亡且有可验证的安全 checkpoint 时，在同一 execution 下创建新 attempt；仅无可靠 checkpoint 时，取得独占恢复权，以稳定 repair key 补齐缺失输出、结束旧 turn 为 interrupted，再准入新 turn。三者互斥，选择绑定同一持久恢复决定、控制版本和 continuation key，不能既续 checkpoint 又新开 turn。checkpoint 必须覆盖已提交效果并满足现有权限、等待与安全点合同，不能借此重放未知写入。修复重复执行无副作用，真实结果优先，不写虚构用量；迟到且可验证的真实回执追加为核对事件，在后续上下文中替代合成占位。
  4. 恢复运行意图：此前仍在运行的普通请求和 active Goal 自动进入统一准入；用户主动暂停的不自动恢复。需要人工处理的只是具体权限、预算、资源或未知操作，不把重启本身作为手动 Resume 的理由。
  5. 决定工具行为：新轮次知道哪些调用未开始、哪些结果未知。继续核查和独立工作不受旧未知结果全局锁定；相关写入仍受原审批与恢复限制。
中断前状态恢复后的事实允许的后续操作
意图已保存，尚未记录 dispatchnot_started；所有 dispatch 必须先持久记录，否则不能作此判断。仍有必要时按当前权限重新调用。
dispatch 已记录，结果缺失outcome_unknown；包括记录开始与真正调用之间崩溃的情况。可信只读工具可重读；服务支持去重时用原幂等键；其他写入先核实。
结果已经持久化completed / error，保留实际返回值。复用结果，不因重启再次运行。
外部任务仍存活running_external + 可验证 handle。重新连接、等待或取消；不重复提交任务。
非幂等写入结果无法查询outcome_unknown + 待处理操作明细。允许读操作及核查；用户确认风险后才能重试或明确放弃该操作。

安全边界：read_only / idempotent / state_probe 能力来自受信工具注册信息及执行时保存的实现身份，不接受模型自称只读，不按 read 这个名字猜。一般 shell、第三方 MCP 与自定义工具默认未知。未知写入相关恢复轮次先限制为可信读取与状态查询；没有可靠相关性判断时，不自动开放写入，必须先核对或由用户明确授权。

请求历史修复先按原调用 ID 匹配最近的调用，再执行 provider ID 转换。已有真实输出优先，重复输出取最后保存的真实记录；缺失结果生成确定性的 unknown 占位。调用和结果在请求投影中相邻，用户消息顺序保留；原历史不变。没有对应调用的结果不作为有效工具协议项发送。中断回复保留部分文字并标注中断，不重用不完整的 reasoning 签名。同一回复内重复调用 ID 无法确定归属时明确报错，不猜测执行事实。该转换没有执行权限，也不能替代执行恢复决策。

恢复权限检查使用同一 conversation provenance 确定旧执行与所调用 Job 的范围，不扩大到被调用会话的全部执行。仅真实内置 read、grep、glob、list 的执行函数可作为只读核查；工具名称、acceptEdits 标记和插件自行声明不能替代实现身份。其余操作在下述适用执行范围内存在未知效果时必须获得单次审批，不能使用 bypass、自动分类或既有 allow 规则免除。持久审批绑定新工具调用与未知效果集合，集合变化后重新审批；不会消除旧效果记录。无法读取恢复状态时拒绝执行。此检查是受限新轮次恢复的前置条件，不单独改变旧执行状态或开启 Resume。

这不是针对某个会话放行，也不是只对白名单文件修复。普通聊天和 Goal 共享同一恢复入口。旧效果审计可继续是 unresolved，而其所属聊天轮次结束为 interrupted；相应调整“存在 unresolved 就不允许结束轮次”的旧约束。

只有显式启用的 Goal 才产生 Goal 界面。启动、执行、暂停和验收不会新增聊天卡片。结束时，在对应聊天位置保留一张简洁记录卡片，复用现有附件卡片样式，点击后打开同一个 Goal 详情窗口，以只读方式查看历史。每条记录保存自己的 Goal 快照和聊天位置，后续 Goal 不会替换其内容。输入框继续只显示当前 Goal。由权威执行身份识别的验收消息属于内部记录，不作为助手聊天正文；普通回复保持不变。聊天不会追加评估文本、证据标识或原始报告。终态历史随 Goal 状态通过乐观并发控制保存。实现通过独立规格与质量审查，覆盖终态快照持久化、稳定历史位置、只读详情窗口复用、键盘焦点恢复和普通 JSON 回复保留。完整验证和安装版 App 验收仍是独立发布检查。

Todo 管计划，验收管目标

目标创建时保留原文并提取可核实要求；不明确到会改变任务范围时才询问用户。多步骤任务由工作 agent 维护 Todo，简单任务允许无 Todo。每个必要要求都有证据检查点；新增或删除 Todo 不得隐式删除原要求。

普通工作轮次不运行第二个 judge。工作 agent 提交 complete 候选，或必要 Todo 全部完成且尚未验证时，进入 verifying。先检查当前 revision、必要 Todo、未结束子任务和相关未知效果，再运行一次独立的只读验收；工作 agent 的“完成”文本不是验收事实。

验收按要求输出 met / unmet / unknown 和证据引用；可确定判断的要求检查真实测试回执、文件版本、运行状态等。语义要求由独立模型审查。需要执行测试时沿用普通工具审批和预算；shell 不因为被称作“验证”就变成只读工具。缺少证据返回下一轮补充，不伪造通过。

仅当前 goal_id + revision + 已核验的结果版本允许提交 achieved；提交前重新核对证据版本并比较 Goal 控制版本。可控产物使用版本号或内容摘要，外部事实记录核实时间及查询回执，不声称跨所有外部系统原子验证。完成表示该次核实时条件成立；完成后不默认监控文件或重新开启目标。后续编辑、新请求或明确监控要求另行验收。人工豁免必须作为明确的目标修订并保留原因，agent 不能自行缩小范围。独立验收同样可能出错，不保证绝对正确。

无进展的判定看结果与证据变化，而不是是否调用工具。唯一的机械例外是完全没有调用工具的自动轮次：它不可能改变结果，因此下一轮续跑提示带警告，连续第二次时 Goal 以 stalled 停下；工具调用、用户轮次或 Resume 都会清零计数。相同真实阻塞连续出现、且没有独立可做工作时才进入 blocked；有运行 handle 的等待进入 waiting，不空转模型轮次。不以“达到固定总轮数”冒充阻塞或完成。

等待使用既有持久 wait 与 execution 终态通知，保存 work_id / Goal revision、handle、已观察版本及唯一消费键。完成、失败或超时通知仅在运行意图仍为 run、版本相符且无其他当前执行时准入一次；缺失通知由既有 reconciler 按退避间隔查询。重启期间到达的结果先保存，恢复后按相同规则自动继续。暂停、取消或修订使旧唤醒失效，不丢弃结果本身；查询超时不推断外部操作已经停止。

费用：按请求归属，按回执结算

请求发出前固定 goal_id / revision / turn_id / request_id；暂停后的普通聊天没有旧 Goal 归属。子 agent 与验收请求显式继承归属，同一 receipt 只计一次，不同时加父项汇总与子项明细。重试是新的 provider attempt，若产生真实消耗则分别计入。

流式累计 usage 按同一 attempt 更新水位，不对每个累计快照求和。持久回执写入成功后再刷新 Goal 投影；临时失败由相同幂等键重试，重启可重建统计。迟到回执仍计入原 Goal，不因为 Goal 已暂停、结束或编辑就丢弃。

tokens 已知与价格已知分别保存。价格表换代不追溯改写历史报价；估算、已知值、部分未知分别显示，例如“已知 $0.42；另有 1 次请求用量未知”。历史游标数据保留，不推算无法证明的归属。主动运行耗时按持久开始/停止记录累计，暂停与停机不计 active time；恢复不清零。突然失去执行者时保留最后心跳时间，发现崩溃的时间不冒充停止时间；显示已知时长下限和中断时段未知。迟到用量不启动已暂停计时；显式时间限额无法核实时停止新准入，不增加默认限额。

预算默认不设限。用户设置硬费用预算时，未知价格或无法核实的消耗不能当作剩余额度；暂停新的付费准入并说明原因。能够计算请求最大额度时预留额度，否则不承诺绝对不超支。重新读取账本、恢复执行及验收前均重新检查显式预算。

后台 Job 在真实活动调用者的准入边界保存 Goal 身份，启动时恢复该身份并清除无关的临时归属。跨会话调用保存原调用者来源，但不创建跨会话 canonical parent。Goal 和 Job 共用 usage.db 的开始与结算事务；回执保存 Job 预留身份，重启后不依赖内存 governor 重建计量。未知 token 与未知费用分别保留预留额度，累计部分数据只保存下限。未开始的过期预留不能发送，已开始请求不会自动释放。硬预算仅接受已审计的输入与输出上限、明确价格和服务档位，不给未设置预算的 Goal 增加默认限制。

实施顺序与必须通过的验收

阶段与改动位置必须证明的行为
1. 统一恢复决策：execution/startup、restart、control/recovery、JobRunner、_exec_dag 投影普通请求、active Goal、已存在子任务在重启后自动恢复；用户暂停不恢复。取消隐藏时间窗口，删除投影层业务状态改写，保持唯一准入与当前权限。
2. 共享执行恢复：agent/production_driver、上下文构造、effects、waits、资源适配器真实子进程在 dispatch 前、开始后、结果写入后被终止；重启后只追加一次修复，保留真实结果，可继续普通聊天。旧 owner 迟到写入、存活 shell 与未知非幂等写入不能被错误重试。
3. Goal 续轮与控制：workflow/goal、HTTP/WS/TUI/ACP 入口Resume 不重放工具；双击、重复完成事件、编辑/暂停竞争不产生双执行。旧 revision 不提交新目标完成。无 Todo 不显示占位；5/5 不直接显示 achieved。
4. 证据验收：Goal completion 候选与现有 agent 检查能力必要项未完成、证据缺失、测试失败、结果过期、相关未知效果分别拒绝完成；实际证据满足时只提交一次 achieved。验证不能提升工具权限。
5. 请求归属与统计：usage/recorder、ledger、Goal 投影重复/乱序 usage、并发子任务、流式累计值、重试、账本故障、暂停后迟到回执均正确；未知不为零，预算超限不继续付费请求。
6. 兼容与本机验收旧 Goal 可读取、未知效果无猜测迁移。完整回归、独立规格/质量审查后更新唯一默认 App，并验收真实按钮、重启续接和费用显示。

每阶段先公共入口故障复现，再最小实现及回归。普通聊天也覆盖恢复测试，不能仅让一个特定会话通过。验收区分源码、自动测试、本机 App 和远端发布；没有测试或部署证据的设计不标已实现。

重启故障验收：不是只测一次 Resume

通过公开聊天、Goal、Job、审批与控制入口建立任务，在独立测试存储及非用户可见的进程测试中进行真实终止；不得终止用户的当前任务来证明故障恢复。最终可见 App 验收只使用默认实例，并先确认更新不会覆盖无关工作。

  • 覆盖前端重载、App 正常退出、worker 正常重启、worker 被强制终止、停机超过原两小时窗口、恢复过程中再次崩溃；宿主重启语义由进程身份变化测试，真实系统重启单列未验收，不自行重启用户机器。
  • 断点包括接收输入前后、provider 请求中、tool dispatch 前后、结果提交前后、父子消息投递中、Todo 全完成但尚未验收、完成提交后投影发送前、费用持久化前后。
  • 同时恢复多个会话，证明公平排队、共享额度、每个工作单一 owner、重复通知不双执行；恢复期间用户 Pause / End、修改权限或新输入优先，旧版本不得继续。
  • 存活子进程只重新关联，非幂等写入结果未知只核查；已接受审批不重复消费，审批未接受不自动批准；晚到结果与晚到费用归原身份。
  • 数据库不可用、损坏迁移、缺失凭据、目录不存在、工具版本改变和投影事件丢失均有明确状态及可恢复入口；不能清空历史或停留在无说明的禁用控件。

任务无法完成时，控制器如何停止

原生 Goal 会在普通 agent turn 结束后自动决定是否继续，因此必须同时处理“暂时没有完成”“缺少外部条件”“目标不可实现”和“持续没有有效进展”。只有轮数上限不能识别这些原因，只能限制最坏情况下的执行长度。

困难任务的状态机绿色是成功；黄色状态必须停止自动工作并等待明确事件；红色状态需要修改目标、预算或运行环境后才能继续。

为什么“调用了工具”不是进展

工具调用只能证明 agent 执行了动作，不能证明验收条件更接近满足。停滞检测应比较连续轮次新增的 evidence refs、通过的 deterministic gates、未完成 checklist 项和外部状态变化。相同证据反复出现时，应进入 stalled，而不是重置停滞计数。

等待不能占用工作轮次

问题先进入持久化异步队列；只要还有不依赖答案的安全工作，controller 就继续执行。仅当全部剩余工作依赖答案时才进入 waiting_user。CI、后台进程、时间或外部事件进入 waiting_external；当前需要显式 resume。

结论：这些实现都不能仅凭语义 evaluator 保证收敛。可靠的控制器需要硬预算、基于证据的停滞检测、明确的 blocked/impossible/waiting 分类，以及只有外部事件才能解除的等待状态。

Codex

Goal 是 thread 上的持久控制实体；工作 agent 通过工具声明完成或阻塞。

数据与权限分离

  • ThreadGoal 是 typed record：thread_id、goal_id、objective、status、token budget、tokens used、time used、created/updated。
  • status 为 active、paused、blocked、usage_limited、budget_limited、complete。
  • 模型工具只允许创建、读取以及把状态改为 complete/blocked；pause、resume、budget/usage limited 由用户或系统控制。
  • 外部 app-server 提供 thread/goal/set|get|clear 与 updated/cleared 通知。

并发与完成语义

  • Goal mutation 与 idle continuation 共用 semaphore，写入使用 expected_goal_id 避免旧 turn 更新新 Goal。
  • resume 读取持久 Goal；只有 active 才重新登记 idle continuation。
  • completion audit 写在 continuation prompt 中，由同一个工作 agent 基于实际证据决定是否调用 update_goal，没有独立模型复核。
  • blocked 要求同一阻塞连续出现至少 3 个 Goal turn；token budget 耗尽由系统转为 budget_limited。
实现判断：Codex 的优势是 first-class state、权限边界、CAS 式更新、资源核算和 resume；风险是完成判断与执行者相同，主要依赖 prompt 约束和工具调用纪律。它累计 elapsed time，但当前结构没有 time budget，也没有等待外部进程的专门状态。

Claude Code

/goal 是通用 Stop hook 机制的 session-scoped prompt evaluator 配置。

复用 Hook 协议

  • 普通 Stop hook 可返回 decision:"block" 和 reason；reason 进入 Claude 的下一轮上下文。
  • prompt hook 可由模型返回 ok、reason、impossible。/goal 在这一通用机制上增加 condition、状态显示和恢复。
  • stop_hook_active 防止扩展脚本无条件递归；通用 Stop hook 连续阻止 8 次后由运行时强制结束。
  • Goal evaluator 只看对话中已经出现的证据，不读取文件或运行测试。

等待、错误与预算

  • 后台 shell/subagent 运行时不判定；完成结果会触发新 turn。长时间等待使用退避 check-in，交互会话每次用户输入之间最多自动发起 3 次 idle check-in。
  • 连续多轮无工具进展时停止自动循环，但保留 Goal，等待下一次用户 prompt 后继续评估。
  • 不可恢复的 auth、余额、无法压缩的 context overflow、模型不可用会清除 Goal；瞬时错误保留 Goal。
  • Goal 没有独立 typed budget；可把 turn/time 终止条件写进 condition。外层 print mode 另有 --max-turns 和 --max-budget-usd。
实现判断：Claude Code 证明了 Goal 可以作为通用“停止拦截器”的特化，而不需要独立执行器。它对 background work 的 defer/check-in 处理完整，但 evaluator 无工具，可靠性依赖工作 agent 把验证证据写入 transcript。

  • session resume、max turns 与 USD budget
  • TaskCreate / TaskUpdate 等任务账本工具

Hermes Agent

GoalManager 把自由文本目标、结构化完成合同、确定性 gate 和异步等待统一到 turn 边界。

完成合同与 gate

  • GoalContract 把 outcome、verification、constraints、boundaries、stop_when 分开保存，并同时注入工作 prompt 与 judge prompt。
  • GoalGate 在 LLM judge 之前执行；失败时跳过 judge，限制输出尾部并把失败证据作为 continuation。
  • gate 记录 attempts、exit code、output tail 和 workspace fingerprint；工作区未变化时复用失败结果，避免重复运行同一检查。
  • subgoal 是用户追加的验收条件，不重启主 Goal，也不重置原始目标。

状态、等待和适配层

  • GoalState 保存 status、turn budget、judge failure counters、subgoals、wait barrier、contract 与 gates。
  • judge 输出 done、blocked、continue 或 wait；wait 可指定 PID、process session 或秒数。
  • CLI 与 gateway 共用 GoalManager，但各自负责把 continuation 排进现有消息队列；不修改 system prompt 和 toolset。
  • Goal 状态随 session resume 恢复；context compression 造成 session id 轮换时迁移 Goal 并清理旧记录。
实现判断：Hermes 当前方案把“可验证完成”和“外部工作尚未结束”分开：确定性 gate 对验证结果负责，judge 对开放式语义负责，wait barrier 对异步依赖负责。默认仍是单 session 单 Goal 与 turn budget；总 token/cost budget 不属于已确认的 GoalState 合同。

实现方式

OpenClaw

把持久工作拆成 scheduler、background task、heartbeat、standing instruction 与 commitment，而不是提供通用 Goal evaluator。

相邻机制 · 开源源码
Persistent intent自动化 / 长期指令

调度与状态

  • Automation job 保存 id、name、enabled、schedule、session target、wake mode、typed payload、delivery、failure alert 和 run state。
  • payload 分为 system event、agent turn、command、script；session target 可为 main、current、isolated 或命名 session。
  • 运行结果区分 execution 与 delivery；持久化 job、运行状态和历史，gateway restart 后继续调度。
  • 脚本与 command 可以用 exit code 提供确定性成功，但这只判定一次 run，不判定开放式目标。

Heartbeat 与 commitment

  • Heartbeat 是系统拥有的 monitor automation；读取 scratch 或 HEARTBEAT.md，无到期任务时跳过模型调用。
  • 结构化 heartbeat task 只有 name、interval、prompt，按各自周期进入下一次 monitor turn。
  • Commitment 记录 agent promise 或从用户上下文推断的后续联系，包含 due window、confidence、status、attempts 与 delivery scope。
  • 这些机制擅长“何时再次执行/通知”，但没有 met/unmet evaluator，也不会把多个 run 约束为同一个完成条件。
实现判断：OpenClaw 最适合作为 Goal 的外部等待和调度参考。把它直接称为 Goal 会丢失完成判定语义；更合适的组合是 Goal controller 在需要未来时间或外部事件时创建/绑定 automation，收到事件后再恢复 Goal。

证据边界：未知结果始终保留在效果记录中；新的副作用需要针对当前操作的单次审批，普通聊天恢复不会重新执行旧工具调用。Todo 全完成只产生验收候选，独立普通聊天按原目标与固定要求检查实际读取或会话证据；提交前重新核对控制版本、证据摘要、相关后台进程和执行状态。同一已检查计划不会自动重复验收。请求统计保存 Goal/revision/execution 身份与价格，累计 usage 水位、子任务继承、预算预留及联合结算由持久账本恢复；缺少回执的请求保留未知，不把旧会话统计推算为新归属。突然失去执行者时只计入可核实的时间下限，不把停机时间计入运行耗时。完成验收仍是受证据约束的模型判断，不保证绝对正确。

目标完成显示

已结束的历史目标在原会话位置显示为可点击的简洁状态行。成功目标使用 Lucide 动态勾选图标与目标已达成，用时 9m 42s，时间来自该目标的有效执行时间。缺失时间不显示为零，中断时间保留已知下限。其他终止状态显示自身状态，不显示成功。点击打开现有只读历史目标详情。完成、验收和用量以已有记录为准，不根据回复文字或待办数量推断完成。

实现状态

紧凑完成状态行使用实际记录的 Goal 状态与活动时长，打开原始只读详情。组件和浏览器检查覆盖这一显示；已安装 App 的验收属于发布验证记录。

新交互式 owner 轮次在 Auto 或 bypass 下，仅检查当前 execution 及其后代中结果不确定的操作。嵌套 Runtime 只有在持久化接收记录证明该轮来自同一 owner 时，才采用相同范围：保存的 actor 是交互式 owner，完整性校验后的 chat 输入具有相同 source，当前 execution、session 和 principal 均匹配。提交到执行线程时传递现有 ContextVars，使子进程启动前的 Page 范围读取使用同一当前执行。Runtime 仍为非交互来源，不获得批准权限。缺失或不匹配的证据保留原限制；无法读取或损坏的恢复状态拒绝执行。当前 execution 及其后代的不确定操作仍要求精确的一次性批准。该筛选不解决或重放旧操作。显式 ask/deny、来源约束、plan mode 和精确 Page 绑定继续生效。

验收：在旧中断操作之后创建新 owner 轮次，通过 permission_decision 和真实嵌套 Runtime 检查 Auto 分类、bypass、当前及后代的不确定操作、来源不匹配和显式规则，并通过真实子进程验证 Page 访问。此嵌套范围修正已实现。独立规格与质量审查、真实子进程 Page 访问、浏览器组件及最终组合检查通过。因环境而跳过的用例不证明对应能力。已安装 App 验收独立记录于发布证据。
