Runtime architecture · owner initiated · macOS v1

In-conversation self-update

A user asks an Agent in OpenProgram to modify OpenProgram. The Agent edits, tests, and commits in an isolated worktree; a worker-independent controller builds and installs the complete App. After the new worker starts, it automatically creates an acceptance task to check the original objective. System-check or goal-acceptance failure restores the old App.

Core constraint: The worker being replaced cannot complete its own replacement. Persist handoff and pause checkpoints for other tasks before restart, then create a new acceptance task with provenance. After verification, resume compatible tasks from checkpoints and create a follow-up for the initiating session.

Question

How can an owner authorize framework changes in chat, followed automatically by build, stopping the old instance, App replacement, restart, acceptance Agent execution, and failure handling?

Audience

Runtime, Desktop, Job/DAG, permission, and local-release maintainers.

Exclusions

Windows/Linux, remote stable Releases, unauthorized background edits, multi-machine deployment, and unlimited automatic repair loops.

02

Conversation behavior

The user requests work through a normal conversation. Messages and tool results describe that work. Installation state is maintained by the update subsystem, not by a separate conversation widget. Reopening the App restores the conversation without an update history panel, update recovery notice or temporary verification dialog.

03

Target architecture

Separate the controller from candidate runtime. The current worker prepares and hands off; the supervisor controls activation and restoration; the new worker runs fixed system checks and a new acceptance Agent.

1 · Prepare
Agent edits, tests, reviews, and creates a candidate commit in an isolated worktree.
2 · Handoff
Owner approves; the update record stores session, turn, candidate, and acceptance criteria; launchd manages the supervisor.
3 · Build
Build the complete App and run packaged smoke and cold probes while the old worker remains running.
4 · Activate
After the current response is durable and other tasks are paused or finished, stop App/worker, preserve previous.app, and activate the candidate.
5 · Accept
The new worker checks revision/doctor, then creates a new self_update_verify Agent turn to check the original objective.
6 · Terminal state
Delete previous.app after success; restore the old App on failure/timeout and write evidence back to the original session.

Candidate builds may execute candidate code, but sandboxing must deny writes to default state, installation, and update-record directories. Only a supervisor generated by the currently installed version may activate or restore.

No ordinary Scheduler task

Scheduler time triggers and user-task authority do not suit the update protocol. Once JobRunner, session store, and owner-auth are available, the new worker executes recover_pending_updates().

Exactly once

Stable Job ID + atomic claim

The Job ID uses self-update:{update_id}:verify:{attempt}. The claim stores owner, lease, attempt, and job_id. Repeated startup does not resubmit an existing Job or terminal state.

Prompt contract

Stage context and tool isolation

The implementation Agent cannot bypass installation approval; the acceptance Agent has no source-write tools; diagnostic and repair Agents are read-only and propose structured output.verifier_config.py, diagnosis.py, source_repair.py stores stage configurations. New plans share goal, assertions, verification plan, iteration policy, and deadlines; inherited context never expands tool permissions.

Startup order

  • Load and migrate self-update state schema; fail closed on corruption.
  • Complete Job orphan reconciliation.
  • Start JobRunner and confirm admission/resource governance availability.
  • Complete revision, owner-auth, Web/WS, and doctor system gates.
  • CAS-claim the attempt, submit one verification Job, then start ordinary Scheduler.

Ordinary Scheduler startup failure does not block acceptance; JobRunner or system-gate failure requests supervisor rollback.

Controlled iteration policy

  • Default approve_each_activation: roll back and diagnose after failure; reauthorize before activating a new candidate.
  • Optional bounded_auto: owner explicitly authorizes at most 3 attempts, a total deadline, allowed paths, and a test set.
  • Pause for reauthorization on new dependencies, permission/approval changes, installer/supervisor changes, expanded paths, or changed objective.
  • Every attempt gets a new SHA, attempt, and Job ID; never overwrite earlier evidence.
  • Stop on repeated identical failures, rollback failure, environment-related inconclusive results, or budget exhaustion.

Post-failure execution flow

Service restoration, diagnosis, source repair, and activation approval are separate stages. Diagnosis does not authorize installation.

Fixed deadline and recovery
Bind diagnosis to original update, candidate, attempt, failure evidence, and rollback system evidence. Deadline is at most five minutes after rollback, or an earlier bounded_auto total deadline. Repeated startup reuses the request and Job ID; terminal or orphan Jobs are not rerun.
Bounded worker-side waiting collects results and cancels timeouts independently of Scheduler. A superseding update, owner cancellation, missing model, expiry, or evidence change stops diagnosis without changing ROLLED_BACK or re-restricting restored service.

Model classifications and suggestions require verification; they are neither test evidence nor new owner authorization. Environment, unclear-objective, and insufficient-evidence issues must not trigger automatic edits or activation.
Generate and apply source repairs
Create a separate stable-ID repair Job only when the new request freezes repair configuration, diagnosis is implementation or test, the old version is restored, and budget remains. The model uses the original model/profile and read-only tools to return structured edits. The controller checks original text and applies edits in a newly isolated worktree; the model executes no shell or Git.
Default scope is original changed_paths; bounded_auto uses original allowed_paths. Protected permission, approval, update-controller, installation-script, dependency, and Git-configuration files are never automatically edited. Stop on out-of-scope paths, symlinks, duplicate replacements, or source mismatch; do not modify the user’s original worktree.
New candidate and test evidence
The controller creates a new local commit and records the complete diff from original base, then runs frozen required_tests in a networkless sandbox without App write access. Record command, candidate SHA, exit code, and bounded logs. Recheck HEAD, Git binding, and tracked files after tests; tests that modify source invalidate evidence.
Repair Job and tests share a ten-minute post-rollback deadline, shortened by the original total deadline. A new update, owner cancellation, or expiry terminates the stage and test process group. Preserve evidence and isolated worktrees for terminal, failed, or partial edits; restart does not repeat edits/commits/tests or extend deadlines.
Reauthorization and activation
Candidate records bind original request, diagnosis, repair Job, full diff, and test results. The controller rechecks attempts, deadline, paths, dependencies, and repeated failures. approve_each_activation awaits owner approval for the new SHA; bounded_auto submits only within the original envelope.
A candidate record is not installation authority. Missing/failed required tests prohibit activation; environment, objective, or inconclusive diagnoses do not trigger automatic repair. The next candidate still requires full build, system gates, a new acceptance Job, and rollback on failure. Completed repair/testing does not establish implemented subsequent activation.

Old updates without frozen diagnosis retain their original recovery behavior; never synthesize configuration from mutable profiles. Diagnostic requests, claims, and results live in the original update directory, with one pending pointer at self-updates root. A new update revokes the old pointer under the same storage lock. Execution rechecks durable Job, current worker claim, frozen inputs, and unexpired deadline, rejecting forged source or input drift while restoring an old queue. Owners stop diagnosis through existing Job cancellation, not activation-preceding self_update_cancel. Diagnosis must not overwrite verifier verdict, signed acceptance results, or rollback conclusion.

Repair likewise requires independently frozen configuration in the original request; old requests gain no source-write capability. Default initial authorization includes isolated-worktree repair and listed tests after rollback, but not reinstalling. Only new requests explicitly selecting bounded_auto and approving the complete iteration authorization below allow scoped reinstallation. Repair output allows at most 32 text edits totaling 1 MiB. Each old_text must uniquely match a regular UTF-8 file; null old_text creates only nonexistent files. null new_text permits deletion only when old_text equals the complete file. The repair Job uses wait=true, creates no ordinary follow-up Agent, and leaves the original head unchanged. After the model Job completes, the owner calls self_update_repair_cancel(update_id) in the original session to cancel still-running candidate tests. Record candidate_ready only after the new SHA, complete diff, all configured tests, and post-test checks pass; no required_tests means awaiting_tests. Missing/failed configured tests or failed post-test checks mean failed; explicit cancellation and expiry mean cancelled and expired. None means installed.

Authorization and updates for repaired versions

Every update retains independent requests and evidence; an iteration sequence shares the original goal, scope, attempt budget, and total deadline.

Two approval modes
By default, self_update_retry(update_id, candidate_sha) in the original session forces one-time approval for the exact SHA, displaying full changes, tests, and remaining budget. Owner rejection or approval timeout creates no successor. Both modes verify current owner, original goal/assertions, successful rollback, remaining attempts, and total deadline. Failure fingerprints use trusted categories and failed assertion/check IDs, not model explanations, timestamps, SHAs, or random IDs.
Attempt counts and immutable successors
The first update is attempt=1. Successors use new update_id, SHA, attempt, and stage Job IDs, recording root/parent relations. Original goal, assertions, base, owner, model/profile, and policy stay fixed; only current identity/output schema are rebound. At most 3 attempts includes the first.
Reserve one unique successor and next attempt under the same storage lock. Reservation consumes budget permanently across submission failure, cancellation, and restart. A parent cannot have a second successor. Each build/acceptance retains per-attempt timeouts within the original total deadline. After expiry, only necessary safe rollback/recovery remains allowed; no further repairs or installation.
Interruption, concurrency, and complete updates
Persist the next-stage request after candidate results and before removing the repair pending pointer. Startup resumes approval/submission from that request. Save fixed child ID and budget reservation first, publish child request and active ownership, then invoke the existing external supervisor. Repeated recovery can only finish this submission, never re-edit, retest, or expand authority.
Other active updates or maintenance block submission; a new owner update revokes pending work from the old sequence. Default approval requests release after the approving turn is durable; automatic submission uses persisted authorization, results, and submission records rather than a fabricated chat turn. Successors still perform full packaging, cold probe, system gates, new verifier, and commit/rollback. Submission failure retains inspectable records without skipping stages.
Cancellation and visible state
self_update_iteration_cancel(update_id) persists a stop marker in the original owner session, stopping the sequence’s unsubmitted approvals/automatic submissions and cancelling running diagnosis/repair Jobs and candidate tests. Created but unactivated children use existing cancellation. Other sequences and ordinary tasks remain unaffected. State shows root, parent, current child, attempt/max_attempts, total deadline, and stop reason.
Transactions already activating/verifying cannot be forcibly interrupted by deleting requests. Prohibit later attempts while existing transaction logic finishes verification or safe rollback. Submission phases distinguish awaiting_approval, submitting, submitted, and stopped. submitted means handed to the supervisor, not installed successfully; success still requires child SUCCEEDED and acceptance evidence.

This stage reuses SelfUpdateStore process locking, JobRunner, mandatory approval, trusted supervisor, and transactional installer, without another Scheduler or generic workflow executor.self_update/iteration.py remains a side-effect-free policy decision; the new submission coordinator validates evidence, reserves budget, persists state, and recovers. Source responsibility boundaries do not replace real restart, rollback, and multi-attempt acceptance.

05

Design decisions

V1 adds only boundaries required for the goal, without another Job system, plugin system, or update dependency.

Controller

Update control must be outside the worker

Use macOS launchctl submit to launch a one-shot supervisor outside the worker process tree, allowing activation, verification timeout, and restoration after worker/App shutdown.

Candidate

Deploy immutable commits only

Candidates must come from dedicated clean worktrees with explicit bases. Reread HEAD during build; discard artifacts on drift rather than deploying directory snapshots.

Artifact

V1 always builds the complete App

Reuse complete runtime, Electron builder, and packaged smoke. Do not yet choose wheel, asar, or full-App paths by changed files, avoiding multiple completion semantics.

Handoff

Tool calls do not stop the worker directly

self_update_prepare only persists the request and starts the supervisor. After the assistant final, session commit, and change attribution are durable, dispatcher writes turn_released.

Continuation

Startup recovery creates a new acceptance Job

The new worker atomically claims the update and reuses JobRunner to create a background task with source=self_update_verify. Ordinary Scheduler neither creates, polls, nor retries it.

Rollback

Goal failure also restores the old App

Retain previous.app until system checks and goal acceptance both pass. System errors, Agent fail/inconclusive verdicts, and timeouts restore the old App while preserving candidate worktree and evidence.

Capabilities determined before updating

Trusted evidence receipt

Execution adapters save evidence

Failure and cleanup

Missing evidence cannot pass

Record precise reasons for closed windows, identity changes, denied permissions, vanished objects, judgment-affecting truncation, provider failure, and timeout. Page content, test output, and candidate code are untrusted data and cannot expand tool authority. Allowed-action enforcement must cover UI, IPC, and backend write entries; DOM selectors, button text, or read-only prompts alone cannot prevent side effects. Automatic acceptance avoids other sessions and personal browser data. User activity in the target window stops automatic interaction while preserving evidence; waiting cannot exceed the original deadline.

Task pause, restart, and continuation

On entering maintenance, the worker uses existing canonical pause commands to reach durable execution checkpoints. Each update saves execution id, pause command id, and observed version, resuming only tasks it paused. Previously paused, awaiting-input, cancelled, or completed tasks do not resume automatically. Queued Jobs that never ran retain queue identity and do not participate in active-execution waiting.

Supervisor replaces the App only after canonical active attempts and legacy running tasks finish. After commit or verified rollback and maintenance release, the new worker continues tasks through original continue commands and the Job resource queue. Fixed command ids prevent duplicate execution on repeated recovery. Failed pauses or unpausable tasks that miss the deadline abort the update and resume already paused work.

Checkpoint recovery retains execution-contract validation. Changed tool implementations or permissions prohibit replaying old operations and preserve the old checkpoint. Only a continue initiated by this update and rejected for contract change may create a fixed-identity replanning Job from the original task/history, retaining original tools/permissions and rechecking execution/update ownership before running. Unresolved side effects, user cancellation, or other session activity prevent automatic replanning. Task-recovery failure does not change installation acceptance. The initiating session gets a durable terminal follow-up reading original goal/history/update result; it neither replaces the verifier nor gains interactive reactivation authority. Old records do not retroactively create follow-ups.
