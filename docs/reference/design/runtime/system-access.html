Unified system access

System access is a host capability boundary. It is separate from model tool approval, workspace permission rules, account credentials and provider authorization. The product has one capability registry, one live report, one explicit setup path, one wait representation and one recovery policy. A status read never opens a native prompt. A model or a remote client cannot grant an operating-system capability.

Current implementation and verified gaps

The base runtime used two hard-coded macOS rows, screen_recording and accessibility. The backend report, native probe, request route, GUI preflight and Web settings each contained part of that list, while package declarations for other categories lived separately. This created drift and allowed a reconnect to look like an unsolicited permission request.

The implemented registry removes those duplicated capability definitions and keeps ordinary chat, browser and headless use independent from optional desktop access. The old two-capability API remains wire-compatible; its rows are generated by the registry. Package usage descriptions, entitlements, report schema, identity metadata, GUI preflight, settings UI and wait manifests now consume the same declarations.

Capability registry

openprogram.system_access owns an immutable registry. Every entry has a stable id, category, display label, platform, required/optional policy, target identity, non-prompting check, explicit request mode, settings destination, package declaration, operation mappings, and recovery policy. Backend report, CLI/TUI doctor, HTTP setup, Web settings, wait manifests and tests consume this registry instead of defining capability ids independently.

FieldMeaning
idStable protocol id, for example screen_recording, accessibility, apple_events, calendar, reminders, file_read, file_write, microphone and camera.

request_modenative for a supported OS request, settings for a settings-only capability, targeted when a target application must be supplied, operation when only the real operation can verify it, and none when the platform has no request API.

The registry is validated at import time: ids are unique, every platform entry has a check and state mapping, every settings action has a fixed destination, and every operation reference points to a declared capability. Package usage descriptions and entitlements are checked against the same ids in build tests.

State and API contract

Each report contains schema, platform, host, executing identity, timestamp, and a capability array. Rows contain id, category, status, detail, instruction, request mode, settings availability, required operations, and recovery metadata. Status means:

  • granted: the current named executor passed the fresh check.
  • not_granted: the check completed and macOS says the capability is absent.
  • unknown: the check failed, timed out, or could not prove identity. It is not treated as denial.
  • unavailable: the dependency or native API is missing.
  • unsupported: the platform/backend has no implementation.

GET /api/system/access returns the registry-derived report. POST /api/system/access/{id} is owner-only, loopback-only and explicit; it rechecks, optionally performs the declared native request, and returns a fresh row. open_settings=true only opens the declared settings destination and never claims a grant. Existing /waits records use the same ids and schema. Responses are no-store and contain no secrets.

First-run setup and operation flow

  1. On first use, the Web settings page displays the registry grouped by product area. It explains why each capability is needed and shows current status. A single “check all” performs read-only checks.
  2. The user chooses “Request authorization” or “Open System Settings” for a row or group. The UI never sends a native request during page mount, reconnect, status polling, history replay or model output rendering.
  3. The backend serializes one native request per executing identity. It uses the named runtime for the native check and request, then performs a fresh check. A macOS dialog may still be separate for separate privacy categories or target applications; the UI reports each result instead of claiming that one click can authorize unknown future targets.
  4. Before an operation, the operation declares its required capabilities. The worker runs one fresh report and creates a durable system_access wait only for missing required capabilities. Browser and VM operations bypass this host check. The wait stores the original checkpoint and continues the same execution after every required row is granted.
  5. After the user returns to the app, focus/visibility causes a read-only refresh. Granting access resolves the wait through the worker reconciliation path; it does not submit a fake answer, invoke a retry function, or create a new execution.

Recovery and identity

Ordinary status reads, startup reconciliation, retries and duplicate events never run tccutil and never reset another application. A verified stale receipt can authorize one explicit migration for the fixed OpenProgram bundle identity; the marker is written before the OS call and prevents loops. Unverified code, unknown checks, unchanged requirements, Accessibility migration and all other applications require the user to use System Settings. The named runtime and containing application retain stable bundle ids and a persistent local signing requirement. A build or cache path labelled python3 or node is not an accepted identity.

Third-party Apple Events authorization is target-specific. Calendar and Reminders use EventKit-style category consent when the native backend supports it. File access is scoped to the user-selected path or security-scoped bookmark. Microphone and camera are declared and requested only by operations that use them. The product cannot pre-authorize an application it has never targeted, a path the user has never selected, or a permission the user has revoked.

Trust, privacy and concurrency

Only the local owner on the execution host can request or open settings. Loopback and Origin checks remain mandatory; forwarded requests and remote clients are rejected. The model can describe a missing capability but cannot invoke the setup endpoint. Native probes run in a fresh bounded process, share one report per reconciliation pass, and do not enumerate screen contents. Requests are serialized per executor. Wait resolution is guarded by execution id, generation, checkpoint version and cancellation state. A failed probe keeps the wait open; a terminal or cancelled execution cannot resume.

Compatibility and migration

Old clients may continue sending screen_recording and accessibility. The API keeps those ids and adds registry metadata. Existing receipts are read with the legacy screen-recording shape. Unknown ids return a client error without opening settings. Existing permission rules and Auto mode are unchanged. No additional application profile, worker or port is created.

Acceptance criteria

  • One registry is the source for report, request, settings, wait manifests, UI labels and package declarations; a registry consistency test fails on drift.
  • Repeated report calls, reconnects, history replay and model output rendering cause zero native prompts.
  • Granted rows cause zero native requests. A request requires a local owner, fixed identity and explicit user action.
  • A GUI task missing either desktop capability pauses before planning, resumes the same execution exactly once after both are granted, and never uses the ordinary question/approval API.
  • Unknown, unavailable and unsupported are displayed distinctly from denied. Optional failures do not make installation or ordinary chat unhealthy.
  • Actual installed `/Applications/OpenProgram.app` acceptance confirms the named executor identity, current Screen Recording and Accessibility state, settings actions, and no Python/node identity migration.
  • Automated checks cover backend registry/probe/request routes, wait recovery, Web rendering and no-auto-request behavior; full repository and documentation gates are run after both independent reviews.

Implementation status

This document is the canonical design for the unified registry. The unified registry, schema/versioned report, identity metadata, package consistency checks, explicit setup UI, no-auto-request recovery, operation preflight parity, and terminal handling for unavailable or unsupported desktop access are implemented. Remaining acceptance is installation-specific: verify the installed default /Applications/OpenProgram.app on port 18100 and its current macOS grants; those grants remain controlled by macOS.
