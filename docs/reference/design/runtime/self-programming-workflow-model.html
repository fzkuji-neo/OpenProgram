Programming model · migration plan

Fixed boundaries of Agentic Functions, Workflows and Skills

This page is the authoritative classification and migration contract. Directories organize source only; decorator-registered functions are executable entities. Ordinary Agentic Functions permit only one model call; all complex orchestration belongs to Workflows.

1. Fixed decisions

Vanilla Function

Deterministic Python capabilities: no model call, Agent launch or Goal creation.

Model calls = 0

Agentic Function

A single-model capability consisting of a prompt and minimal deterministic code, replacing some first-party text Skills.

Exactly one llm() call

Workflow

Compositions containing multistep control flow, Agent tool loops, Goals, multiple model calls, file side effects or persistence.

Complex execution belongs only here
@agentic_function is the existing registration decorator, not permission for arbitrary Agent behavior. Public Workflow entries may still register through it, but their source must reside in workflow/ or programs/workflow/ Workflow categories. Classification follows execution semantics, not decorator names.

3. Target execution model

Workflows continue using static Python imports and ordinary function calls. Registration, permissions, cancellation, DAG caller and Runtime retain existing implementations; this design adds no DSL, dispatcher, registry or database.

4. Skills retention and migration boundaries

SourceTreatmentReason
Third-party or user-installed SkillRetain SKILL.md, resource files and the existing loading mechanismThese are installable extension formats and must not be broken by repository Python migration.
First-party pure-prompt Skill that needs one model callMigrate individually to Agentic FunctionsGain typed parameters, registry discovery, testing and DAG records.
First-party Skill with scripts/tools/multistage stateMigrate to a Workflow or retain as a SkillDo not remove necessary control flow merely to satisfy the one-model-call rule.
Skill providing only documentation and reference materialRetain as a SkillOn-demand context resources are not executable functions.

Migrate one Skill at a time. Prove equivalent input/output contracts before removing each old first-party entry; do not mechanically convert all Skills or change third-party installation protocols.

6. Five independent implementation tasks

Freeze the classification contract

Add static contract tests: Vanilla reachable call graphs must never reach a model; ordinary Agentic Functions must reach exactly one llm() and must never reach agent()/goal(); Workflow categories are unrestricted by this rule.

RED: first detect the current incorrect browser/docs/security/goal classification.

Organize true Agentic Functions

Classify by actual responsibilities such as document, text and research. Preserve deterministic pre/postprocessing; move model-free helpers into Vanilla or internal modules. Moving files must not change registry names, schemas or public calling conventions.

Gate: equivalent registration inventories before/after; every Agentic Function satisfies one llm call.

Move complex capabilities into Workflow categories

Migrate browser/web, docs question, security review, goal, deep work and composite research. Move only code ownership and imports, without a new runtime; organize directories by subsystem.

Gate: call graphs show real entries and dependencies; a directory itself never becomes a Program.

Handle first-party Skills individually

Create an inventory marked keep / agentic / workflow. Migrate pure-prompt single-call capabilities to Agentic Functions and complex flows to Workflows; leave third-party/user Skills unchanged.

Gate: every deleted first-party Skill has equivalent parameter, output and failure-semantics tests.

Remove demos and structures without responsibilities

Move interaction demos, test frameworks and resume demos to tests or delete them; remove empty directories, empty entries and unused helpers. Retain compatibility aliases only for actual public external contracts.

Gate: no demos, empty directories or helpers posing as entities in Programs.

7. Acceptance and completion conditions

Classification contract
Vanilla = 0 model calls; Agentic Function = 1 llm(); complex execution = Workflow.
Directory display
Programs follows actual folder paths without fabricated directories, empty folders or helpers.
Execution identity
Only registered functions are executable; moving files does not change names, schemas, exposure or execution IDs.
Skills
Third-party/user Skills remain compatible; first-party migrations have per-item inventories and equivalence tests.
Architectural limits
No new @workflow, call_workflow(), DSL, second registry or second Runtime.
Product acceptance
The default-App Programs tree has no empty entries; function-detail call graphs derive from the selected function’s actual reachable calls.

Minimum verification: classification contracts, Programs discovery/graph tests, related unit/component tests, Ruff, Web typecheck, documentation links and git diff --check. The default-App Programs tree must still be verified in /Applications/OpenProgram.app before this page can be marked Implemented.

Workflow package imports

from workflows.NAME import NAME references the same authorized public callable in the active directory; snapshot execution explicitly owns its workflows namespace and retains fixed dependency versions. Package helpers use relative imports and execution remains ordinary Python function calls. Both authored and generated packages pass structural validation and mandatory sandbox behavior tests before publication. See Workflow package contract.
