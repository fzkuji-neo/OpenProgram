Delivery boundary and fixed choices

This plan implements the linked configuration contract. The current deliverable is documentation and a browser-testable editor prototype; it does not migrate real user data or modify runtime behavior. The first production release covers saved/inline configurations, atomic persistence, shared resolution, optional memory and the editor. Optional automatic selection has its own later stage; it is not a prerequisite for manual per-call model selection.

  • AgentSpec remains the only saved registry; AgentConfig is a typed value. Reuse Runtime.exec, MemoryBackend, Context Engine, capability catalogs and existing resource governance.
  • New saved/anonymous configurations default to memory off. Legacy profiles preserve effective behavior through explicit migration; no history or memory store is silently moved.
  • Model selection occurs at invocation admission. Changing model mid-response or replaying side effects under a fallback model is outside this release.
  • Single-base resolution only; no named-Agent inheritance tree. No role is mandatory, no autonomous creation of saved Agents, no new worker or orchestration engine.

Migration, old clients and rollback

  • Preflight reads all saved Agent records, the default pointer and effective legacy global settings under the configuration writer lock. Produce a dry-run report of IDs, schema versions, unresolved references and semantic differences. Do not include secrets or memory contents. Unknown schemas and corrupt records block migration for that profile; never silently replace them with main.
  • A legacy config has schema 1 when the version is absent. Normalize it to schema 2 with initial revision 1. Preserve unknown extension data in a dedicated migration backup; reject unsupported executable fields until understood. Explicitly preserve the old memory binding and effective behavior; do not switch old Agents to new empty self spaces. Legacy global inheritance remains a named compatibility source until a user selects a concrete mode.
  • Back up the exact owned configuration files and index with restrictive existing permissions before the first write. Use a journal and restart-safe reconciliation for multi-file work. Commit a profile only after normalized validation succeeds; interrupted migration resumes idempotently. No external workspace, credential, session, DAG or learned-memory content is modified.
  • New UI/API writes require expected_revision. Existing clients supplying updated_at use a temporary compatibility adapter: compare their timestamp under the same writer lock, derive the current revision, then perform one atomic write. Missing both preconditions returns 428; the UI must preserve drafts and request reload. Do not accept last-write-wins to keep an old client apparently working.
  • No-selector Python calls retain their current model/history/memory behavior and output type. New keywords are keyword-only. Explicit agent_id/config defaults to clean history; an explicit inherit request remains subject to visibility rules. Conflicting aliases are validation errors. Existing durable start_from and to meanings do not change.
  • Roll back code only with a reader that understands schema 2, or perform an explicit verified downgrade while writers are stopped. Unsupported new fields prevent a lossless downgrade. Restore the backup only before post-migration edits, or after separately exporting/reconciling those edits; never overwrite newer user changes. A legacy binary must not silently rewrite schema 2.
  • Compatibility removal requires updated first-party clients and a documented deprecation period. Additive schema support must land before strict write preconditions ship; deployment order is backend dual-reader, updated clients, migration enablement, then legacy-adapter retirement.

Optional selection policy: complete extension boundary

P6 is opt-in and runs before the existing resolver. A caller supplies an existing policy reference instead of agent_id/config; they are mutually exclusive. Policy candidates are saved Agent IDs or provider-qualified model references, never arbitrary generated executable configuration. Model-only selection retains the caller’s non-model fields; Agent selection changes the base and uses the normal history rules. The policy must declare which kind it selects, so a model choice cannot silently change memory or instructions.

Decision Contract
Eligibility Filter unavailable provider/account/model, required modality or structured output/tool support, context limit, authority and remaining resource cap before ranking
Ranking Versioned ordered deterministic rules over explicit task tags, required capabilities and caller preferences; model-assisted ranking is a separately enabled later mode
No match / unavailable Return a typed no-eligible-candidate error, or use an explicitly configured eligible fallback before inference starts; never broaden authority
Trace Record policy version, eligible candidate IDs, exclusions, chosen ID and rule identifier; avoid raw user content and unsupported cost/latency claims
Stability Pin selection for retries/resume; new invocation may select again. Never switch an already active tool loop automatically
Evaluation Fixed fixture cases for routing correctness, no-match, denied candidate, unknown price metadata and deterministic replay; report measured quality/cost/latency on an approved corpus before claims

For one Agent-kind policy, all results are saved Agent IDs: task tag=classify and structured-output capability required → the first eligible saved Agent configured with a selected small model; task tag=code-edit and tools required → a selected saved coding Agent; otherwise → a specified saved default Agent. A separate model-kind policy returns only model references and retains non-model fields. Candidate IDs and thresholds are user-configured from the available catalog, not hardcoded product rankings. Missing price/latency metadata means unknown, not free or fast.

Known integration risks and resolved limits

Risk Required treatment
Memory content indirectly appears in derived history Propagate write restrictions through context dependencies and generated summaries; test cross-Agent transfer, not just original node ingestion
A plugin cannot enforce namespace isolation Expose unsupported readiness; block requested scoped binding, do not claim prompt-only isolation
Concurrent files/default index lifecycle Journal with recovery and idempotence; mutation authority remains in one manager
Old clients overwrite newly typed fields Dual-reader/conditional-write compatibility and explicit errors; no silent downgrade
Configuration snapshots contain personal instructions Protect with existing execution storage ACLs/retention; diagnostics show hashes/references, not prompt text
Expanding UI before runtime supports fields Feature readiness follows verified backend support; prototype status remains explicit

There is no unresolved product decision required to begin P0. Exact consumer file paths and backend-specific revocation support are implementation discovery items with the fail-closed behavior specified above. A backend that cannot meet it stays unsupported; implementation convenience does not silently weaken the contract.
