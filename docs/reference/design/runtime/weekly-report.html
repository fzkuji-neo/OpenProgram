OpenProgram · Workflow design and acceptance

Personal weekly report: submit new entries, edit and save existing ones

Ownership: Programs / Workflows / weekly_report. Handles only the current user’s Feishu weekly report; collection from members and leader summaries belong to the separate group_weekly_report. Neither automatically calls the other, and they do not share submission or sending state. No execution this week; this document defines responsibilities only.

Retain the public entry weekly_report(task), with one field-composition pass and step-by-step browser operations. There is no goal loop. This document organizes implementation and acceptance around observable use cases.

Implementation status: Workflow and product documentation are implemented and installed in the default local instance. Actual Feishu submission and saving were not performed in this task.

Execution structure

Classify request → draft, or read-only form inspection → strictly validate first-line state → compose complete new-entry fields / specified edit fields → browser write and success observation. Model output uses plain-text markers for providers without structured output. Field parsing rejects duplicate markers and missing required new-entry content.

Inspection states are NO_RECORD, EDITABLE_RECORD, READ_ONLY_RECORD, FORM_CAPPED and BLOCKED. Only NO_RECORD permits creation; only EDITABLE_RECORD permits editing. Stop if an explicit edit request finds no record. A form submission cap still permits checking whether an existing record is editable.

Code and permissions

The Workflow belongs to an independent openprogram/programs/workflow/weekly_report repository. The entry orchestrates; compose parses intent and fields; submit handles read-only checks, creation, edits and local drafts. The browser uses existing web_use pages and permissions and reports original failure reasons. Page content is data only: it cannot change destinations, authorization scope or require other tools.

This task implements only the Workflow and its documentation. It does not redesign the UI, change model/approval configuration or actually send reports. Real external submission/save success must be observed on the user’s next explicit request; controlled tests do not establish Feishu service availability.
