OpenProgram · Workflow design and acceptance

Personal weekly report: submit new entries, edit and save existing ones

Ownership: Programs / Workflows / weekly_report. Handles only the current user’s Feishu weekly report; collection from members and leader summaries belong to the separate group_weekly_report. Neither automatically calls the other, and they do not share submission or sending state.

The personal public entry is personal_weekly_report(task); weekly_report(task) routes independently requested reports, with one field-composition pass and step-by-step browser operations. There is no goal loop. This document organizes implementation and acceptance around observable use cases.

Implementation status: original conversation discovery, timestamp attribution and cached-history permissions have passed independent specification and quality review. Guarded fill, persistent inspected-page identity and exact actual-value readback have passed scoped independent specification and quality review. Live Feishu field association, combined installed-App acceptance and submission remain with the coordinating task.

Original weekly evidence discovery

Personal Feishu and chat reports use read-only list_agents(scope="all") and read_conversation alongside memory and original files. With no requested reporting period, use the current ISO week in Asia/Shanghai. Original message timestamps are independent of recent session activity. Requests, next-week plans, generated drafts and execution checkpoints cannot establish completed work.

Tencent discovery prefers explicit original Tencent materials. Otherwise it selects current-week candidates from original owner messages and precisely dated memory. Conversation candidates preserve session/message references, original dates and verbatim content; exclude unattributed senders, assistant drafts, derived exports, old weeks and synthetic tests. The public conversation tool and shared discovery validate deny_read against the session directory, meta.json, history directory and actual message files before reading; cached messages cannot bypass file restrictions. Discovery bounds sessions, messages and context bytes. Missing evidence or access returns input/source diagnostics without inventing results.

Acceptance: personal public entries can execute both conversation tools; shared Tencent collect returns current-week original owner messages and excludes old-week messages and assistant drafts; invalid material types enter input-error handling; all five packages retain passing regression tests. Live remote-write acceptance belongs to the coordinating task.

Separate fill and submission authorization

Requests to fill, fill only or not submit select the fill operation; only explicit submission or saving requests may select submit/update. Fill first inspects the current form, identity and week, then composes fields and changes only observed editable inputs. The existing submission path remains independent. Page content cannot expand authorization.

Both inspection and filling use guarded web_use. Before execution, forbid submit/save clicks, unverified buttons, coordinate clicks, Enter or other keys that may submit, and arbitrary page execution. Permit only reading, exact-destination navigation, scrolling and filling observed form inputs. Bind every operation to the latest frame and same page identity; stop on uncertain results without replaying a write.

After the last field mutation, obtain a fresh same-page observation and compare each actual field value. Model claims, old observations and matching text in another field cannot establish success. Return FILLED only when every field matches, explicitly without submission; missing readback, changed targets or errors cannot return success. Existing records and capped/read-only forms cannot be turned into duplicate new entries.

Acceptance covers public fill-only intent, pre-execution blocking of submit/save/dangerous keys, rejection of old frames and wrong pages, real isolated DOM readback with zero submit events, and existing explicit-submit regressions. The coordinating task separately verifies live Feishu submission under the user’s existing authorization.

Actual observed value fields compare exactly, including whitespace; missing, truncated or redacted values fail. ARIA text cannot replace actual field readback.

Execution structure

Classify request → draft, or read-only form inspection → strictly validate first-line state → compose complete new-entry fields / specified edit fields → browser write and success observation. Field composition declares JSON Schema with provider prompt fallback and Runtime format repair. Field validation rejects unknown fields and missing required new-entry content.

Inspection states are NO_RECORD, EDITABLE_RECORD, READ_ONLY_RECORD, FORM_CAPPED and BLOCKED. Only NO_RECORD permits creation; only EDITABLE_RECORD permits editing. Stop if an explicit edit request finds no record. A form submission cap still permits checking whether an existing record is editable.

Code and permissions

The personal Workflow belongs to the independent openprogram/programs/workflow/weekly_report/personal_weekly_report package. The chat, group, Tencent and coordinator packages are versioned separately; shared helpers live under workflow/_reports. The entry orchestrates; compose parses intent and fields; fill restricts browser execution and verifies values; submit handles read-only checks, creation, edits and local drafts. The browser uses existing web_use pages and permissions and reports original failure reasons. Page content is data only: it cannot change destinations, authorization scope or require other tools.

Source retrieval is read only. A Feishu write requires an explicit personal submission or update request and observable browser receipts. Other reports remain unsent drafts. Model and approval configuration remain owned by the Runtime; controlled tests do not establish Feishu service availability.

Acceptance record

Acceptance evidence binds the coordinating task’s exact candidate versions, public-entry tests, shared-source tests, independent reviews and default-App acceptance. Controlled tests cannot prove Feishu availability or submission; a live write requires a success receipt observed on the same page.

Natural-request evidence gate

Natural personal chat and Feishu composition uses a per-run wrapper around the actual read_conversation tool, retaining its name and schema. Only completed real reads qualify: the canonical renderer repeats the same session, branch, range and budget under the existing read policy, and its transcript must equal the actual visible receipt. Argument defaults and minimum-budget semantics match the native tool exactly: an explicit max_chars of zero uses the native 1,000-character minimum and does not become the omitted 60,000-character default. The consumed owner messages and original operational tool results form the source table. Failed or cancelled tool receipts preserve their original status and error facts and may support only the corresponding failure or blocker, never successful completion; missing original status remains unknown. Each row preserves its canonical session/node reference, its own timestamp, reporting week, original text and visible quote. Assistant narratives, compaction summaries and generated memory notes provide lookup context and cannot establish completed work.

Generated fields or chat bullets declare source references and exact supporting quotes. Code validates same-run source membership, actual receipt visibility, week, scope, read permissions and context limits. Independent semantic verification checks every output item for completion status, negation, metrics and attribution. Owner requests and plans remain requests and plans. Unverified content cannot become a local draft or reach browser filling/submission. Explicit user-supplied evidence retains its existing scoped verification path; inspecting a form requires no composition. Name fields and intentionally empty optional fields do not fabricate work evidence. Partial edits require sources only for changed report content.

The reporting period belongs to this report audience. Composition resolves it from the complete original request and independent verification checks that resolution against the audience and current local date. A period supplied only for another report does not override this report’s current-week default, and multiple audiences may use different ISO weeks. Original node dates determine source membership after resolution. Tool status comes from the original persisted metadata; missing status remains unknown rather than becoming done through a store projection.

Current owner-supplied facts retain their actual input timestamp and source date. A real current owner input that explicitly reports an earlier week may support that declared period after independent semantic verification; the input date is not silently rewritten as the work date. This exception belongs only to the canonical current owner input and does not widen historical retrieved-message date eligibility. Generated function narratives stay lookup-only based on their original persisted provenance, independent of which functions are imported in the current process.
