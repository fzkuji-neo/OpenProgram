OpenProgram · Harness design

Restart recovery and Goal design for the complete session runtime

Design question: after an App or worker restart, how do previously running sessions and Goals automatically continue, restoring subtasks, approvals, context, and usage without repeating unknown writes or resuming work the user explicitly stopped?

ReferencesStateRecoveryAcceptanceCostInterfaceImplementationImplementation status

For framework development and product acceptance. This page defines the target design; implementation status is collected at the end. Scope includes Web, TUI, ACP, background Jobs, and authorized subtasks. Goals use the same chat execution layer. Retain the Python Workflow API without duplicating the execution engine, introducing a general scheduler, or promising exactly-once execution for arbitrary external operations.

Verified current behavior · Automatic recovery contract · Complete recovery-state matrix · Failure acceptance matrix

Core contract:Resuming a session does not mean retrying its tools. An old turn may end as interrupted while its operations remain outcome_unknown; a new turn first checks actual state. Goal, Todo, chat history, and incurred usage remain preserved.
  1. 1. Save the objectiveOriginal objective, completion conditions, permission scope, and explicit budget.
  2. 2. Work through ordinary chatThe agent maintains Todo and uses existing tools and approvals.
  3. 3. Check at turn completionSettle usage and decide whether to continue, wait, pause, or verify acceptance.
  4. 4. Accept completionSubmit achieved once evidence supports every condition; otherwise continue working.

There is no default round cap. Round count is diagnostic information, not a substitute for progress or stopping conditions. Retain the short state tools create_goal/get_goal/update_goal; they only read and write objectives, rather than executing the entire task within one function call.

Automatic recovery contract: run intent survives the process

Complete durable run_intent on top of existing admission / command / restart intent rather than adding a parallel scheduler. It records work_id, original input and unconsumed messages, desired_state (run / paused / cancelled / done), latest valid control version, permission scope, objective revision, execution host identity, parent/child relationships, last committed progress, and recovery policy. Acknowledge acceptance to the client only after reliably saving the original user request.

By default, automatically recover previously authorized work whose state remains run, consistently for ordinary sessions and Goals and without requiring the user to reopen the session. Preserve pauses, stops, completion, outstanding approval, and exhausted budgets. Ordinary requests without a Goal continue only until that request finishes, not as indefinite Goals. Background work retains its prior authorization and concurrency quota; restart does not authorize additional subtasks.

Closing a window or reloading the frontend only disconnects the client; “quit and stop all tasks” must persist user stop intent. Ordinary App exit, upgrades, worker crashes, and machine restarts do not implicitly mean user Pause. Graceful shutdown first stops new admission and saves accepted controls and checkpoints, then exits the worker; forced shutdown recovers from the last committed records. Client-only drafts without server acknowledgment must not be represented as submitted requests.

Remove the hidden two-hour recovery expiry. Long downtime preserves run intent, but continuation rechecks directory, host, model/tool availability, credentials, current permissions, and budget. Missing resources or revoked permissions show precise waiting reasons, without switching project, account, or model or expanding permissions automatically. Explicit automatic-recovery disabling remains effective; old paused records with unknown reasons stay paused with an explanation rather than being guessed to have been running.

  1. Load facts:Read run intent, user controls, messages, checkpoints, effects, waits, resources, usage, and projection cursors. Read/migration failures show recovery failure without clearing old state.
  2. Confirm ownership:Reconnect live executors; exclude dead executors through generation fencing. Only one host recovers each work item. Single-host recovery must not silently become cross-host takeover.
  3. Repair context:Merge real results, supply missing tool outputs, and record interruption. Resume from a complete safe checkpoint when available; otherwise start a new turn with the same work_id without re-appending user input.
  4. Decide:User stops take priority, followed by approval, permissions, budget, resources, and unknown effects. Runnable work becomes queued; dependency waits become waiting; faults expose retryable reasons. Persist all decisions in the same control service.
  5. Admit and continue:Use existing fair scheduling and resource quotas; derive a stable continuation key from work_id + control version + predecessor commit point. Admission persistence and recovery-intent consumption must leave no duplication window; converge cross-database steps through a retryable outbox.
  6. Restore the interface:App/Web/TUI reconstruct from canonical snapshots and monotonic event sequences, showing recovery, queueing, working, waiting, or failure; display is not a second control implementation.

Recovery coordination belongs to existing execution control. The server and JobRunner may call the same idempotent entry point but cannot make independent recovery decisions. UI orphan cleanup repairs only derived projections; Goal.after_terminal submits continuation requests only for the current version. Temporary faults use durable retry times and bounded backoff instead of idle model calls. Persistent faults retain pending-recovery records and show the error plus Retry / Pause / End without deleting tasks.

Interruption recovery: confirm execution ownership before restoring context

  1. Confirm the old executor:Use the existing owner lease / generation; do not write repairs when the lease is uncertain or storage unreadable. A disconnected connection alone does not prove process death. Reject subsequent writes from the old generation.
  2. Verify child processes:Reconnect trackable live processes and wait or explicitly cancel; do not treat a running shell as stopped. Preserve unknown-effect records for unreachable remote operations.
  3. Choose exactly one recovery mode:Only reconnect a live owner. If death is confirmed and a verifiable safe checkpoint exists, create a new attempt under the same execution. Only when no reliable checkpoint exists, acquire exclusive recovery ownership, fill missing outputs using a stable repair key, end the old turn as interrupted, and admit a new turn. These choices are mutually exclusive and bind to the same durable recovery decision, control version, and continuation key; never resume a checkpoint and start a new turn together. Checkpoints must cover committed effects and satisfy current permission, wait, and safe-point contracts, without replaying unknown writes. Repeating repairs has no side effects; real results take priority and no usage is fabricated. Append late verifiable receipts as reconciliation events that replace synthetic placeholders in subsequent context.
  4. Restore run intent:Previously running ordinary requests and active Goals automatically enter unified admission; user-paused work does not resume automatically. Only specific permission, budget, resource, or unknown-operation issues need human intervention; restart itself is not a reason to require manual Resume.
  5. Decide tool behavior:New turns know which calls never started and which outcomes are unknown. Old unknown results do not globally block investigation or independent work; related writes retain original approval and recovery restrictions.

Safety boundary: read_only / idempotent / state_probe capabilities come from trusted tool registration and implementation identity saved at execution. Do not accept model claims of read-only behavior or infer them from a name containing read. General shell, third-party MCP, and custom tools default to unknown. Recovery turns related to unknown writes initially allow only trusted reads and state queries. Without reliable relevance determination, do not automatically allow writes; reconcile first or obtain explicit user authorization.

Request-history repair first matches the nearest call by original call ID, then converts provider IDs. Existing real outputs take priority; duplicate outputs use the last saved real record. Missing results get deterministic unknown placeholders. Calls and results are adjacent in the request projection while user-message order remains intact; original history is unchanged. Results without corresponding calls are not sent as valid tool-protocol items. Interrupted responses retain partial text and an interruption marker without reusing incomplete reasoning signatures. Ambiguous duplicate call IDs within one response produce an explicit error rather than guessed execution facts. This conversion grants no execution permission and cannot replace recovery decisions.

Recovery permission checks use the same conversation provenance to scope old executions and invoked Jobs, without expanding to all executions in the invoked session. Only actual built-in read, grep, glob, and list execution functions qualify for read-only investigation; names, acceptEdits flags, and plugin declarations cannot replace implementation identity. With unknown old effects, all other operations require one-time approval; bypass, automatic classification, and existing allow rules cannot waive it. Durable approval binds to the new tool call and unknown-effect set; changes to that set require fresh approval and do not erase old effects. Reject execution if recovery state cannot be read. This check is a prerequisite for restricted new-turn recovery; it does not independently change old execution state or enable Resume.

This is neither an exception for one session nor a repair restricted to allowlisted files. Ordinary chat and Goals share the recovery entry point. Old effect audits may remain unresolved while their chat turns end as interrupted; adjust the old constraint that any unresolved effect prevents turn termination accordingly.

Verification presentation: an explicit verification identity accompanies the assistant message from the first streamed event through history replay. Raw report text remains immutable evidence, not ordinary reply prose. The chat shows a localized pending or accepted-result summary and collapsed requirement assessments, evidence references and raw output. Only the authoritative accepted candidate permits a success summary; malformed, interrupted, superseded and unaccepted reports never imply completion. Older messages are identified through their canonical execution input, not JSON shape. Presentation does not change stored report content, evidence hashes, permissions or Goal completion rules. The implementation passes independent specification and quality review, with regression coverage for streamed and historical rendering, altered report hashes, malformed fields, ordinary JSON, long-history pagination and accepted results arriving before their assistant messages. Source verification and installed-App acceptance remain separate release gates.

Todo manages the plan; acceptance manages the objective

At creation, preserve the original objective and extract verifiable requirements; ask the user only when ambiguity would change scope. The working agent maintains Todo for multi-step tasks; simple tasks may omit it. Every necessary requirement has an evidence checkpoint; adding or removing Todo must not implicitly remove original requirements.

Ordinary work turns do not run a second judge. Enter verifying when the worker submits a complete candidate or all required Todo items finish without verification. First check current revision, required Todo, unfinished subtasks, and relevant unknown effects, then run one independent read-only acceptance review. The worker's completion text is not an acceptance fact.

Acceptance returns met / unmet / unknown and evidence references for each requirement. Deterministic requirements inspect actual test receipts, file versions, and runtime state; semantic requirements use independent model review. Tests retain ordinary tool approval and budget rules: calling shell verification does not make it read-only. Missing evidence returns to another work turn rather than fabricated acceptance.

Only the current goal_id + revision + verified result version may submit achieved. Recheck evidence versions and compare the Goal control version before committing. Controlled artifacts use version numbers or content digests; external facts retain verification time and query receipts without claiming atomic verification across all external systems. Completion means conditions held at that verification; it does not automatically monitor files or reopen the Goal afterward. Later edits, new requests, or explicit monitoring require separate acceptance. Human waivers must be explicit objective revisions with reasons; the agent cannot reduce scope itself. Independent acceptance can also err and does not guarantee absolute correctness.

Judge lack of progress by changes in results and evidence, not tool invocation count. Enter blocked only when the same real blocker recurs consecutively and no independent work is available. Waiting with a live handle enters waiting without idle model turns. A fixed total round count is not evidence of blocking or completion.

Waiting uses existing durable waits and execution-terminal notifications, saving work_id / Goal revision, handle, observed version, and unique consumption key. Completion, failure, or timeout notifications admit exactly once only if intent remains run, versions match, and no other current execution exists. Existing reconciliation polls for missing notifications with backoff. Save results arriving during restart, then automatically continue under the same rules. Pause, cancel, or revision invalidates old wakeups without discarding results; query timeout does not imply the external operation stopped.

Cost: attribute per request, settle per receipt

Fix goal_id / revision / turn_id / request_id before dispatch. Ordinary chat after pausing has no old Goal attribution. Subagent and acceptance requests explicitly inherit attribution; count each receipt once rather than adding both parent totals and child details. Retries are new provider attempts and count separately when they incur actual consumption.

Streaming cumulative usage updates a watermark for the same attempt; do not sum cumulative snapshots. Update Goal projections only after durable receipt writes succeed. Temporary failures retry with the same idempotency key, and restart can reconstruct statistics. Late receipts remain attributed to the original Goal even if paused, ended, or edited.

Store known tokens and known prices separately. Pricing-table changes do not rewrite historical quotes. Display estimates, known values, and partial unknowns separately, such as “Known $0.42; usage unknown for 1 additional request.” Preserve historical cursor data without inventing attribution. Accumulate active time from durable start/stop records, excluding pauses and downtime and without resetting on recovery. When an executor disappears, preserve its last heartbeat; crash-discovery time is not stop time. Show the known duration lower bound and unknown interruption interval. Late usage does not restart paused timers. If an explicit time limit cannot be verified, stop new admission without adding a default limit.

Budgets are unlimited by default. With a user-set hard cost budget, unknown prices or unverifiable consumption cannot be treated as available balance; pause new paid admission and explain why. Reserve a maximum request amount when calculable; otherwise do not promise absolute prevention of overspend. Recheck explicit budgets after ledger reload and before execution recovery or acceptance.

Background Jobs save Goal identity at the real active caller's admission boundary, restore it at startup, and clear unrelated temporary attribution. Cross-session calls preserve original caller provenance without creating a cross-session canonical parent. Goal and Job share start/settlement transactions in usage.db; receipts save Job reservation identity so metering can be reconstructed without an in-memory governor after restart. Unknown tokens and unknown costs retain separate reservations; partial cumulative data records only lower bounds. Expired unstarted reservations cannot dispatch; started requests are not automatically released. Hard budgets accept only audited input/output limits, explicit prices, and service tiers and add no default restriction to Goals without budgets.

Restart failure acceptance: more than testing Resume once

Create work through public chat, Goal, Job, approval, and control entry points; perform real termination using isolated test storage and non-user-visible process tests. Do not terminate the user's current work to demonstrate recovery. Final visible App acceptance uses only the default instance and first confirms that updating will not overwrite unrelated work.

  • Cover frontend reload, normal App exit, graceful worker restart, forced worker termination, downtime beyond the old two-hour window, and another crash during recovery. Test host-restart semantics through process-identity changes; list actual OS reboot separately as unverified and do not reboot the user's machine yourself.

How controllers stop when tasks cannot be completed

Native Goals automatically decide whether to continue after ordinary agent turns, so they must distinguish incomplete work, missing external conditions, impossible objectives, and persistent lack of meaningful progress. Round limits alone cannot distinguish these causes; they only bound worst-case execution length.

Why invoking a tool is not progress

Tool calls prove actions, not movement toward acceptance conditions. Stall detection should compare newly added evidence refs, passed deterministic gates, unfinished checklist items, and external-state changes across consecutive turns. Repeated identical evidence should enter stalledrather than reset the stall counter.

Waiting must not consume work turns

Questions first enter a durable asynchronous queue; the controller continues while safe independent work remains. Enter the following state only when all remaining work requires answers: waiting_user. CI, background processes, time, or external events enter waiting_external; explicit resume is currently required.

Conclusion:Semantic evaluators alone cannot guarantee convergence in any of these implementations. Reliable controllers need hard budgets, evidence-based stall detection, explicit blocked/impossible/waiting categories, and waiting states released only by external events.

Reuses the Hook protocol

  • An ordinary Stop hook may return decision:"block" and reason; the reason enters Claude's next-turn context.
  • A prompt hook may return model-generated ok, reason, impossible./goal adds condition, status display, and recovery to this general mechanism.
  • stop_hook_active prevents unconditional recursion by extension scripts; the runtime forces termination after 8 consecutive Stop-hook stop prevention events.
  • The Goal evaluator only sees evidence already in the conversation; it does not read files or run tests.

Waiting, errors, and budgets

  • Do not evaluate while background shells/subagents run; completion results trigger new turns. Long waits use backoff check-ins, with at most 3 automatic idle check-ins between user inputs in interactive sessions.
  • Several consecutive turns without tool progress stop automatic looping but retain the Goal for evaluation after the next user prompt.
  • Unrecoverable auth, balance, uncompactable context overflow, or model-unavailability errors clear the Goal; transient errors retain it.
  • Goal has no independent typed budget; turn/time termination conditions can be included in the condition. Outer print mode separately provides --max-turns and --max-budget-usd.

Independent judgment and compatibility constraints for Python Workflow

The independent work/judge contract below applies only to Python Workflow. Chat uses the design above: no judge during ordinary work turns, with independent acceptance only on a completion candidate.

Already adopted

Codex control-plane data model

Current snapshots already have stable goal_id, a separate per-execution run_id, typed status, budget/usage, time fields, and CAS version. User controls handle pause/resume/edit/answer/limit/clear; the judge only proposes candidate verdicts.

Adopt directly

Hermes three-stage judgment

The completion contract explicitly defines outcome/verification/constraints/boundaries/stop_when. Deterministic gates run first; semantic judgment runs only after they pass. Asynchronous dependencies enter a wait barrier instead of repeatedly starting work turns.

Adopt directly

Claude Code background-task deferral

If background tasks remain when a work turn ends, neither accept completion nor immediately continue. Completion events resume work; long waits use bounded backoff check-ins and supply the controller with the running-task list.

Already retained

OpenProgram tool-capable judge

An independent judge uses read-only inspection tools to verify files and command results directly and returns typed verdicts. The deterministic gate executor remains future work.

Use in combination

OpenCode Todo as progress projection

Goal checklists should have independent typed-item tables and events for stable UI display. Completed checklist status is only evidence, not equivalent to overall Goal completion, and UI state must not drive the controller.

Combine as needed

OpenClaw scheduling as wait adapter

Future times, CI, external events, and background jobs should not consume Goal turns. GoalRun stores wait handles; scheduler/task subsystems wake it; the controller re-evaluates or continues on the event.

Not adopted

Relying only on worker completion declarations

Codex self-report suits a low-cost general control plane, but OpenProgram already has an independent judge and should not regress to relying only on update_goal(complete). That tool may signal a candidate, while evaluator/controller commits final state.

Current boundary

Versioned session snapshot

extra_meta.goal Schema version, entity IDs, CAS writes, and migration reads already support the current single-session controller. This is not an append-only evidence repository; separate storage is needed only when audit-grade evidence history is required.

Not adopted

Naming Todo, Plan, or Cron as Goal

These address decomposition, change permissions, and timed triggers respectively, without the full semantics of completion conditions + judgment + automatic continuation. APIs and UI should retain those distinctions.

Compatible Python Workflow contract and remaining extensions

Independent judges, role configuration, and recovery checkpoints in this section belong to Python Workflow. Chat entry points share state storage and budget controls but do not invoke this controller.

Goal adds no second agent loop. The controller sits above existing session/dispatcher code, and work still executes through public agent() ; in the diagram, implemented denotes current code, andtarget denotes unimplemented extensions.

  1. Spec and run share a versioned snapshot.goal_id remains stable across resume, whilerun_id identifies one execution. Editing creates a new revision and refines the spec/checklist again. Refinement only restates user requirements and necessary correctness checks, preserving approximate constraints such as “about” without adding format ratios, benchmark names, numeric thresholds, or reference-work comparisons. Significant ambiguity remains a pending question.
  2. Stop policy checks accumulated budgets at phase boundaries.Rounds, tokens, active elapsed time, and cost accumulate across resume; waiting and pause consume no active-time budget. Work turns default to 300 seconds, and silent provider streams remain subject to the whole-call deadline; cumulative budgets are not precise preemptive limits on the current phase.
  3. The controller commits state transitions.Each phase saves a checkpoint; pause/edit/answer/cancel compete with old controllers through CAS versions, preventing stale execution from overwriting new state.
  4. The evaluator is an independent inspection agent.It returns met, unmet, blocked, impossible, waiting_external, needs_user, and can_continue. Besides local inspection it provides web_fetch, web_searchwith existing URL and network-permission checks; web-tool failures propagate as structured is_error receipts. If a judgment includes a failed tool-inspection receipt, the controller rejects metand re-evaluates first; persistent failure reports judge failure. This conservatively requires one acceptance evaluation free of inspection errors; successful receipts alone do not prove all semantic requirements. The general deterministic gate executor remains unimplemented.
  5. The asynchronous question queue does not block unrelated work.Questions accumulate and can be answered individually. Active execution consumes answers at the next boundary and enters the following state only when all remaining work requires answers: waiting_user. Questions occupy only the Goal detail panel without replacing or disabling the ordinary composer.
  6. Restart recovery uses an explicit new execution.Startup reconciliation converts leftover execution state to paused_recoverable; recovery reuses the snapshot rather than resurrecting an old call stack.
  7. External scheduling is a target extension.waiting_external State exists, but automatic job/timer/event wake handles are not implemented. Goal controllers sharing a session store on one machine use a separate OS file lock; startup recovery takes the same lock to avoid rewriting live siblings.

Controller saves use CAS. Concurrent updates within the same run merge the latest confirmed snapshot, current-round state, and latest disk state under the session write lock, without unbounded retries. Implementation status and evidence boundaries

Chat Goals use existing ordinary chat execution and durable completion notifications for continuation; display projections do not rewrite run intent. There are no default round or recovery-expiry limits, while explicit user limits remain. Complete Python, Web, CLI, Desktop, documentation checks and browser regressions after an independent build passed; skipped tests do not prove capabilities. Evidence boundaries: unknown outcomes always remain in effect records; new side effects require one-time approval for the current operation, and ordinary chat recovery never reruns old tool calls. All Todo complete produces only an acceptance candidate. Independent ordinary chat checks actual reads or session evidence against the original objective and fixed requirements; before commit, recheck control version, evidence digest, related background processes, and execution state. Request statistics retain Goal/revision/execution identity and prices; the durable ledger restores cumulative usage watermarks, child attribution, reservations, and joint settlement. Missing receipts remain unknown; old session statistics are not inferred into new attribution. Sudden executor loss counts only verifiable duration lower bounds and excludes downtime. Completion acceptance remains evidence-constrained model judgment, not a guarantee of absolute correctness.
