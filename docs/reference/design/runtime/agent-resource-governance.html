00 Scope and final decisions

This design governs agent/Job eligibility, per-session queue and execution capacity, parent-child budgets, actual usage, termination, and recovery. Existing agent.max_spawn_depth, agent.max_spawn_fanout, agent.max_messages continue governing call topology and cycles, without reinterpretation as resource budgets.

DecisionConclusionReason
max_live_globalDo not addThe existing process-level ThreadPoolExecutor already uses OPENPROGRAM_JOB_WORKERS to control global execution capacity, default 4. Another equivalent setting would create conflicting global limits. The UI displays effective worker capacity read-only.
max_live_per_sessionAddPrevent one session from consuming every worker; count only tasks actually executing whose stop has not yet been confirmed.
max_queued_per_sessionAddLimit admitted but not running tasks to prevent an unbounded persistent queue. Queued tasks consume no live slot.
max_jobs_per_sessionAddLimit cumulative successful admissions over the session lifecycle; terminal tasks do not return this quota.
token / cost / runtime / idleInclude all, with different enforcement conditionsTokens and time are enforceable with safe upper bounds and cancellable boundaries; costs are enforceable in advance only when prices are known. Unknown cost must not be treated as zero.
Factual ledgerReuse usage ledgerActual provider usage remains recorded only in usage_events. Admissions and unsettled reservations are execution state, not a second actual-usage ledger.

Outside this designBackground-session UI, MCP server, purchases or top-ups, organization billing, and multi-machine cluster scheduling. These systems may later reuse shared DTOs, reason codes, budget scopes, and reservation protocols; their product interactions are not assumed here.

Adopt

  • Separate global scheduler capacity and per-session live limits.
  • Count live, queued, and cumulative tasks separately.
  • Stable job ids, cascading cancellation, and user-queryable state.
  • Show tokens, elapsed time, and reason together in task views.

Adapt or reject

  • Reject direct adoption of competitor values.
  • Reject depth, fan-out, or tool permissions as substitutes for resource admission.
  • Reject process-local semaphores alone; admission must be durable and atomic across processes.
  • Do not describe caller timeout or a terminal marker as execution termination.

04 Inspect and configure global defaults and session overrides

Current behavior
The config schema has only depth/messages/fanout. Environment variables control worker capacity, which task pages do not show; no session resource override exists.
User impact
Users cannot limit a session’s worker, token, cost, or time use, or confirm effective values before creation.
Gap
Multiple equivalent global, parent, and child settings make precedence difficult to explain; using 0 for both unlimited and disabled perpetuates ambiguity.
Target behavior
One minimal agent.resource_limits object holds global defaults; session metadata overrides matching fields. APIs always return source, configured, and effective values. Tasks may only tighten effective session limits.
agent.resource_limits:
  max_live_per_session: integer | null
  max_queued_per_session: integer | null
  max_jobs_per_session: integer | null
  max_total_tokens: integer | null
  max_cost_usd: decimal-string | null
  max_runtime_seconds: integer | null
  idle_timeout_seconds: integer | null

All non-null values must exceed 0; null means unset/inherit. For compatibility, queued, cumulative, and the four budget types are disabled by default.max_live_per_session defaults to current scheduler capacity when unset; otherwise its effective value is the lesser of configuration and scheduler capacity.OPENPROGRAM_JOB_WORKERS remains the sole source of global execution capacity, exposed through the read-only scheduler_capacity field.

Only the owner may change global defaults and session overrides. Agent/task requests may supply only stricter token/cost/runtime/idle budgets, without changing live, queued, cumulative limits or increasing any owner limit. Extend existing config get/set with these fields and reuse session metadata; do not create a second quota configuration service.

max_total_tokens and max_cost_usd count governed agent/Job invocations carrying job_id within the session; ordinary foreground main conversations are excluded.max_runtime_seconds and idle_timeout_seconds is a time ceiling for each Job and its ancestor scopes. Changes to live/queued/cumulative limits do not terminate existing live/queued work, but immediately constrain new admission or queued → live; token/cost changes apply the new session ceiling at the next reservation. Runtime/idle defaults affect only subsequently admitted Jobs, avoiding retroactive deadlines.

05 Admission and atomic reservation when an agent creates a task

Current behavior
Agent tools, Web spawn, sync/async runners, and busy-target inbox use different creation paths; fan-out slots are process-local and may be consumed before later validation fails.
User impact
Identical requests can differ by entry point; concurrent frontends/processes may pass non-atomic checks simultaneously; failed creation may leave Job, branch, inbox, or count residue.
Gap
No single admission API, cross-process transaction, idempotent job id, or side-effect ordering exists.
Target behavior
Every execution-task creation path must call ResourceGovernor.admit_job. Perform pure validation first, atomically check depth/fan-out and resource limits and reserve in SQLite, then create Job/branch/inbox and publish events only on success. Rejection creates no Job.

Unified coverage

  • Synchronous and asynchronous agent(); agent(to=...) busy-target precreation; run_agent_turn_async.
  • WebSocket/API spawn; model tools; any future direct JobRunner.spawn_job entry point.
  • Retries with the same job_id and request fingerprint are idempotent reads and cannot increase fan-out, cumulative counts, or queue reservation again; differing content returns quota.admission_conflict.
  • send_message itself creates no task and consumes no cumulative count; if it triggers a model call in governed lineage, that call still counts against the corresponding budget.

Durable intent across SQLite and jobs.json

  1. Generate job_id, admission_id and request fingerprint; validate arguments, target, and permissions without mutation.
  2. In the usage DB’s first BEGIN IMMEDIATE transaction, check depth, per-turn fan-out, and session/parent remaining capacity, insert a preparing admission, reserve one queue slot plus provisional fan-out and cumulative increments, then commit.preparing must be durable before jobs.json writes; every concurrent admission check includes its provisional occupancy to prevent cross-process overallocation.
  3. Use openprogram._compat.flock to protect per-session task-file read-modify-write and persist the Job. Do not broadcast or create other irreversible side effects yet.
  4. In a second BEGIN IMMEDIATE transaction, change admission from preparing to queued, finalize provisional fan-out/cumulative counts, and commit; only then create branch/inbox and broadcast accepted status.
  5. Any failure triggers idempotent compensation. On restart, a durable preparing with a matching Job is finalized in the second transaction; without one, release queue and provisional counts transactionally. SQLite transactions must not span jobs.json file I/O.
Rejections use the stable structure: {accepted:false, job_id:null, reason_code, retryable, effective_limits, usage, capacity}. A full queue is usually retryable; exhausted cumulative or parent budgets are not, unless the owner raises limits or creates a new session.

06 Queueing and live concurrency

Current behavior
The runner submits immediately to the executor, whose internal queue holds waiting work; Job state moves from pending/queued to running.
User impact
Per-session queued volume is uncontrolled; one session can fill the execution pool and queue; queue position is unstable and undiagnosable.
Gap
No durable dispatcher, per-session fairness, or atomic queued/live exchange exists.
Target behavior
Admission first enters a durable queue. The dispatcher submits only when global worker and session live capacity are available, releasing queue and acquiring live in one transaction. Queued work consumes no live slot.
preparing→ queued→ atomic exchange live→ cancel/timeout stopping→ confirmed exit released

Compatible Job states remain pending/queued/running/completed/cancelled/errored; resource state persists separately.stopping is especially important: a Job may display cancelled, but its live lease cannot return until worker/thread/runtime termination is confirmed. This prevents overallocation when the 30-second watchdog only changes status.

The dispatcher selects the earliest globally ordered admitted_seq task whose session currently has live capacity, skipping temporarily ineligible sessions so their head task cannot block others. The global worker pool still determines total execution capacity.

Only the single execution process holding the existing worker lock may call queued → live and submit to the executor. Web/TUI/CLI/API processes only admit and durably enqueue, preserving the single-worker topology and preventing separate global thread pools per process. Multiple execution workers would require a separate scheduling design.

07 Parent-child budget allocation and tightening-only inheritance

Current behavior
Message/generation budgets inherit through ContextVar and filter tools; Jobs lack token/cost/time fields and atomic constraints on parent remaining budgets.
User impact
A parent cannot limit its whole descendant tree; explicit child budgets have no verifiable upper bound; concurrent children can spend the same parent balance.
Gap
Scopes, shared remaining capacity, and deterministic allocation rules are missing.
Target behavior
A task request may carry one limits object containing only token/cost/runtime/idle budgets. Explicit child limits cannot exceed effective session limits, parent-task limits, or current parent-scope remaining capacity.

Deterministic rule without explicit child allocation

Do not divide the parent budget equally in advance or predict future work from fan-out. Children join the shared parent budget scope. Every provider/tool reservation atomically checks the task’s own ceiling, every ancestor scope, and session scope; the first successful durable reservation acquires capacity. This avoids idle static shares and does not misrepresent current remaining capacity as a guaranteed child allotment.

The UI labels shared_remaining as a shared live balance, not an allotment. Explicit child budgets create stricter local ceilings without permanently deducting from the parent in advance; actual reservations consume parent balance.

08 Metering and enforced stopping for tokens, cost, wall-clock, and idle

Current behavior
Usage events are recorded best-effort after model calls; provider transport has timeouts; Runtime deadlines can propagate but do not represent total task duration.
User impact
Some usage is visible only afterward; concurrent requests each see available balance; unknown prices appear as numeric zero and can mislead; timed-out synchronous threads may keep executing.
Gap
Pre-request exposure reservations, task attribution, unknown-cost semantics, activity definitions, and preemptible boundaries are absent.
Target behavior
The existing usage ledger alone records actual usage; add reservation state in the same DB. Atomically reserve before model/tool calls, settle using final provider usage afterward. Active timers and boundary checks jointly trigger existing cascading cancellation.

Explicit bound for non-preemptible operations

Enforce exhaustion at model-request/tool-call boundaries, with active timers triggering cancellation promptly. Do not describe an executing operation as instantly terminated. Its maximum non-preemptible interval must equal the minimum of declared operation timeout, remaining task runtime, and system cancel grace. Synchronous in-process operations that cannot meet this must move to terminable subprocesses or be rejected for strict-budget tasks; asyncio.wait_for returning does not mean the executor thread has ended.

Accounting delay and crashes

  • Reservation states are reserved → started → settled, or, before provider I/O begins, reserved → released. Release not-yet-started reservations if credential resolution, request configuration, or provider-generator creation fails; after successful start, cancellation, transport errors, or missing terminal usage retain conservative exposure for late settlement of the same reservation. Absence of a first stream event does not prove the provider never received the request.
  • If a request started but final usage is unavailable, retain conservative unsettled exposure; do not fabricate actual tokens/cost or release immediately and allow repeated overspending.
  • Budgeted tasks fail closed if the accounting DB is inaccessible before calling. Post-call settlement failure marks the task errored, stops further calls, and retains the reservation for reconciliation.
  • Existing best-effort recording may remain for non-budgeted legacy paths; governed calls require acknowledged reserve/settle protocols.

09 Slot release and cumulative semantics after cancellation, failure, timeout, and completion

Current behavior
Terminal states are absorbing and cancellation cascades; runner finally cleans process-local maps. A watchdog may mark cancelled while the execution thread remains active.
User impact
Equating terminal Job state with release can admit new work while the old worker still runs; never releasing after crashes permanently leaks slots.
Gap
Job state and resource lease are not separated; cumulative-count return rules are undefined.
Target behavior
Release queue/live only when execution termination is confirmed or lease-recovery rules hold. Increase cumulative count once on successful admission and never return it for any terminal state.

Cumulative counts last for the session lifecycle. There is no implicit reset, and session archiving does not return quota. 10 Restart recovery, cross-process concurrency, and diagnosis

Current behavior
Startup marks all nonterminal Jobs errored: worker died before completion; jobs.json has only a thread lock; the profile worker lock establishes a single-worker execution topology.
User impact
A process crash during admission leaves indistinguishable Job/count residue; two frontend processes may concurrently modify the same jobs.json; “worker died” cannot explain quota recovery.
Gap
Owner instance, lease expiry, preparing reconciliation, cross-process file locking, and structured diagnosis are missing.
Target behavior
Single-worker execution remains supported; multiple UI/API processes compete through SQLite admission transactions. Each live admission carries owner/lease; reconciliation uses intent, Job, and lease facts to prevent permanent quota leaks.

Recovery rules

  • preparing + Job exists: validate admission/job ids, then finalize as queued;preparing + no Job: roll back queue and provisional cumulative delta.
  • queued re-enters the durable dispatcher after restart without consuming live capacity.
  • live/stopping with an absent owner and expired lease: first mark the Job errored under the existing orphan policy with reason error.worker_lost, then release live; another instance cannot claim an unexpired lease. Initially renew every 10 seconds with a 30-second TTL, persisted using UTC wall-clock. If the original owner still holds the worker lock, an apparently expired wall-clock lease must not be released. These are not user quota settings.
  • A lease proves worker ownership, not rollback of external side effects. Preserve worker-lost diagnosis in Job output.
  • All jobs.json read-modify-writes use cross-process flock; SQLite uses WAL, BEGIN IMMEDIATE, and unique keys for idempotent admission/reservation.

This design adds no cluster consensus or remote scheduler. If multiple workers are later allowed, the same job_admissions lease/owner contract may extend, but leader election, clock assumptions, and external-runtime fencing require a separate design.

13 Compatibility, migration, and implementation batches

Compatibility principles

  • Mark old Jobs missing new fields as legacy/unmetered; missing does not mean zero, and historical jobs.json is not rewritten.
  • Existing Job status enums, job ids, broadcasts, and cascading-cancel APIs remain compatible; resource state and reason are optional additions.
  • Existing depth/messages/fanout settings and semantics remain unchanged. They guard topology/cycles and do not count quota.
  • Existing OPENPROGRAM_JOB_WORKERS remains the sole global worker capacity. No new max_live_global.
  • Old-database migration adds only nullable columns/tables/indexes; usage events remain append-only.
