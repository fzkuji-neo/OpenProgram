External Program Run Nodes

Defines DAG views, completed summary handoffs, and chat history for a user directly running a function from Programs, fn-form, or another external entry point. This page covers top-level runs, terminal delivery, and projections of existing execution events, not internal workflow stages.

Design status: chat UI and summary handoff implemented · DAG projection remains a design
Core decision

An external invocation appears in the conversation layer as a rounded-square Program/Function node, branching directly from ROOT without synthetic User or LLM nodes. Substantive workflow results are written to files by default; successful Conclusion handoffs are generated by a separate summary function, not the workflow result body. For other terminal states, the frontend deterministically generates Conclusion from status and error.

End-to-end flow: execution, handoff, and chat projection

One external auto_workflow invocation DEFAULT: FILE ARTIFACTS + SHORT HANDOFF
Default deliveryWrite artifacts to files; chat naturally summarizes work, the main process, and final completion status, without mandatory citations or paths.
Trust boundaryNeither the summary model nor agent previews can authorize body return; authorization reads only the original task.
Failure isolationA failed summary call uses only a conservative fallback and does not change the completed workflow status.

Terminal conclusionThe old summary actually equals the complete return value of workflow(), incorrectly treating report content as a chat summary.After successful workflow completion, call an independent tool-free summary function. It reads the original task, function names and states, and up to 240 characters of operational handoff preview for each function=agent step in the execution record. It reads no call arguments, complete artifact bodies, or result summaries from non-agent functions, preventing intermediate results from entering through later call arguments. Output follows natural chat structure: usually 2–3 overview sentences, optionally a short numbered process for multi-stage tasks, then a completion assessment. Single-stage tasks may omit the list. Include citations, paths, and warnings only when useful for handoff, not as fixed fields. Previews must not restate substantive conclusions. Complete artifacts are written to the current session working directory by default and retained only in files and workflow state.
Summary callThe frontend makes no additional model call.The additional LLM summary call occurs only in the backend on successful workflow completion, reusing the current session’s selected provider/model with tools disabled and a JSON-object response requirement. Call failure or malformed output uses a conservative fallback that does not claim artifact completion, does not change the completed state, and never falls back to showing complete artifacts. Capped, cancelled, interrupted, and failed states skip LLM summary, while the frontend still generates deterministic status or error Conclusions.
Public handoff schemaComplete raw result, call arguments, error bodies, and per-step results remain in workflow state.summary_kind is fixed to workflow_handoff_v1; summary is short conversational Markdown, with no fixed item count or fields; return_result is computed only by a deterministic guard over the original task, with explicit negation taking precedence over direct-return wording; result defaults to null, reading raw result from state only when the guard is true. Public items uses a safe field allowlist retaining only step identity, status, hashes, and timestamps; public revisions retains only version and time. Arguments, results, and error bodies do not enter the public payload.
Legacy artifact deliveryHistorical code.py/SINGLE-run planner examples allow return findings or direct return agent(...).These rules serve explicit legacy resume only; new creation is prohibited. Current create/revise projects use the pre-publication author contract. Substantive artifacts default to the current working directory and enter chat results only when the task explicitly requests direct body return.
Expanded contentInternal function calls form the execution layer through caller; chat already has RuntimeBlock, TreeStep and Details.Fully reuse existing components and interactions without a Planner-, Agent-, or workflow-specific visual layer.
Runtime selectionDirect runs still belong to the current session; the session picker’s provider_override/model_override selects that session’s model, falling back to the session agent configuration when no explicit override exists.Before creating the function subprocess, the parent resolves the same selection and explicitly passes a provider/model snapshot. The subprocess must not override it with global auto-detection.
footerThe top-level footer already has time, Copy, Retry, Edit & re-run, and version navigation.The footer is outside execution and always at the message bottom: after Conclusion when present, or after the collapsed title otherwise. Its top spacing reuses the 12px assistant-body-to-footer paragraph gap; visibility conditions, button order, and behavior remain unchanged.

Implementation evidence

Chat UI implementation: runtime-block.tsx adds only a dedicated avatar and ExecutionStrip for top-level Programs; execution tree and usage share one collapsible region. The footer follows both that region and Conclusion, with execution-strip.css reusing the assistant message’s 12px body-to-footer gap. Nested LLM tool calls retain their original structure. Successful Conclusions treat only content marked workflow_handoff_v1 as a work summary and show the complete result separately afterward only when return_result=true; for capped, cancelled, interrupted, and failed states, runtime-summary.ts deterministically generates status or error Conclusions without a model call. The old payload’s raw summary is no longer treated as a work summary.
Backend implementation: workflow/__init__.py calls one independent tool-free summary function after the current package Workflow succeeds. Inputs are the task, executed function names, statuses, raw-result length, and only agent-step operational handoffs capped at 240 characters. No call arguments, complete raw results, or other function result summaries are included. A deterministic guard reading only the original task authorizes body disclosure. Malformed or failed summaries produce a safe handoff with errors retained only in state. Historical planner and SINGLE file-delivery rules remain only for explicit legacy resume.
Automated checks: pytest -q tests/component/agent/test_agentic_workflow.py covers current package Workflow and explicit legacy resume, whose creation paths must not mix; full Web checks, Web typecheck, documentation links, and git diff --check are also verified.
Real acceptance: Historical workflow payloads lack the workflow_handoff_v1 marker, so the old 12198-character task result is no longer displayed as Conclusion. Real 18100 acceptance of new handoffs must use a newly created workflow run and only /Applications/OpenProgram.app, the default ~/.openprogram from 18100; do not start 18200.
