Self-Programming Workflow · architecture and implementation plan

Separate Workflow discovery, creation, revision, and execution

This page defines how the OpenProgram Chat Agent selects existing Workflows, creates reusable Workflows on demand, and lets users manually trigger the complete process through auto_workflow(task) . Selection, creation, revision, and execution must be independent public operations. The complete entry point only orchestrates them and retains no second implementation.

1. Design decisions

Remove the entry point for new agentic_workflow calls.Separate its capabilities into search_workflows, create_workflow, revise_workflow and execution of a specific Workflow; also provide a complete auto_workflow entry point for manual user use only.

Chat Agent path

Agent → search / create / revise / workflow

The Agent decides whether to call an existing Program directly. Search only when the catalog is large or candidates are not loaded. The Agent does not call auto_workflow.

Manual user path

User → auto_workflow(task)

One request performs search, one visible selection, creation if needed, and execution. Every step remains independently visible in the DAG.

auto_workflow is a convenience orchestration entry, not a candidate Workflow or component. Exclude it from search results, prohibit imports in generated code, and omit it from Agent tools.
workflow/ categorizes code only. Directories, helper files, and internal subdirectories are not Programs. Programs, the Registry, and call graphs treat only actually registered @agentic_function as executable entities. Directory hierarchy must not change public names, invocation, or execution semantics.

Workflow parameter ownership

Users supply the task, evidence and deliverable requirements. Execution parameters belong to the Workflow; do not expose them through Advanced, settings dialogs or parameter questions.

When a Workflow has several task-dependent parameters, make one tool-free model request before execution to produce the complete plan. Supply real runtime capabilities and application limits. Validate every field and cross-field constraint, apply a complete fallback on invalid output or planning failure, and propagate cancellation. Fixed invariants remain code-owned; the model cannot change permissions, credentials or application ceilings. Persist the effective plan before resumable work and reuse it on resume.

The canonical development example, parameter contract and acceptance checklist are in Workflow authoring. Missing task facts may require clarification; execution tuning must not be delegated to the user.

3. Target architecture and two primary paths

Manual user orchestrationChat Agent decisionPublic Workflow capabilitiesPersistent state and execution

Chat Agent decision order

  1. An already-loaded Program or Workflow clearly matches: call it directly without searching first.
  2. An unloaded dynamic Workflow may exist: call search_workflows.
  3. Complete match: invoke the candidate’s pinned revision directly.
  4. Partial capability only: compose direct calls for a one-off task; when reuse, recovery, scheduling, or stable structure is needed, call create_workflow.
  5. No match: the Agent can still use tools directly for an ordinary one-off task. Create only when the user explicitly requests a reusable asset or the task has stable recurring structure.

5. Search, component reuse, and creation

One package contract and a human-author entry

Agent and human authors use the same static validator. New projects must use the package format pyproject.toml + README.md + __init__.py + workflow.py + tests/test_workflow.py + helper ; legacy entry.py is outside new authoring. The first CLI phase provides openprogram workflows validate <directory>, returning read-only diagnostics for structure, metadata, AST, imports, entries, and dependency-import shapes. Missing dependencies, cycles, and revision pins remain create/revise publication checks.--json provides stable script output. create/revise invokes the same candidate validator before publication, without a second rule set.

Static validate does not execute project code and must not be described as passing publication tests. A behavioral-test gate must run in a mandatory sandbox independent of the user profile, with network disabled by default, credentials filtered, and write directories and time bounded; unavailable sandboxing must deny publication. This gate is a separate subsequent task.

Search contract

Search uses catalog metadata and pinned Git HEAD for deterministic text retrieval, then gives candidate contracts to the calling Agent. Chat Agent decides in the chat path; the manual auto path uses its sole visible selection Agent. Search results are not execution permission; permissions, input schemas, and side effects accompany candidates.

  "workflow_id": "web_research",
  "revision": "<git revision>",
  "retrieval_score": 4,
  "matched_terms": ["web", "research"],
  "input_schema": {},

  "permissions": ["network"]
}

Reuse components during creation

create_workflow receives read-only snapshots of available Workflows and the public Program catalog. Generated projects reference Workflow packages through normal Python imports without copying dependency source. The manifest pins each dependency revision; publication rejects dependency cycles, missing entries, and undeclared permission expansion.

research_report/
├── pyproject.toml
├── README.md
├── workflows/

│       ├── collect.py      # imports web_research
│       └── synthesize.py
└── tests/
    └── test_research_report.py
Pin inputs

Freeze catalog revisions and reachable dependencies; later external commits do not change this authoring attempt.

Generate one candidate

Only the candidate directory is writable; source repositories, dependency Workflows, and user directories stay read-only.

Deterministic validation

Check package, unique entry, schemas, imports, dependency closure, cycles, permissions, and test commands.

Bounded pre-publication repair

Repair only generated-candidate structure or test failures, with a retry limit. Do not repair cancellation or provider errors.

Atomic publication

After all validation succeeds, create one commit and update the catalog. Return a Workflow ref without executing the user task.

One-off tasks do not automatically create Workflows. Creation requires an explicit user request or at least one need for stable reuse, recovery, scheduling, or versioned review.

6. Lifecycle, failure, and trust boundaries

PhaseAllowed state changeFailure rule
searchNo persistent run; read-only resultReport or skip corrupt catalog items; never change projects.
create / reviserunning → completed | failed | cancelledFailure and cancellation do not publish. Candidates may be reclaimed; diagnostics go to run state.
workflow runrunning → completed | failed | capped | cancelled | interruptedPreserve the original error and checkpoint; do not automatically rewrite a published Workflow.
autoAggregate child-call stateStop on any child failure; never mark partial results completed.
resumeResume only the specified runPin the original snapshot/revision; do not search again or reselect a project.

Boundary requirements

  • Authoring writes are limited to the current candidate and run state. Network, credentials, and external tools follow current session permissions.
  • Publication to the same target Workflow must serialize; different projects may run concurrently. Concurrent publication does not alter running snapshots.
  • Cancellation, permission denial, timeout, provider terminal errors, and external Stop never enter repair.
  • The invocation form inherits the session’s Project; it offers no second working-directory override.
  • Local App refresh refuses to proceed when active runs exist; restarting must not rewrite run state as failed or cancelled.
  • Legacy code.py, legacy snapshots, and historical runs support read-only recovery; new calls never produce the old format.

8. Implementation plan

Each phase has a separate commit and proceeds through public RED, minimal GREEN, specification review, and quality review. Do not start the next phase until both reviews pass. Existing tests/component/agent/test_agentic_workflow.py anchors the monolithic entry; migrate corresponding test ownership in each phase so removing the entry does not invalidate all tests at once.

Phase 0

Connect exposure controls

Add to @agentic_function a tool-level exposure parameter passed into Layer-2 register(..., expose); reuse existing _unexposed/exposed_names().

Gate: minimal registration-contract tests prove the parameter takes effect; defaults remain unchanged and all existing functions stay exposed.
Phase 1

Extract read-only search

Extract from the existing module the public contract search_workflows ; return pinned revisions, schemas, permissions, and match information; exclude auto_workflow and legacy projects. Move search tests to the new entry.

Gate: catalog and run directories remain byte-identical before and after the call; the Agent can read candidates without execution nodes.
Phase 2

Separate creation and revision

Move candidates, validation, dependency pinning, and publication into create_workflow; implement revise_workflow with an explicit target and new revision. Creation does not execute the user task. Delete execution-time repair; move author/validate/publish tests to the new entry.

Gate: create adds only one project; revise adds only one revision; failure, cancellation, and terminal errors never publish; no automatic execution-time publication path exists.
Phase 3

Create user-level auto_workflow

Use the preceding public capabilities for search → visible select → reuse/create → run. The full DAG shows each step. The invocation form contains only task and inherits the session Project; register it as hidden from Agents using Phase 0.

Gate: visible in user forms but absent from Agent tools; real App reuse and create paths are distinguishable.
Phase 4

Remove new agentic_workflow calls

Stop registering the old entry and remove selection/repair branches used only by the old composite path. Retain explicit resume_workflow(run_id) and the legacy read-only executor. Delete or migrate remaining tests tied to the monolithic entry; retain resume/legacy tests.

Gate: new catalogs, DAGs, and runs contain no agentic_workflow; historical runs remain inspectable and resumable with unchanged artifacts.
Phase 5

Classification directories, UI, documentation, and final gates

First establish “directories classify; Registry defines runtime identity,” then move relevant source into workflow/. Programs creates expandable navigation from actual directories and function nodes from the Registry; the call-graph root uses the selected function name. Finally synchronize product documentation and accept direct, reuse, create, cancel, and legacy recovery in the default App.

Gate: the source tree has no old agentic_workflow/; the Registry has no legacy name; in Programs, workflow expands but cannot run. Its expanded contents show only four registered functions. Helper files and internal directories are not Programs. Call-graph roots use selected function names. Directory moves do not change registered schemas, execution, recovery, or cancellation. Automated regressions must cover these constraints, followed by documentation build, zero dead links, and visual acceptance in the default App.
Phase 6

Unify author static validation

Expose the current package validator as a shared read-only entry for the human CLI and Agent author; add English/Chinese author specifications. create/revise revalidates candidates through the same function before publication. Exclude legacy reading, behavioral tests, scaffold, publish CLI, and catalog migration from this phase.

Gate: a valid directory yields the same metadata and file list in CLI and Agent candidate validation. Invalid directories return nonzero status and deterministic diagnostics. Validation neither writes directories, initializes Git, nor executes test code.
Phase 7

Mandatory isolated behavioral-test gate

Run candidate tests before publication in a mandatory sandbox independent of the user profile, with no network, filtered credentials, constrained write directories, and a timeout. Missing sandbox, test failure, or cancellation prevents publication.

Gate: malicious credential reads, out-of-root writes, network access, timeout, and ordinary failure all have public RED tests. create/revise keeps catalog and HEAD unchanged on every failure.

11. Explicit exclusions

  • Do not add @workflow, a graph DSL, a second Runtime, or a string call_workflow() dispatcher.
  • Do not automatically turn every user message into a Workflow or create projects by default for one-off tasks.
  • Do not automatically modify published Workflows or implicitly publish revisions after ordinary execution errors.
  • No Workflow database, background Git polling, remote push, Marketplace, or remote dependency resolution.
  • This phase does not implement scaffold, manual publish commands, catalog state-directory migration, or execution of untrusted tests; each is a separate subsequent task.
  • Do not change existing Python call semantics for Agents, Programs, or Workflows; this design separates only entry points and lifecycles.

Portable Workflow package contract

A Workflow is a self-contained Python package under openprogram/programs/workflow/<workflow_id>. Its public function name and package-relative location remain stable when the OpenProgram checkout moves. Package metadata, imports, dependency revisions, UI links and invocation requests never contain a developer home directory.

ConcernContract
IdentityThe lowercase package identifier is the registered callable name. Python composition uses ordinary imports and direct calls. No new runtime, decorator or invocation protocol is introduced.

Authoring and publication lifecycle

The formal manual interface is openprogram workflows validate DIRECTORY, openprogram workflows test DIRECTORY, and openprogram workflows publish DIRECTORY. Validate is read-only. Test copies a validated candidate and pinned dependencies into a temporary workspace and runs its tests in a required OS sandbox with network disabled, credential-free environment, protected source files and bounded process lifetime. Manual publication and the generated create/revise entry points use the same required behavior-test gate. Publish repeats validation and tests on the exact snapshot it commits; it never trusts an old success report. Existing packages require an explicit --replace and a clean destination. Failure, timeout, sandbox unavailability or unsuccessful tests publish nothing.

Documented from workflows.NAME import NAME imports resolve to the same authorized callable as openprogram.programs.workflow.NAME in the live catalog. The live alias exposes only named authorized entry points. Snapshot execution explicitly owns its workflows namespace and continues to load pinned bytes; it never falls back to the live catalog. The package README specifies purpose, input, output, effects, failure/cancellation behavior, dependencies, tests and a reproducible invocation.

Acceptance

  • Record, move the checkout, discover and resolve the same authorized Workflow without editing package metadata or per-package paths.
  • Recover the previously recorded weekly-report package from its obsolete checkout prefix without authorizing unrelated directories.
  • Reject traversal, unknown scope, unauthorized packages and ambiguous resolution; preserve explicitly installed external sources.
  • In the default installed App, the existing weekly_report favorite appears and Use opens its task form; do not execute or submit a report during acceptance.
  • The English authoring guide and Chinese translation specify identical creation, validation, publication, relocation and troubleshooting behavior, with commands verified against the CLI.
