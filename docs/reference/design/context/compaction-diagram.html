Current rolling-summary constraints

Compaction uses the same DAG visibility, tool-result rendering and aging rules as model requests. Top-level conversation defines only the replaceable range; each range's budget includes actually visible subcalls. Always retain the latest complete user turn, and retain the latest two by default; the token budget may allow fewer than twenty top-level messages. Short history already below the retention budget does not invoke the summary model.

Summary input starts at the first message of the selected range and includes original user requests, the prior summary and visible tool results. Summary input and covers_ids describe the same range; no removed prefix is omitted from model input. The previous summary comes only from records applicable to the current branch, not a session cache from another branch.

After generation, perform the same replacement and rendering in the in-memory graph and persist only if estimated tokens strictly decrease. Estimates include summary markers and tool results; compaction markers and the context panel use the same message rendering. Failure, cancellation, empty summary, no gain or content changes during generation neither commit a summary nor increment compaction count. Failures do not substitute a structural summary that discards content.

Storage retains one rolling summary and existing covers_ids without migrating or deleting history. Repeated compaction incorporates the currently applicable summary; existing DAG rendering rules preserve branch isolation, unchanged HEAD and tool-call/result pairing. Historical incorrect summaries are not automatically rewritten.

Acceptance and boundaries

  • With large tool results among sixteen top-level messages, summary coverage includes complete older turns and actual context shrinks.
  • The summary receives every replaced user request and visible tool result; recent turns stay unchanged.
  • Equal-length or longer summaries, cancellation, provider errors and edits during asynchronous work do not write.
  • Repeated compaction, branch switching, occupancy statistics and final requests render consistently.

Reference sources remain those already compared on this page; this change adds no external implementation or changes to other multi-tier compaction policies.

Implementation status

These corrections are implemented. Regression tests cover complete summary input, retaining the latest two turns, rejecting no-gain summaries, cancellation/concurrent changes, repeated compaction and statistics consistency. Session-graph compaction scope uses the same message snapshot, avoiding inconsistent summary state if compaction repeats during loading.

5. Execution flow 
Before every LLM call:

1. Budget Reduction → truncate oversized tool outputs (every turn)

2. Cascade checks (tier order):
   Tier 1: Microcompact condition met? → clean old tool outputs
   Tier 2: Still over threshold? → Snip older turns
   Tier 3: Still over? → Context Collapse segment summaries
   Tier 4: Still over? → Auto-Compact full summary

3. Call the LLM

4. If the API returns 413:
   Tier 5: Reactive → emergency compaction → retry
   → stop on failure
6. Complete example

Scenario: 200K context, several hours of work, with research_agent invoked midway.

Stage 1 (0–30%): normal conversation

🔵 user → 🔵 assistant; Budget Reduction checks tool outputs and skips those within limits. No cascade tier triggers.

Stage 2 (30–50%): Tier 1 Microcompact begins

Tool calls exceed 50. Cache-aware Microcompact triggers for the first time, cleaning old outputs and freeing about 15K tokens. It repeats every 25 calls. Tiers 2–5 do not trigger.

Stage 3: invoke 🟢 research_agent

While the function runs, internal 🟡 tool calls expand. Budget Reduction truncates oversized outputs. On completion, expose=io hides the internal subtree and the node enters normal cascading.

Stage 4 (over threshold): Tier 2 Snip triggers

Microcompact leaves context over budget. Snip removes the oldest five turns, including completed function nodes, bringing it below threshold. Tiers 3–5 do not trigger.

Stage 5 (extreme): Tier 3/4 trigger

After repeated Snip, little removable content remains. Context Collapse summarizes segments; if insufficient, Auto-Compact summarizes everything. This is rare.

Stage 6: continue using the system

Conversation continues normally after compaction. Repeat the cascade when over threshold again. The model can inspect old function internals by reading DAG children through tools.

Request compaction within one message

Chat and internal function execution share AgentLoop's pre-send processing: measure the request after message conversion, memory injection and actual-tool resolution. Compaction replaces only completed tool-group result text in the current request view, preserving call arguments, result IDs, error states, original user text and multimodal content. Original execution records are not rewritten.

Summaries use independently budgeted chunks with bounded calls and total duration; summary requests do not reenter AgentLoop. Cache belongs only to the current AgentContext and matches original result content and model configuration, never spanning function views. Older results are preferred and the latest tool group is retained; completed latest groups may also be processed when necessary. Recheck actual tools and system content on every send.

Without an explicit output cap, use the minimum of model capability, default output reserve and one quarter of the context window; measurement and provider requests use the same value. Never silently reduce explicit caps; reject sending if protected content plus that cap exceeds budget.

Scope: request compaction for tool accumulation within one turn. It does not replace existing cross-turn DAG summaries or promise lossless semantics or exact agreement between local estimates and provider counts. Do not send a known over-budget request when uncompressible protected content exceeds budget.

Implementation status: connected to the shared AgentLoop request entry and passed independent specification and quality reviews. Regression tests cover consecutive calls within a turn, internal function entry, original-text retention, summary budgets, cancellation and credential propagation. This processing creates no persistent DAG summary node.
