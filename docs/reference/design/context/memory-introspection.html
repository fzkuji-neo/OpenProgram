Memory introspection: how an agent knows what it remembers

A live test exposed the problem: when an agent running in OpenProgram was asked to describe “how the current memory system is designed,” it described Claude Code configuration files and skills on the host and recommended a tool deleted with the previous generation for preserving knowledge, without mentioning the actual system under openprogram/memory/. This page examines context assembly and checks the memory clues available to the model each turn against eight reference implementations, then specifies identification text, introspection-tool placement, and what the model should see when memory fails.

00Four layersLayer 1

Each layer answers one question: how memory appears in current context, what others do, which lines to change next, and what the design should be without current implementation constraints.

01Actual form of fifteen componentsLayer 1

context/components.pyFifteen registered components each declare a layer (L0/L1), within-layer order, condition, and builder. The assembler collects them by ["L0","L1"], sorts by order, drops false conditions, builds the rest, and joins them with two newlines. Ascending order places more stable content first, because a stable prefix extends provider cache hits.

Three boundary forms. Greenhas XML tags, exposing block boundaries; Orangehas only a prose introduction, requiring semantic separation; Redis plain text separated by two newlines and indistinct from adjacent blocks. Of fifteen, five are green, three orange, and seven red: identity, inline_prompt, workspace_files, current_dateare all red; memory_globalis green but conveys only part of its identity, as the next section explains.

02What the memory block looks likeLayer 1

Memory enters context through two paths sharing the same delimiter function. The delimiter was designed for recall, preventing old facts from being treated as new user requests. The resident block reuses it and consequently says only “this is recalled content.”

The resident block already has delimiters; missing delimiters are not the problem.LocalMemoryBackend.system_prompt() (local_backend.py:59) is return fence_memory(text) if body else "", so <memory-context>has always existed. Its sentence was written for recall to prevent old facts from being treated as new requests, which it successfully does. Reusing it for resident content answers the identity question with only “this is recalled content.”
Adding another wrapper is wrong because delimiting is not idempotent.fence_memoryfirst calls sanitize_context, and sanitize_context has a first regex _FENCE_BLOCK_RE that removes the entire <memory-context>…</memory-context> block, including its content. Measured fence_memory(fence_memory("hello world")) returns an empty delimited block: <memory-context>\n[System note…]\n\n\n</memory-context>. Identification must therefore replace the introduction, not add another wrapper.

03Why failures are silentLayer 1

From disk to wire, memory crosses four except, each converting exceptions to an empty string. To the assembler, an empty string means the component is absent this turn. Thus empty memory and failed memory look identical to the model: nothing appears.

These conditions require different model responses. Disabled memory is the user’s decision and need not be mentioned. An empty workspace is a normal fresh-install state: say “I have no record of this yet.” A memory failure must never imply “the user never told me this,” which would mistake a system failure for a fact. Current code gives the model no way to distinguish them.

07Introspection tools and empty/failure visibilityLayer 2

Introspection tools · default availability

Only openclaw and hermes provide them by default

A tool existing and a tool being available by default are different

openclawPlaces memory_search + memory_get in memory-core, the memory plugin slot’s default implementation, so installation makes it available without selection. The tool description is itself an instruction: Mandatory recall step…, and explicitly says If response has disabled=true, memory retrieval is unavailable and should be surfaced to the user.

hermes has memory enabled in the core set, but only add/replace/remove, without list; returning the full list after each write substitutes for listing.

codex-cliHas four real introspection tools (List / Read / Search / AddAdHocNote), but both switches default off: Feature::MemoryTool is default_enabled: false, and an additional memories.dedicated_tools. claude-codeUses no dedicated tools: memory is files accessed through generic Write/Read/Grep; the prompt directly instructs the model to write in that directory.

Our position resembles codex: six implemented tools, unavailable by default. Codex uses explicit feature flags; ours is the easily overlooked fact that they are absent from DEFAULT_TOOLS.

openclaw: 2 default toolshermes: 1 default toolcodex: 4 tools, off by defaultOurs: 6 tools, off by default
Empty / failed · model visibility

Only openclaw distinguishes all three states

Can the model distinguish empty, failed, and disabled

Empty: the BOOTSTRAP.md template explicitly tells the model: There is no memory yet. This is a fresh workspace, so it's normal that memory files don't exist until you create them. This makes emptiness normal rather than suspicious. claude-code has a similar placeholder for subagents: Your MEMORY.md is currently empty. When you save new memories, they will appear here., but not for the main session.

Failed: openclaw retrieval failure returns structured disabled:true + unavailable:true + warning + action: Check embedding provider configuration and retry, and requires the model to tell the user. Unique among the eight.

Changed: codex alone says that old content is no longer valid: The previously provided AGENTS.md instructions no longer apply. This applies to project documents, however; missing memory remains silent.

The other five, including ours, silently omit the block, leaving the model unable to distinguish never-recorded content from failed retrieval.

openclaw: all three statesclaude-code: subagent placeholdercodex: invalidation noticeOther five: silent

09Planned changesLayer 3

Four independently deployable and verifiable changes. Total 85 tokens per turn, including 65 in the L0 cached prefix that are not repeatedly billed from the second turn onward.

Change A · smallest change

The tool catalog itself identifies memory

functions/__init__.py:72-114 + :123-136

The six memory_* enter DEFAULT_TOOLS, and all six also enter DEFERRED_DEFAULT_TOOLS. The deferred catalog sends only names, not descriptions (deferred_catalog_text is "\n".join(name …)); the six lines measure 20 token.

Each turn, the model scans its tools and sees memory_search, memory_browse, memory_status names, making memory availability explicit.wiki_agent is no longer the only listed knowledge-system-like tool. It need not be removed; put the correct answer alongside it.

Answers to three design questions. How to add identification: replace the resident block’s introduction without adding delimiters, because delimiting is not idempotent and the existing recall introduction serves a different purpose. How the model knows it has memory: both tool catalog and prose are needed, in that order. The catalog costs less (20 versus 65 tokens) and is more authoritative to the model. Prose answers the three questions names cannot: location, completeness, and authorship. Should the model know about failures: yes, distinctly from emptiness, or it may interpret a system failure as “the user never said this.”

10Cost and locationsLayer 3

Why defer all six instead of keeping two resident.The deferred catalog sends only names, and memory_searchandmemory_browse already state their purpose. Schema parameter instructions are needed only when calling the tool. tool_search is never deferred and is the sole entry point for loading the others, so the model can act on a known name in one step. Most sessions never call the six tools. A single status line replaces 821 tokens of stale content, producing a net reduction.

11Ideal stateLayer 4

The target without current implementation constraints. Four items, each naming the gap and reason for deferral.

All four move from static prose claims to system-reported facts about what the model can know. Currently, the context layer describes memory on its behalf as it existed when designed. Ideally, memory reports its present state, leaving prose only for invariant facts. All four layer-3 changes deliberately remain static prose and metadata: they do not change interfaces and can therefore be deployed or reverted independently. Changing fifteen builders would invalidate all cached prefixes. Changes A and C supply the needed knowledge without a self-inspection request.
