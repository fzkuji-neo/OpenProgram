Mechanism diagrams

How a conversation becomes topic files on disk, what happens if a write fails midway, how forks track previously written messages, and who maintains the small memory block injected into every session. The main text is in docs/reference/design/memory/overview.md; the complete design for section 04 is in written-marker.md. This page illustrates mechanisms only. Comparisons with other implementations and the rationale for our choices are in Memory writing: comparison of eight frameworks.

Running implementation

Two write entry points, five write steps, staged transactions, nightly organization, the silence-means-success return-value contract, and Section 05 and its resident-block derived view: core.md is rendered from topics/core.md; exceeding the budget no longer rejects transactions.

Designed, not yet implemented

Section 04’s write cursor: the running implementation still uses positions, which can omit an entire fork or write only a fragment starting mid-conversation. The planned approach marks nodes as written and walks backward from head to the first marked node.

04 Cursor: identity versus position

A session is a graph, not a linear sequence. Re-asking, retrying a reply, or spawning a subagent creates a branch. Every branch’s messages should enter memory, but shared prefixes should not be written twice.

Diagram details: Cursor stores ordinal=9; accept only larger ordinals. Walk backward from head, collect unmarked nodes, stop at the first marker. Traverse the whole branch and subtract IDs in the set. Value identifies the memory workspace; exported sessions. retain markers without being mistaken for another workspace. Observed: stored position 9 treats a five-turn branch as empty,. and an eleven-turn branch as its last two turns.

Why position cannot represent identity: ordinals are assigned when a linked structure is expanded into a list. They describe that expansion, not messages. Before expansion there is no ordinal; afterward it has no relationship to the message ID. The same message reached by two paths can receive different ordinals, and different messages at equal depths can share one. Furthermore, get_branch filters turns marked rewind , and compaction inserts summary nodes, so even one path changes between reads.
The representation also rejects correction: advance_cursor raises cursor cannot move backwards when a new ordinal is below the stored one, although moving backward is exactly what branching requires. A monotonic counter cannot be corrected into a representation of branching conversations.
The two failures differ in visibility: before the branch exceeds the stored height, nothing is claimed and the whole branch is omitted. Afterward, only the excess is claimed: a fragment beginning mid-conversation is written, then the entire branch is marked written. This second case returns success without any indication of failure.

Diagram details: Use node markers. External bookkeeping that remains correct after forks requires a set, introducing file placement, migration, permanent ID retention, and read cost that grows with the conversation.

Perform the idempotent step first: archive evidence, write topics, then mark nodes. Archives are append-only and content-addressed; archiving the same batch twice is byte-identical. Topics have block IDs and footnotes, so partial writes would corrupt them; transactions install all or nothing. If the writer dies between steps, it leaves unreferenced evidence, no markers, and the same pending batch for the next retry. Marking first would turn that crash into silent loss of those turns.
Completion needs verifiable output: marking requires successful transaction installationandactual file changes. Nightly organization must report changed files, not merely inspected files. Absence of an error is not an output.
Verified cost to session storage: sessions have no whole-tree hash. The sole byte-level tree hash is the memory-workspace revision rooted at <state>/memory, separate from <state>/sessions , so node markers are not mistaken for concurrent memory writes. The session-index cache is affected: history-directory mtime changes on rewrites just as on appends. Another process rebuilds the index; measured cost for 289 nodes and 4.2 MB is 14–50 ms and is self-limiting. Git is what grows: the session directory runs git add -A per turn, and changed nodes become new blobs. Therefore, mark only the current batch; never rescan and rewrite every node, or each turn adds the entire session and total growth becomes quadratic. Two additional constraints: markers must not change updated_at(the idle watcher uses it to decide whether a session was handled; changing it would trigger another forced write), and must not use the “mark session synchronized” path.

05 Maintaining the resident block

core.md is the small block injected at each session’s start. It is now rendered from topics/core.md; 2000 tokens is a rendering budget, not a transaction gate. Previously it was the writable source of truth: once full, it stopped changing and rejected every later transaction.

Diagram details: management/block_views.py _synchronize. Both writers and nightly organization use this file.

Diagram details: It reports COMMIT_REJECTED, outside the retryable set, so the watcher still marks the session handled. Ordinary topic file without a size limit. Both writers and nightly organization use only this file. Rebuilt after each successful installation. Include content up to 2000 tokens. Omitted blocks produce IDs, not errors. Omitted paragraphs remain in the source, indexed and discoverable through search and memory_get. A unique block in core.md could make clipping reject the entire transaction. Rendered IDs are always a subset. Observed: an 11,883-token handwritten core.md no longer blocks an unrelated write; rendering produced 1,983 tokens.

Difference between the approaches: the current description’s old path rejects on the write path, preventing content from entering; the planned replacement omits on the rendering path, making content invisible only for that injection. Why not add another gate: another gate still blocks writes and stable facts. Other implementations must distinguish human and automatic content before clipping because their resident file is the only copy: deleting a line destroys it. Here the complete source remains, so authorship does not need classification.

07 Failure behavior

Writes have three return outcomes interpreted by the watcher. Silence means success; failures distinguish transient conditions from those that will not change on retry.

10 Unified modification interface

Memory supports both direct Topic-file edits and structured calls by models or other programs. Neither replaces the other; they differ only in how callers express changes. All modifications use the same Runtime staging, validation, derived views, atomic installation, and Git process.

Method one · edit files directly

Background writers or organizing models create, rewrite, move, or delete topics/**/*.md inside Runtime-provided staging. Each Source in new footnotes is written as [short keyword](source_ref). The model chooses keywords and an existing Source, not the final URL. After editing it must not overwrite production Memory directly; it calls commit_edits so Runtime allocates/preserves IDs, resolves source_ref into archive links, validates Source/block links, rebuilds Timeline/Recent/Relations/Core, and installs everything. Web/CLI file edits use the same staged_edit entry.

Method two · structured interface

Model tools and owner REST accept memory_changes[]. Content operations are create_record, update_record, delete_record; structural operations are move_records. Runtime renders them into Topic Markdown and uses the same installation path as direct edits.

Source identity

source is immutable and must be verified. Runtime uses it to generate links, inspect trust state, and restore derived views. Display text cannot change the target.

Reference keyword

label is local display text for this citation, generated in the same Memory write call, not a permanent Source title. Memory-agent prompts and tool schemas require short context-relevant keywords and discourage Markdown, URLs, Source IDs, speaker names, or time templates. Apart from a nonempty-string Markdown requirement, Runtime does not assess keyword quality, truncate/rewrite labels, or add a model call for them.
Canonical output:{"content":"...","sources":[{"source":"provider/thread/message","label":"research scope"}]}. Topic files retain standard Markdown: [research scope](../../sources/...#source-...). The parser recovers Source identity from the link target, never from bracketed display text.
