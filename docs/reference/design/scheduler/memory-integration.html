Memory interface

Scheduler owns timing, execution, status, and results; Memory owns long-term semantic facts. Stable references and existing Memory tools connect them, but they share neither state files nor write transactions. Agents can explicitly maintain associated Memory records while planning, executing, and closing tasks.

1. Goals and boundaries

One-time tasks

Store a timezone-aware run_at and execute once when due. Migrate dated legacy Commitments to this type.

Recurring tasks

Reuse existing five-field cron parsing, owner signatures, frozen sandbox policies, and non-interactive execution boundaries.

Monitoring tasks

Periodically execute observation prompts with cron. The first version records execution logs and state without promising cross-channel exactly-once notifications.

Explicit exclusions

The Memory writer does not infer tasks; Memory pages do not show Commitments; Scheduler service does not implicitly create or modify Memory. No cross-store Scheduler/Memory transactions, external-token permission model, placeholders or ID forwarding for deleted records, second executor, project management, task dependencies, or subtasks are introduced.

2. Target data relationships

1 CreateOwner Web UI, an Agent tool, or an external API creates a Scheduler task.
2 FreezeThe runtime signs prompt/command, cwd, permissions, sandbox, and MemoryRef.
3 WakeThe persistent OpenProgram worker checks once/cron schedules every minute.
4 ResolveBefore execution, read current Memory content using workspace_id + memory_id.
5 ExecuteExecute within frozen non-interactive permission boundaries and write Scheduler logs and state.

Worker tick exception boundary

If the initial @reboot tick or subsequent ordinary ticks raise Exception, the daemon writes a warning and full traceback to stderr and continues at the next minute boundary. It neither immediately replays nor compensates. After initial failure, subsequent ticks use reboot=False. Redirected stderr from the persistent OpenProgram worker goes to the global worker log; standalone foreground scheduler-worker displays it in the current terminal. Neither is an individual task execution log.run_once, KeyboardInterrupt, SystemExit and other BaseException remain fail-fast.

4. Agent lifecycle protocol

PhaseAgent behaviorBoundary
Planning or creationOnly if the task itself merits long-term retention does the agent use memory_update.create_record to create a task record, then attach the returned memory_id as memory_refs to the Scheduler task. Ordinary temporary reminders need not write to Memory.Execute the calls sequentially without treating them as one atomic transaction; explicitly report either failure to the agent.
Execution or state changeThe prompt task receives current MemoryRef content at execution. If the record describes this task, the agent first reads its revision and original content, then uses update_record to write current status, results, or information to retain for the next execution.Scheduler cannot use other side-effect tools such as shell, file writing, or network sending; added write capability is limited to existing Memory transaction tools.
ClosureIf long-term value remains, update the associated record as completed, closed, or with the final result; if no retention value remains, delete it using delete_record. An interactive agent may also disable or delete the Scheduler task.After deletion, the current Memory API no longer resolves the old ID. A Scheduler task still referencing it fails on the next resolution; remove or close the task first.

Git recovery boundary

Commits preceding record deletion remain retrievable and recoverable from reachable history in the same Memory Git repository, provided changes were committed, the repository still exists, and history was not rewritten or pruned. Current memory_get queries only HEAD. Recoverability through Git history therefore does not mean an old memory_id can be queried directly through the current API, nor does it provide an absolute 100% guarantee.

5. Legacy Commitments migration

  • Migrate only open records. Dated records become enabled one-time tasks scheduled for 09:00 local time on that date.
  • Undated records become paused one-time drafts, retaining text and provenance until the owner sets a time.
  • After successful migration, move the original commitments.jsonl to the Scheduler migration archive. Repeated startups must not create duplicates.
  • Remove the record_commitments tool and prompts from the Memory writer. Retain the old runtime parser only for one-time migration compatibility.

8. Implementation brief and acceptance

This change is limited to the internal Memory lifecycle of Scheduler prompt tasks: retain existing Scheduler service, REST, UI, and Memory data formats; permit Scheduler-origin calls to memory_status, memory_get and memory_update, and extend Agent tool descriptions and execution-context prompts. Public RED tests must prove these three tools execute while shell, ordinary file writes, network sending, and Scheduler self-modification remain strictly denied. Memory writes continue through existing authority, revision, transaction, and Git paths. External API permissions are outside this implementation. After record deletion, current queries for the old memory_id return NOT_FOUND.

The separate worker reliability change isolates complete tick exceptions in run_forever and lets scheduler-worker and cron-worker bypass stdio redirection intended only for Ink TUI startup. It does not change Scheduler service, REST, task state formats, claim, spawn, or run_once.
