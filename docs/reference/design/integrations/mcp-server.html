LAYER 1

How we work today

The MCP client and authenticated stdio server now coexist. The internal control surface still has 198 FastAPI routes and approximately 100 WebSocket actions. OwnerAuthMiddleware uniformly enforces process tokens, cookie/Bearer credentials, Host/Origin checks, and WebSocket authentication before accept. The MCP server instead uses an independent 0600 token, credential-fingerprint client identity, fixed paired scope, an empty allowlist by default, and a non-interactive gate; it does not reuse the Web owner token.

01Direction: MCP client and server coexist

Consuming external tools and exposing fixed tools are independent entry points. Both are implemented and share controlled capabilities through the Runtime registry.

Existing reuse points: AgentTool.execute has the signature (call_id, args, cancel: asyncio.Event | None, on_update). Its argument dictionary, cancellation event, and incremental callback provide all three mechanisms required by the protocol server. The server uses an explicit CallToolRequest handler to connect these parameters to the MCP 1.29.0 stdio transport.

02Three internal surfaces, authenticated Web boundary

FastAPI and WebSocket surfaces still have no versioning commitment, but are protected by OwnerAuthMiddleware and mapped to full owner authority after successful authentication. This authentication is neither an MCP client identity nor a low-authority external protocol contract.

The authentication boundaries are independent: OwnerAuthMiddleware already protects Web HTTP, SSE, and WebSocket, but authentication grants the singleton owner’s full authority. The MCP server must authenticate external clients separately, enforce an empty allowlist by default, and assign low-authority scope. It must not provide or reuse the Web owner token for clients.

06Four protocol approaches and their tradeoffs

In-protocol approval · push

codex: elicitation/create

exec_approval.rs · patch_approval.rs
Mechanism
Push exec and patch approvals back to the MCP client with custom correlation field threadId, codex_elicitation, codex_mcp_tool_call_id, codex_event_id, receiving ReviewDecision.
Tradeoff
Low latency, butrequires client elicitation support; the source itself notes that this payload does not yet conform to ElicitResult (missing action / content).
In-protocol approval · pull

openclaw / hermes: poll a pair of tools

permissions_list_open · permissions_respond
Mechanism
Expose pending approvals as data through two tools, with decision allow-once | allow-always | deny. openclaw also supports push through the experimental capability bit claude/channel/permission .
Tradeoff
Works with generic clients without elicitation support, providing a compatible fallback at the cost of another round trip and the polling interval.

Progress and errors

No standard progress usage; error handling has converged

notifications/progress · isError
Progress
codex only logs received notifications/progress ; its own streaming uses custom notification shapes.None of the surveyed frameworks emits standard progress externally.
Errors
All return {isError: true, content:[text]} when a tool executes but fails, reserving JSON-RPC errors for protocol failures (unknown tool name, malformed arguments).We adopt this distinction.
Two negative examples: weclaw’s POST /api/send has no authentication, and its ACP client unconditionally approves every session/request_permission ; opencode’s serve runs without authentication when OPENCODE_SERVER_PASSWORD is unset, merely printing a warning. claude-code-leaked’s mcp serve exposes all built-in tools with an empty permission context and isNonInteractiveSession: true, with no interactive question path at all. This iteration’s acceptance criteria exclude all three approaches.
LAYER 3

Implemented minimum capabilities

openprogram mcp serve uses stdio as its only transport and exposes six tools. tool_call filters using an allowlist that is empty by default. External callers receive the paired low-authority tier and are never interactive. Startup authentication uses an environment credential with no disable switch. Cancellation maps to existing per-turn tokens; progress is driven by on_update ; errors follow the distinction above. Everything below is tied to implementation commit 885d8f15.

09Authentication: validate at stdio startup, with no in-protocol token

TOKEN

Generate once; constant-time comparison

<state_dir>/mcp_server_token (0600)　↔　OPENPROGRAM_MCP_TOKEN
Generation
openprogram mcp token create atomically writes the token file and prints it once;serve never implicitly generates a token.
Validation
openprogram mcp serve compares the environment variable against the token file in constant time before reading any MCP message. Missing credentials, incorrect permissions, or mismatch cause a nonzero exit; stderr is fixed to Error: MCP server authentication failed and stdout is empty.
Protocol boundary
initialize.clientInfo is neither read nor recorded and does not participate in authentication, identity, authority, routing, or results. The token never enters JSON-RPC, logs, errors, or session content.
Authority semantics
The environment credential permits only a low-authority stdio connection. Every request maps to fixed paired and never receives owner authority.
TRANSPORT

stdio as the only transport

openprogram mcp serve · module openprogram/mcp/server/
Why
Every surveyed implementation supports stdio first; itinherits the trust boundary of the launching process and does not expose the internal full-owner Web API as an integration surface.
Specification baseline
The first version pins the repository’s current mcp 1.29.0 and protocol 2025-11-25; the SDK negotiates compatible versions without custom handshake fields.
HTTP
After the stdio contract stabilizes, design Streamable HTTP, OAuth, Origin validation, and deployment lifecycle separately, without reusing the Web owner token.
Module location
A top-level module alongside openprogram/mcp/ ;does not reuse client modules (translation runs in the opposite direction), but shares _runtime.py and approval stages — those are the intended reuse points.

LAYER 4

Ideal state

ACP already has a stdio server entry point. This iteration preserves it without expanding the protocol surface. Inbound webhooks lack fixed job capabilities, and an SDK lacks a surface stable enough to promise compatibility. The latter two enter design only once their security and compatibility prerequisites are satisfied.

11Three gaps and why they remain outside scope

EXISTING · OUT OF SCOPE

Existing ACP stdio server

openprogram acp already provides a stdio entry point through openprogram/acp/server.py , with session, permission-request, and event mappings. It currently uses owner authority and interactive permission semantics. This is separate from the independent MCP client identity, fixed paired scope, and non-interactive gate in this design.
No expansion in this iteration: do not change ACP transport, protocol capabilities, or authorization semantics, or merge MCP tokens, allowlists, or tools into ACP. Run existing ACP regression tests when revising shared Runtime types only.
DEFERRED · WEBHOOK

Inbound webhook

hermes demonstrates the required controls: route-specific HMAC secrets validated at startup, per-route rate limits, an idempotency cache against replay, and body-size checks before reading. These are minimum requirements. The gap is that a webhook is apush trigger with no owner present on arrival, placing it in the same category as cron triggers: it requires a job capability approved and fixed at registration, not a tier calculated on delivery.
Not implemented now: the prerequisite is the fixed job capability from sandbox batch I and step 05B, handled separately. MCP already covers pull-based integration, for which there is a concrete requirement.
DEFERRED · SDK

Client SDK

codex provides TS and Python, opencode generates TS from OpenAPI, openclaw provides a private TS package, and claude-code-leaked provides an Agent SDK. hermes provides no SDK, letting integrators use MCP / ACP / HTTP directly. An SDK is a compatibility commitment, while 198 routes and approximately 100 actions remain an internal surface changing with the frontend; only two have fixed shape assertions.
Not implemented now: the order is deliberate — implement MCP first, because for every language with an MCP SDK, that SDK isthe client library. This is why hermes can be integrated without a dedicated SDK. A dedicated SDK is justified only when actual integrations prove MCP tools too coarse.
Where the stable surface is: publish only the six MCP tools above in this iteration; ACP retains its existing contract, while webhooks and a dedicated SDK remain unpublished. FastAPI and WebSocket remain internal surfaces, do not become MCP transports, and gain no HTTP, OAuth, or Web routes.
