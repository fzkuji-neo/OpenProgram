Task 1: DOM-first Browser Agent baseline

Approved design: docs/reference/design/integrations/web-use.html.

Baseline: 717d4e17. Implementation starts in an isolated worktree and branch codex/browser-agent-20260814.

Production files: openprogram/programs/workflow/browser/__init__.py, openprogram/programs/_registry.py, openprogram/programs/__init__.py, openprogram/agent/authority.py.

Test files: tests/component/programs/browser/test_browser_agent.py.

Behavior contract

  • The public entry is named browser_agent and controls only the currently visible built-in web tab in OpenProgram Desktop, using the existing engine=app.
  • Internal tools default to observe, returning URL, title, viewport, page text, an ARIA snapshot, and element refs valid for the current observation, without screenshots.
  • Only an explicit screenshot returns one current-viewport PNG for native vision processing by the current model; it does not call image_analyze.
  • Do not import or call OCR, YOLO, object detectors, candidate boxes, zoom, component memory, vision memory, workflow replay, or automatic learning.
  • Every page-state-changing action must carry the latest frame_id and element ref. Invalidate the old observation immediately after the action; observe again before the next write action.
  • In public results, status=succeeded is produced only when an internal tool has actually passed a DOM/URL assertion after the last write action. Model output supplies only a summary and cannot determine status.
  • Do not expose JavaScript eval, cookies/storage, uploads/downloads, sidecars, headless fallback, or the user’s Chrome profile.
  • Completion, cancellation, timeout, and exceptions all close this Playwright session. The existing playwright_browser API remains unchanged.

Public-entry RED

python -m pytest -q tests/component/programs/browser/test_browser_agent.py must first demonstrate these gaps:

  • No constrained DOM/ARIA/ref observation and viewport screenshot tool exists.
  • No stale-frame rejection or post-action re-observation requirement exists.
  • No runtime-authoritative completion exists; the model can claim success without verification.

Security, cancellation, error, and concurrency boundaries

  • Reads and screenshots require no additional authorization. Each external-origin navigate/click/type/press/select uses existing approval. Local project pages still require frame-freshness and cancellation checks.
  • In the first version, each browser_agent call owns one browser session. Existing playwright_browser sessions are not reused, preventing cross-task reference and verification interference.
  • The first version does not claim to solve multi-window responder binding. If the desktop control plane cannot uniquely identify the tab, return target_lost or the underlying error rather than choosing another page.
  • Step limits, timeouts, invalid structured replies, tool errors, and missing verification all return failed/cancelled, never succeeded.

Explicit exclusions

Desktop Computer Use, GUI Harness visual pipelines, new permission-card UI, permanent origin grants, tab leases, multi-window routing redesign, Windows, OS keychain/keyring, and browser-profile migration are outside Task 1.

Task 2: Turn-scoped Surface Awareness and bound Web Use

Implementation scope: Chat turns automatically carry the current split web surface. The model’s first context includes a bounded DOM/ARIA preview. Expose web_use only when a valid surface exists; bind reads and actions to the originating WebSocket’s window_id + tab_id + target_id.

Foreground requirement: none. Electron directly reads the bound WebContents and returns its CDP target. activateView does not call BrowserWindow.focus() or another OS focus API. The target pane need not have keyboard focus; ordinary DOM/ARIA actions use neither desktop coordinates nor screenshots.

Runtime target: default profile ~/.openprogram, port 18100, and /Applications/OpenProgram.app. No second desktop process or visible worker is launched from Electron source.

Task 2 current scope and remaining work

The current implementation supports turn-scoped exact Page binding, server-owned monotonic connection/Page/access revisions, renderer-owned monotonic geometry revisions, exclusive WebSession leases keyed by the canonical Page revision, and explicit screenshot for one current-viewport native-vision input. Within a session, action, verify, observe, and close execute serially. The initial observe and every subsequent observe, act, and verify revalidate the exact binding before calling the backend. Page capabilities store page/access/geometry revisions; agentic subprocesses return expected values through the parent-child bridge. The parent worker compares Page/access revisions, and the exact renderer checks in-app pane state and geometry revision both before native preview/activate and after asynchronous completion. Any mismatch returns page_context_stale without entering the backend. Stale asynchronous results contain neither preview nor target. Pane-bound or in-app visibility changes invalidate old WebSessions without rebuilding Page identity. Background Pages obtain exact targets directly through resolve. macOS window order, occlusion, position, and minimization do not affect binding or screenshot decisions. Leases are not released before close, initial-observe failure, owner disconnection, or process cleanup completes. Target replacement revokes old Page identity. Owner WebSocket disconnection immediately revokes all its bindings and wakes pending exact-socket requests. Component concurrency verification with two connections and 48 bindings confirmed commands go only to the originating connection and disconnecting one does not affect the other. Installed two-window transfer/rollback, temporary screenshot-artifact retention, and the unified three-backend parity suite are complete. A dedicated permission card is a later UI item outside this functionality-only scope.
