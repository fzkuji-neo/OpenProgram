Web Use: control only built-in browser Pages

An agent can call web_use, or let GUI Agent Harness execute continuously through the same interface. The runtime binds an exact Page and pins one of three browser backends for execution.

System structure

The three backends are alternative execution paths. The runtime pins one when creating the WebSession and confines every action to the same Page.

Representing four webpages in one window

Currently, list_pages returns both tab_entries + pages: the former describes single/split layout and pane ordering; the latter provides independently controllable exact Page tokens. Cross-window targets retain the same structure, adding an outer windows[], while each Page retains its original window_id. For the full fields, see Multi-Page data model.

Chat rendering stability

When a live normal assistant reply or its corresponding runtime card exists, Web Use tree updates must not trigger transcript reload. A standalone run without a persisted runtime card may perform one initial hydration. This preserves existing historical message element identity and prevents streaming replies, scroll positions, and message-action state from being reset.
